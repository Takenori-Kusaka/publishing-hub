# AI に実装させるリポジトリで「作成者が自分の変更を承認できない」をブランチ保護で強制する — pit-in-template の始め方

:::note info
この記事は、生成AIを使って作成し、筆者が内容を確認・修正したうえで公開しています。
:::

# 解決したい課題

生成AIのエージェントに実装を任せると、変更は人が読める速度を超えて増えます。その結果、プルリクエストの承認が「全部読んでから押す」から「とりあえず押す」へ縮退します。承認を得たあとに自分で push して内容を変えられる設定のままでは、承認の記録が何も保証しません。

この記事では、ピットイン方式(AI が実装を主導する前提の開発プロセス)の準拠テンプレートを使い、次の2点をリポジトリの設定で強制する手順を示します。

- 作成者は自分の変更を承認できない(最後の push の後に承認を要する)
- 自動検証(G-5)を通らない変更は既定ブランチへ入らない

- 概要(Zenn): [ピットイン方式とは — AI が実装する時代の開発プロセスを、一枚の図で理解する](https://zenn.dev/takenori_kusaka/articles/pit-in-process-overview)
- テンプレート: [Takenori-Kusaka/pit-in-template](https://github.com/Takenori-Kusaka/pit-in-template)
- 標準本文: [Takenori-Kusaka/process-compass](https://github.com/Takenori-Kusaka/process-compass)

# 技術選定理由

## 規約ではなくルールセットで止める

「作成者は承認しない」は、規約に書くだけでは守られません。ピットイン方式は、実行環境の設定で強制できる項目を必ずそちらへ降ろし、降ろせない項目は遮断できたものとして数えない、という方針を取ります。GitHub では、ブランチ保護よりも後発の[リポジトリルールセット](https://docs.github.com/ja/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)が JSON で書けて、リポジトリをまたいで同じ設定を配れるため、テンプレートはルールセットの JSON を同梱しています。

要点は `require_last_push_approval` です。これが `true` でないと、承認を得たあとに作成者が push して内容を変えられます。GitHub の[プルリクエストのルールの説明](https://docs.github.com/ja/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging)にあるとおり、最後の push を行った人以外の承認が要るようになります。

## 必須チェックを1つに集約する

個々の検査ジョブを必須チェックに並べると、検査を足すたびに保護設定を変える必要があります。テンプレートは集約ジョブ `gate-g5` の1つだけを必須にし、実際に走るテスト・静的解析・ライセンス検査のコマンドは言語ごとのアダプタから差し込みます。

# 手順

## 1. テンプレートからリポジトリを作る

GitHub の **Use this template** から新しいリポジトリを作り、手元へ clone します。

## 2. プロセス構成を決める

Claude Code でリポジトリを開き、次を実行します。

```text
/process-init
```

人数・事業の段階・品質要求・最悪の場合の帰結・開発形態などの設問に答えます。回答から、`process.config.json`(機械が読む構成)と `PROCESS-PROFILE.md`(人が読む構成書)を生成します。あわせて、有効なゲートだけを残したワークフローと、規模に応じたルールセットも生成されます。

## 3. ルールセットを適用する

3〜9名の体制で生成されるルールセットは次のとおりです。テンプレートの実装から逐語で抜粋しています。

```jsonc
// https://github.com/Takenori-Kusaka/pit-in-template/blob/main/.github/rulesets/team.json
{
  "name": "team",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] }
  },
  "rules": [
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 1,
        "dismiss_stale_reviews_on_push": true,
        "require_code_owner_review": false,
        "require_last_push_approval": true,
        "required_review_thread_resolution": true
      }
    },
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": true,
        "required_status_checks": [{ "context": "gate-g5" }]
      }
    },
    { "type": "non_fast_forward" },
    { "type": "deletion" }
  ]
}
```

リポジトリの Settings → Rules → Rulesets から **Import a ruleset** でこの JSON を取り込みます。`~DEFAULT_BRANCH` は既定ブランチを指す GitHub の予約語です。

## 4. 自動検証(G-5)のワークフローを確認する

必須チェック `gate-g5` を出すワークフローの冒頭です。構成が未設定のあいだは検査の中身を判定しない、という分岐から始まります。

```yaml
# https://github.com/Takenori-Kusaka/pit-in-template/blob/main/.github/workflows/gate-g5.yml
name: gate-g5

on:
  pull_request:
    # ...
    types: [opened, synchronize, reopened, edited, labeled, unlabeled]
  # ...
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pull-requests: write
  # ...
  issues: read

jobs:
  # プロセス構成が未設定のあいだは、検査の中身を判定しない
  config:
    name: config
    runs-on: ubuntu-latest
    outputs:
      configured: ${{ steps.read.outputs.configured }}
    steps:
      - uses: actions/checkout@v4
      - id: read
        run: |
          v=$(node -e "const c=require('./process.config.json');console.log(c.configured===false?'false':'true')")
          echo "configured=$v" >> "$GITHUB_OUTPUT"
          if [ "$v" = "false" ]; then
            echo "::notice::プロセス構成が未設定です。/process-init を実行するまで G-5 の検査は実施しません"
          fi
```

テストや静的解析のコマンドは `adapters/<stack>.json` から差し込まれます。`none` を選んで空のままにすると G-5 は失敗します。検査を実施していない状態を、通過した記録にしないためです。

## 5. 次の一手に従う

以降は `/pit` を実行し、出力された次の一手に従います。人の判断を要する段階(ゲートの判定、受入基準へ戻る判断、出荷の実行)では、AI は先へ進まず、待つ席を示して止まります。

# 落とし穴

- **1人 + AI の体制では、独立レビュー(G-6)は原理的に埋まりません。** `require_last_push_approval` を有効にしても、承認できる他人がいなければ既定ブランチへ入れられなくなります。テンプレートはこの場合、G-6 を省略ではなく「未達」として表示し続けます。
- **ルールセットが止めるのは、変更の作成者本人による承認です。** 作成者が AI や bot のとき、作成を指示した人は作成者ではありません。指示した人の承認は、ルールセットでは止まりません。標準では出荷判定(G-7)の証跡の集約で差し戻します。
- `main` 以外を既定ブランチにしている場合は、`gate-g5.yml` の `push.branches` を改めます。

# まとめ

| 強制したいこと | 置き場所 |
| --- | --- |
| 作成者は自分の変更を承認できない | ルールセットの `require_last_push_approval: true` |
| 自動検証を通らない変更を入れない | 必須チェック `gate-g5` と `strict_required_status_checks_policy: true` |
| 検査を実施していない状態を通過にしない | アダプタが空なら G-5 が失敗する |

プロセスの全体像(二層構造、8つのゲート、3つの原則)は、冒頭の Zenn の記事にまとめています。
