# 査読と採否の手順（記録）

原稿（正本と派生物）の査読を担当に渡すときの手順と、それぞれが要る理由（実際に起きたこと）の記録です。PR #38 の文書のうち、2026-09 の本の改訂と派生物の作成で使って効いた部分だけを残しました。機械の検査（`npm run check`、[linting.md](../linting.md)）が見る範囲の外を扱います。

取りまとめ役が担当への指示書を作るときに、パスを指定して読みます。どの文書からも自動では読み込ませません。リポジトリ直下の `.ignore` で、普段の検索からも外してあります。

## 1. 事実の査読と読者役を両方回す

事実の査読と、文脈ゼロの読者（コールドリード）の両方を回します。片方で他方の代わりはできません。

- **事実の査読**は、別のセッションの査読担当が行います。正本・リポジトリ・書き直し前後の原稿・指示書を読むので、事実の食い違いは見つけられます。書き手と同じ知識を持つため、第三者が読めるかは見つけられません。
- **文脈ゼロの読者**は、別のセッションの読者役が務めます。原稿のテキストだけを読むので、第三者が読めるかは見つけられます。正本を読んでいないため、事実が正しいかは判定できません。

起きたこと:

- SNS 10 本は、事実の査読で [止める] が 0 件でした。原稿だけを渡した読者役に読ませると、9 本は 1 投稿目から何の製品か分からず、10 本すべてが読者の知らない「本」を前提にしていました。
- 本の改訂では、書き手 7 人全員が検査のエラー 0 を報告しました。そのあとで、事実の査読が [止める] 29 件と [直す] 184 件を出しました（例:「レビューでも指摘されました」「9 月 3 日の修正」）。

## 2. 事実の査読担当に渡すこと

### 2.1 読むもの

正本の該当箇所、リポジトリ、書き直し前と後の両方の原稿、指示書を読ませます。後の版だけを読ませません。書き直しで消えたものは、後の版だけを読んでも見えないためです。

### 2.2 見る観点

| 観点 | 見ること | 起きたこと |
| --- | --- | --- |
| 正本に無い主張 | 改訂前からある文でも、正本にも実装にも裏付けがなければ止める | 20 本すべてが検査の 12 段階に合格したあとで、査読が次の文を見つけた。Qiita「数十ミリ秒」「原則は 4 つ」（正本は 5 つ）、note「効きました」「忙しいときに破ります」、SNS「費用は…だけ」 |
| 言い換えでかわす | 規則に当たった文を同義語や婉曲表現で言い換えて通していないか。正本に無い理由を作っていないか | 評価の最中に「理由を作って足しません」を書き足した。その 16 分後、Gemini が Playwright の選定理由を作った。note は「コミット」を「変更」に言い換えて V10 を通した |
| 事実の欠落と変更 | 数値・日付・件数・固有名が、書き直し前と同じか | 英字語を訳したときに、事実が変わった訳（「置き換え事故」「5 つの年齢帯を総当たり」）が出た |
| 外した番号は脚注へ | 本文から外した番号が、脚注に移っているか。消えていないか | 番号 7 件が脚注に移らずに消えた（第Ⅴ部 3 件、第Ⅵ部 4 件） |
| 引用の改変 | 引用符の中が原文のままか | 訳した文を引用符に入れたまま残した（第Ⅱ・Ⅲ・Ⅵ部）。Qiita は textlint の敬体混在を避けようとして、原則の引用を改変した |
| 呼び名の揺れ | 呼び名が初出で 1 回宣言され、以後そろっているか | 「中心の輪」は宣言なしに使われ、章ごとに揺れた。「保管庫」は宣言より前に出た。note 3 本の間で呼び名が割れた |
| コードと出典の一致 | 抜粋したコードが出典の実装と一致するか | Qiita の 38 ブロックはすべて別のリポジトリが出典で、Q12 は注意止まりだった。一致しているかは、書き手の自己申告しか根拠がなかった |

### 2.3 指摘の書き方

- 指摘には、該当の文を必ず引用します。重さを 3 段で付けます。**止める**は事実の欠落・変更、正本に無い主張、読めない図です。**直す**は読みにくい文、型の崩れ、呼び名の揺れです。**任意**は好みです。引用の無い指摘は、採否を決めるときに検証できません（2026-09-21 の派生物の採否では、引用が無い別のモデルの指摘を不採用にしました）。
- 「問題なし」と書く前に、原稿ごとに候補を 3 つ以上挙げ、退けたものは理由を書きます。候補が 1 つも挙がらない原稿は、見ていない原稿と区別できないためです。
- 査読担当は原稿を編集しません。指摘だけを書き、報告はファイルに残します。採否を決める前に原稿が変わると、何を採用したかを追えないためです。

## 3. 読者役に渡すこと

1. 原稿の本文と題名を、1 つのテキストファイルに書き出して渡します。frontmatter のほかの項目、脚注、リポジトリの情報は入れません。SNS は、どれがタイムラインに流れる 1 投稿目かを明記します。本文だけを渡したときは、題名まで読者役から落ちました。
2. 媒体の読者像を 1 つ与えます。例: SNS は「タイムラインで偶然見た技術者」、Qiita は「検索から来た実務 3〜5 年の技術者で、題の課題を解きたい」、note の保護者向けは「IT と無縁の仕事をしている小学生の親」、意思決定者向けは「プログラムは書かない管理職」です。
3. 読者役には、そのファイル以外を開かせません（リポジトリ、正本、リンク先、ウェブ）。分かったふりもさせません。開けば文脈ゼロでなくなり、書き手と同じ知識で読むことになります。
4. 原稿ごとに次を答えさせます。「9 本は何の製品か分からない」は、最初の問いへの答えでした。
   - 冒頭（SNS は 1 投稿目）だけで、話の中身と製品（誰向けの何か）が分かるか
   - 意味が取れなかった語と文（引用）。前提の知識を求められた箇所（引用）
   - 読み終えて、次の行き先が分かるか
   - 離脱しそうになった箇所（引用と理由）
   - 締めの段落が本文から自然に出てくるか

読者役は LLM で、人の読者ではありません。「温かく感じる」「いいねしたくなる」のような反応の記述は、採否の根拠にしません。根拠にするのは、原稿から確かめられる事実（何が書いてあるか、何が定義されていないか、どこを指すリンクか）だけです。

## 4. 指摘の採否を決める

指摘（査読担当、読者役、別のモデル、オーナーの問いかけ）は、すべて採用するものではありません。指摘ごとに、規則に照らして決めます。

1. **関係する規則と、その規則がある理由を先に読む。** 理由は、docs、ポリシーの `//` の注記、規則を入れたコミットの文にあります。理由を説明できないまま規則を変えません。
2. **採否の表を作る。** 列は「指摘 / 採否（採用・一部採用・不採用） / 根拠にした規則 / 直し方」です。表はファイルに残します。
3. **根拠にしてよいもの**は、媒体の役割と読者（[publishing-model.md](../publishing-model.md) §1）、編集の規則（[social-editorial-guide.md](../social-editorial-guide.md) と AGENTS.md 2 章）、事実の捏造禁止、オーナーの決定です。**根拠にしてはいけないもの**は、読者役の感想、引用の無い指摘、検証できない主張です。
4. **自分が過去に出した指示も採否の対象にする。**
5. **規則と衝突する指摘は、衝突を示して、規則の理由に沿う直し方を探す。** 規則を変えるのは、理由を読んだうえで、それでも読者のためにならないと言えるときだけです。

起きたこと:

- 読者役の報告を受けて、規則の理由を読まずに規則を変えにかかり、オーナーに止められました。
- 2026-09-21 の派生物の採否は 13 件で、うち 4 件を不採用にしました。例: SNS に紹介ページのリンクが無いという指摘は、出口を 1 つにする規則と、想定読者が製品の顧客でないことから不採用にしました。
- 指摘の原因が、取りまとめ役の指示書にあったものがあります。派生物にも本の呼び名を使わせた指示と、SNS にも原則の締めを置かせた指示です。
