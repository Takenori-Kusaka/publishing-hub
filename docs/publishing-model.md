# マルチプラットフォーム出版・配信アーキテクチャモデル (ADR)

## Status
Approved / Revised (2026-09-12)

## Context
リポジトリ `publishing-hub` は、技術書籍（Zenn）や技術記事（Zenn/Qiita）、ビジネスコラム（note）、ならびにSNS（LinkedIn/Bluesky）へのマルチチャネル配信を統合管理する。
単一のMarkdownを各媒体に機械的にコピー＆ペースト（マルチポスト）する運用は、 「**プラットフォームごとの読み手の文脈不一致**」「**重複コンテンツによるSEOペナルティ**」「**技術記事としての深さの欠如**」 などの重大な品質低下を招く。

本ドキュメントでは、各媒体の特性に最適化されたコンテンツバリアント（派生物）の設計方針、相互リンク戦略、媒体別Linterの使い分け、および人手による査読・プレビューを可能にする検証システム（CI）の詳細を決定する。

---

## Decisions

### 1. 媒体別読み手設計（Target Audience & Granularity）

各メディアの読者層、および推奨されるコンテンツの粒度・文脈を以下のように定義・強制する。

| プラットフォーム | ターゲット読者層 | 最適なコンテンツの粒度・文脈 | 主な役割・ポジショニング |
| :--- | :--- | :--- | :--- |
| **Zenn** | **技術的探究心の強いエンジニア** | 長文、体系的、厳密な解説。ソースコードの完全性とアーキテクチャ解説、動作する完成品リポジトリの提示が必須。 | **「正本（SSOT）」**<br>教科書・技術解説のマスターピース。 |
| **Qiita** | **課題解決を急ぐ実践的エンジニア** | 課題とその解決策（How-To）、技術選定の客観的理由、再現性の高いコードブロック、公式ドキュメントや一次情報源のリンクが必須。 | **「技術課題解決バリアント」**<br>短時間で価値が伝わるエンジニア向けレシピ。 |
| **note** | **プロダクトマネージャー、意思決定者、一般ビジネス層** | ストーリー性、エッセイ調、背景にある人間的ドラマや組織課題の解決。生コードも図の記法も置かず、構造は言葉で語る（図が要るなら画像を手動で添える）。 | **「思想・ナラティブバリアント」**<br>なぜそれを作ったか、何が変わるかの本質提示。 |
| **SNS (LinkedIn / Bluesky)** | **ネットワーキング中のカジュアル読者** | LinkedIn は 1,600 字まで 字の短論考、Bluesky は 260 grapheme までの 1 つの観察。UTM付きリンクカードで正本へ誘導。 | **「ディスカバリーチャネル」**<br>本稿（SSOT）への導線、認知拡大。 |

---

### 2. 単一ミラー（重複コンテンツ）の防止と相互リンクトポロジー

同じ内容の単純コピペは、検索エンジン（Google等）によって「重複コンテンツ」として認識され、ドメイン全体のSEO評価（PageRank）が低下するペナルティを受ける。本基盤では以下の「環状リンクトポロジー」を強制する。

```text
         [ Zenn / GitHub (SSOT) ] <──────────────────┐
                     │                                │
                     ├────────────────┐               │
                     ▼                ▼               │ Canonical /
              [ Qiita Variant ]  [ note Variant ]     │ Source Link
                     │                │               │ (SEO評価の集中)
                     └───────┬────────┘               │
                             ▼                        │
                      [ SNS Post ] ───────────────────┘
                     (LinkedIn/Bsky)
```

1. **カノニカル（正本）への集約:**
   - Qiita / note の記事内には、必ず正本である **「Zenn記事URL」** または **「GitHubリポジトリURL」** への直接リンクを最上部または冒頭に明記する。
   - これにより、Googleのクローラーに対して「オリジナルはGitHub/Zennであり、他は最適化されたバリアントである」というセマンティクスを伝え、SEO評価を正本に集中させる。
2. **コンテンツの非対称性（Asymmetry）の確保:**
   - **Zenn:** コード実装の完全性と、文字数制限のない網羅性を追求。
   - **Qiita:** 「3. コアコードの実装詳細」など、読者がコピペして今すぐ使える特定の関数・ロジックのみをハイライトして解説。全体コードは「GitHubを参照」として役割を分割。
   - **note:** 「2. 技術選定理由」の背景、意思決定、人間的 friction にフォーカス。コードや設定ファイルのテキストは一切記述しない。

### 3. 媒体別 Linter の使い分けと適用設計

配信品質を自動的に担保するため、Linter を「校正」「構造」「用語」の 3 層に分け、媒体ごと・題材ごとに別々の規則を当てる。1 本の設定を全ファイルに共有しない。詳細は [linting.md](linting.md)。

```text
                          [ npm run check ]  (scripts/lint/check-all.mjs)
                                  │
      ┌───────────────┬───────────┼───────────────┬──────────────┐
      ▼               ▼           ▼               ▼              ▼
 [ 校正 ]        [ 構造 ]     [ 用語 ]      [ 非対称 ]      [ 既存 ]
 textlint        zenn / qiita  terms        variants        books / figures
 媒体別5本の     note / social 題材別辞書   重複率・導線    japanese / links
 プロファイル    genre・規範   表記ゆれ検出 タイトル・節構成
```

### 4. 内容の査読（Review）と見え方プレビューの仕掛け（CI）

公開前に、配信する内容の一部（SNS の本文と URL カードの中身、全媒体の検査の結果）を PR 上で確かめられる仕掛けを提供する。媒体ごとの表示（レンダリング）は媒体ごとに違い、PR では確かめられないため、本格的な査読は公開された記事で行う（2026-09-21 のオーナーの決定。AGENTS.md 1 章）。

1. **SNS用 redacted プレビュー自動レンダリング (`render.mjs`):**
   - PRが作成されると、GitHub Actions (`social-check.yml`) が `npm run social:render` を自動実行。
   - 投稿主の識別子を伏せた上で、UTMパラメータを付けた本文と、URLカードの中身（タイトル・説明・URL・サムネイルのパス）を Markdown に書き出す。文字数（Graphemeカウント）は同じワークフローの `social:validate` が検査する。
   - 成果物を PR Artifacts としてアップロードし、人間がマージ前に本文とカードの中身を読めるようにする。SNS 上での実際の見え方は、ここでは確かめられない。
2. **note 原稿の検査と配信パッケージ (`check-note.mjs` / `build-note.mjs`):**
   - note の原稿は `platforms/note/public/<id>.md` に正本とは別に書く。ビルドは検査（生コード・Mermaid・表の禁止、正本への導線、物語の要素）に通った原稿だけを WXR / HTML に変換し、`status`・`source`・`canonical_url`・検査結果をマニフェストに記録して GHA Step Summary に掲示。
   - `publish-note` は原稿の `status` が `ready` のときだけ投稿する。`draft` はビルドまでで止まる。
3. **Qiita 同期の gate (`publish-qiita.yml`):**
   - 同期の前に Qiita プロファイルの校正、レシピ要件、正本への導線と重複率、複数称の検査を通す。検査に落ちた記事は同期されない。
4. **検査レポート (`validate.yml`):**
   - `npm run check` の 12 段階の結果を `.tmp/lint/report.md` にまとめ、Step Summary と Artifact に出す。

## Consequences
- **メリット:**
  - 各メディアの特性を突いた「刺さる」配信が自動化され、メディアごとのコピペ重複によるSEO低下リスクが完全に消失する。
  - 「私たち」などの複数称や、低品質（コードなし・リンクなし）な記事の Qiita 自動同期が CI レベルで永久に遮断される。
  - プレビューと検査レポートにより、本文・カードの中身と検査の結果をマージ前に Actions 上で確かめられる。媒体ごとの見え方を含む本格的な査読は、公開された記事で行う。
