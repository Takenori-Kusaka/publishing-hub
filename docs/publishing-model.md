# マルチプラットフォーム出版・配信アーキテクチャモデル (ADR)

## Status
Approved / Revised (2026-09-12)

## Context
リポジトリ `publishing-hub` は、技術書籍（Zenn）や技術記事（Zenn/Qiita）、ビジネスコラム（note）、ならびにSNS（LinkedIn/Bluesky）へのマルチチャネル配信を統合管理する。
単一のMarkdownを各媒体に機械的にコピー＆ペースト（マルチポスト）する運用は、 「**プラットフォームごとの読み手の文脈不一致**」「**重複コンテンツによるSEOペナルティ**」「**技術記事としての深さの欠如**」 などの重大な品質低下を招く。

本ドキュメントでは、各媒体の特性に最適化されたコンテンツバリアント（派生物）の設計方針、相互リンク戦略、媒体別Linterの使い分け、および人手による査読・プレビューを可能にする検証システム（CI）の詳細を決定する。

---

## Decisions

### 1. 媒体別読み手設計（Target Audience & Granularity）

各メディアの読者層、および推奨されるコンテンツの粒度・文脈を以下のように定義・強制する。

| プラットフォーム | ターゲット読者層 | 最適なコンテンツの粒度・文脈 | 主な役割・ポジショニング |
| :--- | :--- | :--- | :--- |
| **Zenn** | **技術的探究心の強いエンジニア** | 長文、体系的、厳密な解説。ソースコードの完全性とアーキテクチャ解説、動作する完成品リポジトリの提示が必須。 | **「正本（SSOT）」**<br>教科書・技術解説のマスターピース。 |
| **Qiita** | **課題解決を急ぐ実践的エンジニア** | 課題とその解決策（How-To）、技術選定の客観的理由、再現性の高いコードブロック、公式ドキュメントや一次情報源のリンクが必須。 | **「技術課題解決バリアント」**<br>短時間で価値が伝わるエンジニア向けレシピ。 |
| **note** | **プロダクトマネージャー、意思決定者、一般ビジネス層** | ストーリー性、エッセイ調、背景にある人間的ドラマや組織課題の解決。生コードは排除し、概念図やアーキテクチャ思考を重視。 | **「思想・ナラティブバリアント」**<br>なぜそれを作ったか、何が変わるかの本質提示。 |
| **SNS (LinkedIn / Bluesky)** | **ネットワーキング中のカジュアル読者** | 300字前後の超要約文、1テイクのアウトプット図、UTM付きリンクカード。 | **「ディスカバリーチャネル」**<br>本稿（SSOT）への導線、認知拡大。 |

---

### 2. 単一ミラー（重複コンテンツ）の防止と相互リンクトポロジー

同じ内容の単純コピペは、検索エンジン（Google等）によって「重複コンテンツ」として認識され、ドメイン全体のSEO評価（PageRank）が低下するペナルティを受ける。本基盤では以下の「環状リンクトポロジー」を強制する。

```text
         [ Zenn / GitHub (SSOT) ] <──────────────────┐
                     │                                │
                     ├────────────────┐               │
                     ▼                ▼               │ Canonical /
              [ Qiita Variant ]  [ note Variant ]     │ Source Link
                     │                │               │ (SEO評価の集中)
                     └───────┬────────┘               │
                             ▼                        │
                      [ SNS Post ] ───────────────────┘
                     (LinkedIn/Bsky)
```

1. **カノニカル（正本）への集約:**
   - Qiita / note の記事内には、必ず正本である **「Zenn記事URL」** または **「GitHubリポジトリURL」** への直接リンクを最上部または冒頭に明記する。
   - これにより、Googleのクローラーに対して「オリジナルはGitHub/Zennであり、他は最適化されたバリアントである」というセマンティクスを伝え、SEO評価を正本に集中させる。
2. **コンテンツの非対称性（Asymmetry）の確保:**
   - **Zenn:** コード実装の完全性と、文字数制限のない網羅性を追求。
   - **Qiita:** 「3. コアコードの実装詳細」など、読者がコピペして今すぐ使える特定の関数・ロジックのみをハイライトして解説。全体コードは「GitHubを参照」として役割を分割。
   - **note:** 「2. 技術選定理由」の背景、意思決定、人間的 friction にフォーカス。コードや設定ファイルのテキストは一切記述しない。

### 3. 媒体別 Linter の使い分けと適用設計

配信品質を自動的に担保するため、Linterを階層別に配置し、デプロイ前に検証（gate）する。

```text
                      [ npm run check ]
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
   [ Textlint ]       [ Japanese Linter ]   [ Qiita Quality Linter ]
 (books/articles)     (check-japanese.mjs)  (check-qiita-quality.mjs)
         │                    │                    │
  ・Zenn原稿全体の      ・中国語/第2水準漢字  ・1500文字以上の深さ
    表記揺れチェック     の検知               ・GitHubリンク必須化
  ・技術日本語規則      ・単数個人称の強制    ・公式ドキュメント2件
    (ja-technical)        (「私たち」の排除)  ・コードブロック3箇所
```

1. **Textlint (Zenn正本・全ドキュメント共通):**
   - 商業技術出版レベルの日本語表現を担保するため、`preset-ja-technical-writing` を適用。
2. **Japanese Linter (`scripts/check-japanese.mjs`):**
   - **主語の個人化 (`J3`):** このリポジトリで管理されるのは個人発信のみであるため、「私たち」「我々」「弊社」などの複数称・組織称を検知してエラーと。個人（私、著者、当方）またはシステム主語に統一。
3. **Qiita Quality Linter (`scripts/check-qiita-quality.mjs`):**
   - 技術記事としての品質をシステム的に担保するため、新規作成記事に対して「1500文字以上」「GitHubリンク」「公式ドキュメント2件」「コードブロック3箇所」を義務付け。

### 4. 内容の査読（Review）と見え方プレビューの仕掛け（CI）

本番公開前に、人間が「実際の配信結果（レンダリング結果）」をPR上で精密に確認できる仕掛けを提供する。

1. **SNS用 redacted プレビュー自動レンダリング (`render.mjs`):**
   - PRが作成されると、GitHub Actions (`social-check.yml`) が `npm run social:render` を自動実行。
   - YAML内の機密情報をマスクした上で、文字数（Graphemeカウント）と、UTMパラメータが自動付与されたURLカードの見た目を Markdown テーブルとして完全書き出し。
   - 成果物を PR Artifacts としてアップロードし、人間がマージ前に「実際のスマホや画面でどう見えるか」を100%確認可能にする。
2. **note用 WXR警告システム (`build-note.mjs`):**
   - noteビルド時、Zenn特有の記法（Mermaid図、脚注など）を検出した場合、自動的に「警告フラグ（Warning）」をマニフェストファイルに追記し、GHA Step Summary（概要）に直接警告リストを掲示。
   - 執筆者はマージ前に「Mermaidを画像として手動配置する必要がある」などの作業を事前に把握できる。

---

## Consequences
- **メリット:**
  - 各メディアの特性を突いた「刺さる」配信が自動化され、メディアごとのコピペ重複によるSEO低下リスクが完全に消失する。
  - 「私たち」などの複数称や、低品質（コードなし・リンクなし）な記事の Qiita 自動同期が CI レベルで永久に遮断される。
  - プレビューと警告マニフェストにより、手動公開に劣らない「内容の最終査読プロセス」がマージ前にActions上で確立される。
