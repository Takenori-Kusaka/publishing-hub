# 出版・配信アーキテクチャモデル (ADR)

## Status
Approved

## Context
リポジトリ `publishing-hub` は現在、Zenn向けの技術書籍および記事を管理・自動同期する構成として運用されています。この度、Zenn・Qiita・note に加え、個人としての専門的知見の発信や技術的なコミュニティとの対話の活性化を目的として、**LinkedIn** および **Bluesky** へのSNS配信基盤を本リポジトリへ統合することになりました。

SNS配信にあたっては、以下の課題をクリアする必要があります。
1. **情報の断片化防止:** 長文の専門記事（正本）と、SNS向けの短文（配信原稿）との論理的な関係が乖離しないこと。
2. **再現性と確実性:** 公開する文面がPull Request（PR）上で事前に人間によって確認・プレビューでき、勝手に書き換わらないこと。
3. **セキュリティと規約遵守:** 外部サービスのAPI制限や規約に違反しないこと。特にパスワードや非公式APIトークンの漏洩、スクレイピングによるアカウント停止リスクを排除すること。

## Decisions

### 1. 「正本 ＋ 媒体別派生物」方式の採用
長文の技術書籍（`books/`）や技術記事（`articles/`）を知識・論証の「正本（SSOT）」と位置づけます。SNS向けの配信原稿は `social/posts/<id>.yaml` という独立した独立成果物として管理します。
正本からSNS向けに機械的に切り詰めて即時送信する「自動要約クロスポスト」は行いません。AI（LLM）による下書きの支援は認めますが、生成結果をYAMLファイルとして確定し、PR上で人手レビューを経てマージします。

### 2. 配信処理（Actions実行時）における決定性
公開ワークフロー（GitHub Actions）の実行時において、要約、翻訳、言い換え、ハッシュタグ自動生成などの非決定的な生成AI処理は一切禁止します。
 Actionsが行うのは、以下の決定的な変換に限定されます。
- 改行コードの正規化および末尾余白の除去
- URLへのUTMパラメータ自動付与
- Bluesky用のfacets（リンク、メンション、ハッシュタグ）の自動生成
- 画像アップロード時のEXIF等メタデータの自動除去
- API payloadの構築と送信

### 3. 公式API経由の通信限定（ブラウザ自動操作の禁止）
LinkedInは公式のPosts APIおよびImages API、Blueskyは公式のAT Protocol（`@atproto/api`）のみを利用します。
Playwright等によるブラウザの自動操作、cookieの偽装、セッション `li_at` の利用、HTMLスクレイピングは一切行いません。これは、外部サービス（特にLinkedIn）の不正自動操作に関する利用規約を遵守し、アカウント制限のリスクを完全に排除するためです。

### 4. 認証情報の厳重な保護
SNS投稿用のトークン（`LINKEDIN_ACCESS_TOKEN`）やアプリパスワード（`BSKY_APP_PASSWORD`）は、すべてリポジトリ直のSecretsではなく、GitHub Actionsの **Environment Secrets**（`social-production`）として保護します。
Environmentに「Required Reviewers（必須承認者）」を設定することで、マージ後の投稿実行時に手動による承認を必須とし、意図しない自動投稿や第三者へのシークレット流出を防ぎます。

## Consequences
- **メリット:** 
  - SNS投稿内容の完全な履歴管理（誰が、いつ、どのコミットを配信したか）が可能になる。
  - Zennの既存の自動デプロイプロセスや、既存の日本語校正（textlint）を一切破壊しない。
  - 生成AIの出力のブレ（ハルシネーション等）がSNSに無検査で直接配信されるリスクを完全にゼロにできる。
- **トレードオフ:**
  - 配信原稿をYAMLファイルとして個別に作成・保守する必要があるため、執筆者の運用コストがわずかに増加する。しかし、このコストは配信品質の担保と炎上・誤公開防止のために必要なトレードオフであると判断。
