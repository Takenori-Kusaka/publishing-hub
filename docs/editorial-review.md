# 原稿の査読と仕上げの基準

正本（Zenn）と派生物（Qiita・note・SNS）を、公開に出せる状態へ仕上げるときの基準です。機械の検査（[linting.md](linting.md)）が見る範囲の外を扱います。

この基準の目的は、「自己レビューしたか」ではなく、**誰がどの文脈で何を読み、何を見つけ、どう採否を決めたか**を示せるようにすることです。「自己レビュー済みですか」と問われる時点で、査読の中身が外から見えていません。

## 1. なぜこの基準があるか

2026-09 の『生成AIに実装を任せて商用サービスを作る』の改訂と派生物の作成で、次のことが起きました。

- 機械の検査（12 段階）がすべて 0 件でも、オーナーの査読で「第三者が読めない」「図が簡潔すぎて分からない」「読者について語る文が本文に出ている」と指摘された
- 書き手と同じ文脈（リポジトリ、正本、指示書）を読んだ査読担当は、事実の食い違いは見つけられたが、第三者の読みやすさは見逃した。SNS 10 本は 10 本とも査読を通ったのに、原稿だけを渡した読者役に読ませると、9 本は 1 投稿目から何の製品か分からず、10 本すべてが読者の知らない「本」を前提にしていた
- 読者役の報告を受けて、規則の理由を読まずに規則を変えにかかり、オーナーに止められた

原因は 3 つです。査読の層に「書き手の文脈を持たない読者」がいなかったこと。指摘を受けてから採否を決める手順が無かったこと。そして、どちらも毎回その場で決めていたことです。

## 2. 査読の 4 層

層ごとに、読む者の持つ文脈は違います。持つ文脈が違うので、見つけられるものも違います。1 つの層で他の層の代わりはできません。

| 層 | 読む者 | 持つ文脈 | 見つけられるもの | 見つけられないもの |
| --- | --- | --- | --- | --- |
| 1. 機械の検査 | `npm run check` | 規則だけ | 形の違反（字数、禁止語、英字の密度、メタ談話の定型、導線の有無、正本との重複率） | 読んで意味が通るか。規則が拾わない型の違反 |
| 2. 事実の査読 | 別のセッションの査読担当 | 正本、リポジトリ、書き直し前後の原稿、指示書 | 事実の欠落と変更、正本に無い主張の混入、引用の改変、呼び名の揺れ、コードと出典の一致 | 第三者が読めるか（書き手と同じ知識を持つので、知識の呪いを点検できない） |
| 3. 文脈ゼロの読者（コールドリード） | 別のセッションの読者役 | 原稿のテキストだけ | 定義されていない語、読者の知らないものを前提にした文、何の製品か分からない、次の行き先が分からない、離脱しそうな箇所 | 事実が正しいか（正本を読んでいないので判定できない） |
| 4. オーナー | 著者 | すべて | 方針との整合、公開してよいか | 自分の書いた文の読みにくさ（層 3 と同じ理由で見えにくい） |

層 2 と層 3 は、両方回します。層 2 だけでは第三者の読みやすさが、層 3 だけでは事実が、保証されません。

## 3. 各層の手順

### 3.1 機械の検査

`npm run check` を、コミットしたあとにもう一度回します（[AGENTS.md](../AGENTS.md) §2.3 の手順 10）。規則が拾わない型の違反を層 2・3 で見つけたら、その型を検査に足すかを決めます（例: 「この章から 4 章で〜を扱います」「ここでは〜を並べます」型のメタ談話は、層 2・3 で見つかってから Z13 / Q18 / N14 に足した）。

### 3.2 事実の査読

- 査読担当は、書き直し前と後の両方を読む。後だけ読まない
- 指摘は必ず該当の文を引用し、重さを 3 段で付ける。**止める**（事実の欠落・変更、正本に無い主張、読めない図）、**直す**（読みにくい文、型の崩れ、呼び名の揺れ）、**任意**（好み）
- 「問題なし」と書く前に、原稿ごとに候補を 3 つ以上挙げ、退けたものは理由を書く
- 査読担当は原稿を編集しない。指摘だけを書き、報告はファイルに残す

### 3.3 文脈ゼロの読者（コールドリード）

1. 原稿の本文だけを 1 つのテキストファイルに書き出す。frontmatter、脚注、リポジトリの情報は入れない。SNS は、どれがタイムラインに流れる 1 投稿目かを明記する
2. 媒体の読者像を 1 つ与える。例: SNS は「タイムラインで偶然見た技術者」、Qiita は「検索から来た実務 3〜5 年の技術者で、題の課題を解きたい」、note の保護者向けは「IT と無縁の仕事をしている小学生の親」、意思決定者向けは「プログラムは書かない管理職」
3. 読者役には **そのファイル以外を開かせない**（リポジトリ、正本、リンク先、ウェブ）。分かったふりをさせない
4. 原稿ごとに答えさせる項目:
   - 冒頭（SNS は 1 投稿目）だけで、話の中身と製品（誰向けの何か）が分かるか
   - 意味が取れなかった語と文（引用）。前提の知識を求められた箇所（引用）
   - 読み終えて、次の行き先が分かるか
   - 離脱しそうになった箇所（引用と理由）
   - 締めの段落が本文から自然に出てくるか
5. 報告はファイルに書かせる。修正したら、**別の読者役**にもう一度読ませる（同じ読者役は前の版を覚えている）

読者役は LLM で、人の読者ではありません。「温かく感じる」「いいねしたくなる」のような反応の記述は、採否の根拠にしません。根拠にするのは、原稿から確かめられる事実（何が書いてあるか、何が定義されていないか、どこを指すリンクか）だけです。

### 3.4 オーナー

オーナーに渡す PR の本文に、§5 の証跡を置きます。オーナーが「自己レビューしたか」を問わずに済む状態で渡します。

## 4. 指摘の採否を決める

指摘（査読担当、読者役、別のモデル、オーナーの問いかけ）は、すべて採用するものではありません。指摘ごとに、規則に照らして決めます。

1. **関係する規則と、その規則がある理由を先に読む。** 理由は、この docs、ポリシーの `//` の注記、規則を入れたコミットの文にあります。理由を説明できないまま規則を変えない
2. **採否の表を作る。** 列は「指摘 / 採否（採用・一部採用・不採用） / 根拠にした規則 / 直し方」。表はファイルに残し、PR の本文から参照する
3. **根拠にしてよいもの**: 媒体の役割と読者（[publishing-model.md](publishing-model.md) §1）、編集の規則（[social-editorial-guide.md](social-editorial-guide.md)、[AGENTS.md](../AGENTS.md) §2）、事実の捏造禁止、オーナーの決定。**根拠にしてはいけないもの**: 読者役の感想、引用の無い指摘、検証できない主張
4. **自分が過去に出した指示も採否の対象にする。** 指摘の原因が指示書にあることがある（例: 派生物にも本の呼び名を使わせた指示、SNS にも原則の締めを置かせた指示）
5. **規則と衝突する指摘は、衝突を示して、規則の理由に沿う直し方を探す。** 規則を変えるのは、理由を読んだうえで、それでも読者のためにならないと言えるときだけ

例: 2026-09-21 の派生物の採否（13 件、うち不採用 4 件）。SNS に紹介ページのリンクが無いという指摘は、SNS は正本への入口で、出口は 1 つにする規則と、想定読者が製品の顧客でないことから、不採用にした。

## 5. PR の本文に残す証跡

原稿の PR の本文には、層ごとに次を書きます。

| 層 | 書くこと |
| --- | --- |
| 1 | 「検査した状態:」の行（コミット後の計測） |
| 2 | 査読担当が何を読んだか（書き直し前後、正本の該当章）、指摘の件数（止める / 直す / 任意）、反映した件数 |
| 3 | 読者役の読者像、渡したもの（原稿のテキストだけ）、見つかった件数（何の製品か分からない原稿の数、定義されていない語の数 など） |
| 採否 | 採否の表の要約と、不採用にした指摘とその根拠 |

## 6. 仕上げの基準（媒体ごと）

どの媒体も、読者は正本を読んでいません。原稿は単独で成立させます。

**全媒体**:

- 冒頭で、何の話か、何の製品か（誰向けの何か）が分かる
- 読者の知らないものを既知として扱わない（「リンク先の本の原則」「前に書いた記事」）
- 正本で作った呼び名（造語）を持ち込まない。持ち込むなら、その原稿の中で定義する
- 読者や本文について語る文（「この記事では」「ここでは〜を並べます」「結論から言うと」）を書かない
- 正本に無い数値・主張・体験談・評価を足さない

**媒体ごと**:

| 媒体 | 次の行き先 | 固有の基準 |
| --- | --- | --- |
| Qiita | 正本、GitHub、紹介ページ | 日本語にした技術用語は初出で英語の原語を併記し、検索できるようにする。手順が途切れるなら実装から逐語で補うか、該当ファイルへの導線を置く |
| note | 正本、紹介ページ、デモ | 読者の言葉だけで書く。保護者向けに開発の話（費目、実装の事故）を入れない |
| SNS | 正本の章（出口は 1 つ） | 1 投稿目で観察 1 つと製品が何かの 1 句。原則や本の話を締めに足して論点を 2 つにしない |
| Zenn（正本） | 紹介ページ、デモ、GitHub | 図は PNG を開いて、図だけで筋が追えるかを確かめる |

## 付録: 指示書の雛形

事実の査読担当と読者役に渡す指示の骨子です。実際の指示書は作業ごとに書き、この骨子を外さないでください。

**事実の査読担当**: 作業ツリーの場所 / 読むもの（方針、指示書、正本の該当章、書き直し前後）/ 見る観点（事実の保存、語彙、メタ談話、型、第三者の読みやすさ、書いてはいけないもの、図）/ 指摘の書式（引用、止める・直す・任意、退けた候補）/ ファイルを編集しない / 報告の保存先。

**読者役**: 読者像 1 つ / 読んでよいファイル 1 つだけ（他を開かない）/ §3.3 の 4 の項目 / 分かったふりをしない / 報告の保存先。
