# 生成AIの利用の開示

このリポジトリの原稿は、生成AIのエージェント（Claude Code など）が作成・改訂し、筆者が確認して公開します。読者は、読んでいる文章が生成AIを使って作られたことを知る権利があります。この文書は、どの文言を、どこに、どう置くかを決めた根拠と、検査の仕様をまとめます。

規則の値は [lint/policies/disclosure.json](../lint/policies/disclosure.json)、検査の実装は [scripts/lint/disclosure.mjs](../scripts/lint/disclosure.mjs) にあります。

## 1. 調べたこと（2026-09-13 時点）

学術出版、報道機関、配信プラットフォーム、法令と公的指針の一次資料を確認しました。

### 1.1 配信先のプラットフォーム

| 媒体 | 読者への明示 | 要点 |
| --- | --- | --- |
| Zenn | 規定なし | 生成AIの活用は禁止しない。公開前に内容の正確性を確認することを求める（[ガイドライン](https://zenn.dev/guideline)、[2026-03-10 のお知らせ](https://info.zenn.dev/2026-03-10-ai-contents-guideline)） |
| Qiita | 規定なし | AIが生成した内容は検証してから投稿し、内容に責任を持つ（[コミュニティガイドライン](https://help.qiita.com/ja/articles/qiita-community-guideline)） |
| note | 規定なし | 規約・ガイドライン・AI機能のヘルプに明示の規定はない |
| LinkedIn | 推奨 | AIに大きく依存した場合は、文脈から明らかでなければ投稿内で知らせる。投稿の責任は投稿者にある（[ヘルプ](https://www.linkedin.com/help/linkedin/answer/a1481496)） |
| Bluesky | 規定なし | AI生成コンテンツの規定もラベルの値もない（[コミュニティガイドライン](https://bsky.social/about/support/community-guidelines)） |

国内の配信先は、明示の義務と文例のどちらも定めていません。共通するのは「検証してから公開し、投稿者が責任を負う」ことです。

具体的な文例は、どれも「AIを使った」と「人が確認・編集した」の2要素を持ちます。

### 1.4 法令と公的指針

- **EU AI Act 第50条**: 公共の利益に関する事項を知らせる目的で公表するテキストは、AIで生成・改変したことを開示します。人によるレビューか編集管理があり、編集責任を負う者がいる場合は例外です。開示は、遅くとも読者が初めて見る時点で、はっきり分かる形で示します（[条文](https://artificialintelligenceact.eu/article/50/)）。行動規範の案は、テキストの上部、見出しの近く、冒頭の奥付にラベルを置く例を示します（[欧州委員会](https://digital-strategy.ec.europa.eu/en/policies/eu-icons-labelling-ai-generated-content)）。
- **中国「人工知能生成合成内容標識弁法」**: テキストの冒頭、末尾、途中の適切な位置に文字の表示を置きます（[国家互联网信息办公室](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)）。
- **日本「AI事業者ガイドライン」**: 「AIを利用しているという事実及び活用している範囲」の情報提供と、人の判断の介在を推奨します。拘束力のある表示義務や定型文はありません（[総務省・経済産業省](https://www.soumu.go.jp/main_content/001064279.pdf)）。
- **機械可読の表示**: 画像や記事のメタデータには IPTC の [digitalSourceType](https://cv.iptc.org/newscodes/digitalsourcetype/)（trainedAlgorithmicMedia など）と [schema.org の digitalSourceType](https://schema.org/digitalSourceType) があります。Markdown の frontmatter に標準のキーはありません。

本リポジトリは筆者が確認して公開するため、EU の例外に当たる可能性があります。ただしこれは法的な判断ではありません。本リポジトリは例外に頼らず、方針として開示します。

## 2. 決めたこと

### 2.1 2層で示す

**冒頭の告知**と**末尾の宣言**の2層にします。

- 冒頭の告知は、読者が初めて見る位置へ1〜2文で置きます。Medium の「冒頭2段落以内」と、EU AI Act の「読者が初めて見る時点」「テキストの上部」を手本にします。
- 末尾の宣言は、最後の見出し「生成AIの利用について」に、4つの要素を書きます。Elsevier・Wiley・Taylor & Francis の宣言文と、日経の断り書きに倣います。

告知だけでは何にどう使ったかが分からず、宣言だけでは読み終えるまで気づけません。両方を置くことで、行動規範の案が示す「ラベルと追加情報の層」と同じ構成になります。

### 2.2 宣言の4要素

| 要素 | 書くこと | 例 |
| --- | --- | --- |
| ツール名 | 使った生成AIの名前。分かる範囲でモデル名 | 生成AIの Claude（Anthropic の Claude Fable 5.1）を使いました。 |
| 用途と範囲 | 何に使ったか | 構成の検討、本文の下書きと改稿、校正に使っています。 |
| 人による確認 | 人が確認し、必要に応じて修正したこと | 筆者が内容を確認し、必要に応じて修正しました。 |
| 責任の所在 | 公開した内容の責任を誰が負うか | 公開した内容の責任は筆者が負います。 |

事実と違う宣言は、書かないより悪い開示です。ツール名と用途は、コミットの共著記録（Co-Authored-By）など、確かめられる範囲で書きます。確認していないことを「確認した」と書いてはいけません。

### 2.3 媒体ごとの形

| 媒体 | 冒頭の告知 | 末尾の宣言 |
| --- | --- | --- |
| Zenn の記事 | `:::message` の枠 | 最後の見出し（h2 か h3）「生成AIの利用について」 |
| Zenn の本 | 最初の章に `:::message` の枠 | 最初の章の最後の見出し |
| Qiita | `:::note info` の枠 | 最後の見出し（h1 か h2） |
| note | 引用（`>`） | 最後の見出し（h2） |
| LinkedIn | 本文に1文（位置は自由。末尾を推奨） | なし |
| Bluesky | スレッドのどこかの投稿に1文 | なし |

- **本**は、Taylor & Francis が書籍の開示を序文かはじめにとしているのに倣い、序文にあたる最初の章（`config.yaml` の `chapters` の先頭）に置きます。Zenn の本は章ごとに直接リンクされるため、途中の章から読み始めた読者は最初の章の告知を見ません。全章への告知は今のところ求めていません。必要になれば `books.scope` を広げます。
- **frontmatter には置きません。** 読者に表示されないうえ、Qiita CLI は同期のたびに frontmatter を決まったキーで書き直し、独自のキーを消します。
- **署名欄（タイトルや著者名）には置きません。** Google が「著者の署名欄に AI と書くのはふさわしくない」としているためです。
- **SNS** は文字数の制約が厳しいため、1文だけにします。LinkedIn のヘルプの推奨に倣い、Bluesky にも同じ原則を当てます。

### 2.4 文例

Zenn の記事の冒頭:

```md
:::message
この記事は、生成AIを使って作成し、筆者が内容を確認・修正したうえで公開しています。使ったツールと用途は、末尾の「生成AIの利用について」に書いています。
:::
```

Zenn の記事の末尾:

```md
## 生成AIの利用について

この記事の作成には、生成AIの Claude（Anthropic の Claude Fable 5.1）を使いました。構成の検討、本文の下書きと改稿、校正に使っています。筆者が内容を確認し、必要に応じて修正しました。公開した内容の責任は筆者が負います。
```

本の最初の章は、主語を「本書」「著者」にします（開発プロセスの本は一人称に「本書」を使う規範を持つためです）。Qiita は冒頭を `:::note info`、note は冒頭を `> ` にします。

SNS:

```text
LinkedIn: ※この投稿は、生成AI（Claude）で下書きし、筆者が内容を確認して公開しています。
Bluesky:  ※生成AI（Claude）で下書きし、筆者が確認して投稿しています。
```

## 3. 検査

| コード | チェッカー | 内容 | 強度 |
| --- | --- | --- | --- |
| Z8 | `check-zenn` | 記事と、本の最初の章に、冒頭の告知と末尾の宣言（4要素、最後の見出し）がある | エラー |
| Q11 | `check-qiita` | Qiita の記事に同じもの（冒頭は `:::note`） | エラー |
| N9 | `check-note` | note の原稿に同じもの（冒頭は引用） | エラー |
| SOCIAL_AI_DISCLOSURE | `social:validate` | LinkedIn の本文と Bluesky のスレッドに開示の1文がある | エラー |

- 告知は「冒頭15行以内に、媒体の書式で始まり、1文の中に『生成AI』と『確認』か『検証』を含むブロック」で判定します。
- 宣言は、見出しの名前、見出しのレベル、最後の見出しであること、4要素の語で判定します。
- さらに、宣言を git の共著記録（`Co-Authored-By`）と突き合わせます。生成AIのエージェントは、コミットには自分を共著者として記録しながら宣言には前任のツール名を残したり、検査の語に合わせて他のツールの用途を広げたりすることがあるためです（2026-09-13 の評価で gemini-3.7-flash に実際に起きました）。git の履歴が浅い（shallow）環境では、この突合を省きます。CI は全履歴を取得して検査します。
  - 原稿の本文を変えたコミットの共著者（生成AI）は、モデル名まで宣言に書きます。モデル名は共著者名の数字を含む語で、`Claude Opus 5 (1M context)` なら「Opus 5」、`Gemini CLI (gemini-3.7-flash)` なら「gemini-3.7-flash」です。開示の枠（冒頭の告知と末尾の宣言）だけを変えたコミットは数えません。
  - 開示の枠だけを変えたコミットの共著者を、本文の下書き・作成・改訂に使ったと書いてはいけません。
  - 宣言に書いたツールは、原稿を変更したコミットの共著記録にあることを求めます。作業ツリーがコミット済みのときだけ見ます。
  - 原稿の直前の版（コミット前は HEAD、コミット後は原稿を最後に変えたコミットの親）の宣言になかったツールを書き足したら、そのツールの文に用途と範囲（章・節の見出しか番号、題名、コードのパス）を書きます。「全体の改訂」「検証の修正」のような総称はエラーです。
  - 直前の版からあるツールの文を、そのツールが共著でないコミットで書き換えると警告します。自分の関与は別の文で書き足します。
  - SNS 原稿は、開示の1文と共著記録で同じ確認（本文を変えたコミットの共著者の名前）をします。

改訂したエージェントのコミットと宣言の文の例です。

```text
Co-Authored-By: Gemini CLI (gemini-3.7-flash) <noreply@google.com>
```

> Gemini CLI（Google の gemini-3.7-flash）で、2 章「技術選定理由」と 3.1 節のコードの抜粋を改訂しました。
- 媒体間の重複率（V2 / V2b / V7）を測る前に、告知と宣言を取り除きます。どの媒体にも同じ文言で入るため、複製と誤判定しないようにするためです。
- SNS の文数（BS_ONE_POINT）と段落の数え方（LI_PARAGRAPH / LI_STRUCTURE）も、開示の1文を除いて数えます。
- Qiita CLI が同期した過去記事（ファイル名が20桁の16進数）は、生成AIの普及以前の投稿を含むため対象外です。

Qiita・note・SNS の検査は公開前の門を兼ねます。Zenn は GitHub 連携が直接公開するため、検査は報告にとどまります。

告知が書く「筆者が内容を確認・修正した」を事実にするため、Qiita・note・SNS は公開の直前に人の確認の記録を確かめます。公開原稿の本文を変えた最新のコミット以降に、人の `Reviewed-by` トレーラーがなければ公開しません（H1、[linting.md](linting.md)）。作者は問いません。共著記録のない生成AIの改訂も、人が確認するまで公開しないためです。

### 3.1 例外

生成AIを使っていない原稿は、`lint/policies/disclosure.json` の `exempt.entries` にパス（glob）と理由を書きます。理由のない例外は置きません。

## 4. 限界

- 検査が見るのは「書いてあるか」「どこにあるか」と、宣言と共著記録の突合、書き足したツールの範囲の書き方です。共著記録を残さなかったツールや、書かれた用途と範囲が事実どおりかは、機械では判定できません。それを補うのが公開前の人の確認（H1）です。
- 共著記録（Co-Authored-By）を残さないツールで作った部分は、履歴から使ったツールを確かめられません。その場合は筆者が記憶と作業記録から補います。
- 公開済みの SNS 投稿は、原稿（YAML）を直しても投稿そのものは変わりません。2026-09-12 に配信した LinkedIn と Bluesky の投稿は、この規則を入れる前のもので、開示を含みません。
