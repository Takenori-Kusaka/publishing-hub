# 公開前のセルフレビュー ― 記録が無ければ公開しない

原稿(正本と派生物)は、公開のスイッチを立てる前に、**執筆したセッションとは別のセッション**に 2 つの読み方で読ませ、その結果を原稿の隣の記録(`<原稿>.review.yaml`)に残します。記録の欠落・古さ・引用の不在・止める指摘の未処理のどれかがあれば、`npm run check` と公開のワークフローを止めます(R1〜R8、`scripts/lint/check-review.mjs`)。

## 1. なぜ要るのか(起きたこと)

- 派生物 20 本が機械検査の 12 段階すべてに合格したあとで、査読が正本に無い主張を見つけた(Qiita「数十ミリ秒」、note「効きました」、SNS「費用は…だけ」)
- SNS 10 本は、事実の査読では止める指摘が 0 件だったのに、原稿だけを渡した読者役は 9 本で「何の製品の話か分からない」と答えた
- 本の改訂では、書き手 7 人全員が「エラー 0」と報告したあとで、査読が止める 29 件と直す 184 件を出した

機械検査は**形式**を見ます。内容が正本に支えられているか(事実)と、初見の読者に伝わるか(文脈)は、別の読み手が、正本と突き合わせるか、正本を知らない状態で読むかしないと出てきません。同じ方向を指す根拠が 3 系統あります。新聞社の校閲が「事実確認」と「素読み」を分業してきたこと。検査法の実証研究(Perspective-Based Reading)が、視点を分けた読者を混ぜると欠陥の発見範囲が広がると示していること。LLM 評価の研究が、自分の出力を自分で評価すると甘くなる(自己選好バイアス)と示していることです(根拠の一覧は kusaka-brand の `research/04-self-review-research.md`)。

執筆者の「0 エラー」が信用できないのは、執筆者が不誠実だからではなく、**同じ文脈で読む限り同じ見落としをする**からです。

## 2. 役割

| 役割 | 読むもの | 見つけられるもの | 見つけられないもの |
| --- | --- | --- | --- |
| 執筆者(writer) | 全部 | (レビューしない) | 自分の文章の欠陥 |
| 事実の査読(fact) | 原稿、正本、直前の版、規則 | 正本に無い主張、矛盾、引用の改変、呼び名の揺れ | 初見の読者に通じない語 |
| 読者役(cold) | **原稿の本文だけ**(`scripts/review/pack.mjs` が作る 1 ファイル) | 冒頭で主題が分かるか、通じない語、離脱点、結びの自然さ | 事実の正誤 |
| 取りまとめ役(著者) | 記録、原稿 | 採否の決定(規則に照らして) | (指摘は出さない) |

査読と読者役は原稿を**編集しません**。指摘だけを書きます。採否は取りまとめ役が規則に照らして決め、直すのは執筆者です。

## 3. 手順

1. 原稿を書き終え、`npm run check` を通す(機械検査は前提であって、合格ではない)
2. `node scripts/review/pack.mjs <原稿>` で、読者役に渡す 1 ファイル(`.tmp/review/<id>/cold.txt`)と、査読に渡すパス一覧(`brief.json`)を作る
3. **別のセッション**で事実の査読を起動する。指示書は `scripts/review/prompts/fact-review.md`。出力は記録の `premortem` と `fact_review`
4. **別のセッション**で読者役を起動する。指示書は `scripts/review/prompts/cold-read.md`。渡すのは `cold.txt` だけ。読者像を 1 つ与える(例: 「タイムラインで偶然見た技術者」「検索から来た実務 3〜5 年の技術者で、題の課題を解きたい」「プログラムは書かない管理職」)。出力は記録の `cold_read`
5. 取りまとめ役が**採否表**(`adoption`)を書く。列は「指摘 / 採否 / 根拠にした規則 / 直し方」。根拠にしてよいのは、媒体の役割と読者(`docs/publishing-model.md` §1)、編集の規則(`docs/social-editorial-guide.md`、AGENTS.md 2 章)、事実の捏造禁止、オーナーの決定。根拠にしてはいけないのは、読者役の感想、引用の無い指摘、検証できない主張
6. 執筆者が直す。直した後の原稿のハッシュ(`node scripts/lint/check-review.mjs --hash <原稿>`)を採否表の `fixed_in_sha256` に書く(赤字照合)
7. `summary` に判定(go / go-with-fixes / no-go)と上位のリスク、確認しなかった範囲を書く
8. 記録と原稿を**別のコミット**にする。公開のスイッチ(`published: true` / `private: false` / `status: ready`)はこの後に立てる
9. `npm run check` の `review` 段階が R1〜R8 を通すことを確かめ、PR を出す。オーナーは記録の `summary`、`not_checked`、採否表で「不採用」にした行だけを読めばよい

## 4. 検査(R1〜R8)

| 規則 | 内容 |
| --- | --- |
| R1 | 公開のスイッチが立った原稿に記録がある。この仕組み(2026-10-12)より前に公開した原稿は `lint/policies/review.json` の `grandfathered` に理由つきで載せ、本文を改訂したら記録が要る |
| R2 | 記録が新しい。`subject.sha256`(か採否表の `fixed_in_sha256`)が現在の原稿の正規化ハッシュと一致する。派生物は `canonical[].sha256` も一致する |
| R3 | 引用が実在する。主張・指摘・読者役の `quote` が原稿に、`source_quote` が正本に逐語である。無ければ捏造として止める(LLM が引用をでっち上げる失敗への唯一の機械的な防御) |
| R4 | 未支持(`unsupported` / `contradicts`)の主張と「止める」の指摘に採否表の行があり、「直す」「削る」は `fixed_in_sha256` が現在の原稿と一致する。「不採用」は理由を書く |
| R5 | 読者役の実質。`subject_identified` が `subject.terms` のどれかを含み、冒頭で主題が分かったと答えている。候補(分からなかった語・離脱点)が 1 件以上 |
| R6 | 独立性。査読・読者役のセッション ID が執筆者と異なる。読者役の `allowed_inputs` が `subject_body_only` だけ。記録を最後に変えたコミットが原稿本体を変えていない(未コミットなら注意) |
| R7 | 判定が `go` か `go-with-fixes`。`no-go` は失敗 |
| R8 | `not_checked` がある。主張の照合が 3 件以上 |

規則の値は `lint/policies/review.json`、記録の書式は `lint/review/review-record.schema.json`。

## 5. 偽装をどこまで防げるか

一人の所有者がすべての鍵を持つリポジトリで、偽装を完全に防ぐことはできません。できるのは「偽装するほうが正しくレビューするより手間がかかる」状態にすることです。

- 方針: 査読と読者役は原稿を編集しない。執筆者は `fact_review` と `cold_read` を書かない(AGENTS.md 2.3)
- 引用の実在検査(R3): 「それらしい記録」を一括生成しても、引用が原稿と正本に逐語で無ければ落ちる
- セッション ID と入力の宣言(R6): 読者役が正本を読んでいれば、読者役ではない
- コミットの分離(R6): 記録と原稿を同じコミットで変えると報告する
- 将来の強化: GitHub Artifact Attestations で、CI 上のレビュージョブが生成した記録に署名を付ける(公開リポジトリなら無料プランでも可)。2026-10-12 時点では未実装

## 6. 図のレビュー

図(キービジュアル・節図)は、読者役に `[画像: alt]` として渡ります。図だけを先に見て主題を答えさせ(`figure_only_subject`)、本文と図の用語が一致しているかは事実の査読が見ます。図の機械検査(S1〜S6: ソース・再現性・主ラベルの大きさ)は `docs/diagrams.md`。

## 7. 公開後

訂正が要ると分かったら、記事の末尾に訂正の注記を置き、`docs/corrections.yaml` に 1 行を足します(誤→正、原因、記録の `not_checked` に入っていたか、この訂正から足した規則)。訂正が検査規則に還流したかを追えるようにするためです。

## 8. 既存の手順との関係

`docs/records/editorial-review.md`(2026-09 の査読の記録)の手順を、記録ファイルと検査として機械化したものです。あちらは「起きたこと」の記録として残し、手順の正本はこの文書と `lint/policies/review.json` です。
