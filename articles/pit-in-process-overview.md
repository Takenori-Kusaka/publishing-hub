> マシンは人間より速い。それでも、決められた場所では必ず人間が触る。

ピットイン方式は、生成AIが実装を主導する前提で、人の判定を守るための開発プロセスです。正式名称は「AI協調型ソフトウェア開発プロセス標準」といいます。正本は [Process Compass](https://takenori-kusaka.github.io/process-compass/phase4-process-design/overview/) の標準本文です。この記事は、はじめて聞いた人が全体像をつかむための概要です。冒頭の一枚で全体像を、続く節で各部分を図と表で示します。

## 1. ピットイン方式とは

F1 のピット作業は、18〜20名が2秒以下で終えます。タイヤ1本に3名が付き、作業を最小単位まで分解して専任を置くことで、この速さが生まれます。レースそのものは止まりません。決められた場所でだけ、人の手が入ります。

AI が実装を主導する開発でも、この形は変わらないというのがピットイン方式の主張です。名前の由来となった対応は、次の3点です。

| F1 のピット作業 | ピットイン方式 |
| --- | --- |
| 作業の分解と持ち場の分離 | タスクの分割基準と、兼務の禁止 |
| レースそのものは止めない | AI の生成速度を落とさずに判定を通す構成 |
| 競技規則が安全のために意図的な遅延を定めている | ゲート(G-1〜G-8。判定の場) |

採らなかった候補(関所・クリアランス方式など)と、その理由は、標準本文の判断記録(ADR)に残しています。

## 2. なぜ必要になったのか

![生成が速くなると変更単位が増え、判定の回数が増え、判定者の帯域が飽和し、判定が印を押す操作へ縮退する連鎖の図。下に、帯域を守る3つの方法(機械化・判断の分業・判定の期限)](/images/pit-in-process/fig-bandwidth.png)

理想像は「AI が自律的に開発し、人間は意思決定だけを行う」と語ります。しかし現場で起きるのは逆の現象です。生成が速く自律的になるほど、**人間の検証帯域が最大の律速点**になります。検証帯域は、人が一定の時間に確かめられる量のことです。律速点は、全体の速さを決めてしまう箇所を指します。

エージェントは、人が読める速度を超えて変更を生成します。規模の大きな差分を1行ずつ確認する作業は、時間の制約のもとで、実質的に印を押す操作へ縮退します。

標準は、この帯域を3つの方法で守ります。

- 機械化できる検査は、すべて自動検証(CI)へ移す。合意済みのルールは人の目を通さない
- 人の判断を種類で分ける。価値判断、技術判断、理解の確認、記録の確認を別の人が担い、1人に集中させない
- 判定に期限を付ける

判断の質は、読んだ行数ではなく、確認した観点の数で決まります。

## 3. 全体像 — 二層構造

![二層構造の図。外殻は事業判断の節目で、事業ステージ(S0 探索・S1 価値確立・S2 スケール)の境界にステージ移行ゲート(SG)を置く。内側は AI 協調ループで、仕様承認・AI 実装・自動検証・独立レビューを機能単位で回す](/images/pit-in-process/fig-two-layer.png)

ピットイン方式は二層構造です。外側はゆっくり、内側は速く回ります。

| 層 | 内容 | 頻度 | 既存制度との関係 |
| --- | --- | --- | --- |
| 外殻 | 事業判断の節目。投資の継続、ステージ移行、出荷の可否 | 案件あたり数回 | 既存の稟議・決裁権限規程と、出荷判定の席・判定者・時点は変えない。出荷判定者の署名の意味と、リリース決裁での残存リスクの受容の記名は改める |
| 内側 | AI 協調ループ。仕様承認 → AI 実装 → 自動検証 → 独立レビュー | 機能あたり数時間〜数日 | 新たに規定する |

外殻は、事業ステージ(S0 探索・S1 価値確立・S2 スケール)で区切ります。ステージの境界にはステージ移行ゲート(SG-0〜SG-2)を置き、会議体が投資の継続を判定します。

二層に分ける理由は2つあります。事業判断の頻度を上げると決裁が滞留し、開発の反復の頻度を下げると AI の生成速度を活かせません。判断の性質が違うので、判定者・判定基準・期限を分けなければ、責任の所在が曖昧になります。

既存制度を変えないわけではありません。変更は4点あり、標準はこれを小さく見せないと明記しています(第11節)。

内側のループは、機能単位で4つの工程を反復します。

| 工程 | 主体 | 完了条件 |
| --- | --- | --- |
| 仕様承認 | 人 | 受入基準が検証可能な形式で確定している |
| AI 実装 | AI エージェント | 実装計画の全タスクが完了している |
| 自動検証 | 機械(CI) | 定めた機械判定の基準をすべて満たす |
| 独立レビュー | 人(作成を指示した者以外) | 仕様と実装の一致を確認し、挙動を記録した |

## 4. 8つの工程ゲート

![8つの工程ゲート G-1〜G-8 を縦に並べた図。G-4 機能仕様承認と G-5 自動検証を、省略できないゲートとして強調している](/images/pit-in-process/fig-gates.png)

1つの開発サイクルには、8つの工程ゲートを置きます。ゲートとは、定められた判定者が、定められた基準との突合により、次段階へ進めてよいかを判定する場です。判定者の列にある役割(席)は、第5節で説明します。

| ゲート | 判定するもの | 判定者 | 期限の目安 |
| --- | --- | --- | --- |
| G-1 企画承認 | 投資対効果、リスクの受容方針 | 事業決裁者 | 既存の稟議どおり |
| G-2 要件合意 | 受入基準が検証可能な形式か | 価値責任者 | 48時間 |
| G-3 技術設計判断 | 設計の可逆性、非機能、代替案 | 技術判断者 | 48時間 |
| G-4 機能仕様承認 | タスクの粒度と範囲 | 価値責任者 | 24時間 |
| **G-5 自動検証** | **8基準すべてを機械が判定** | 機械 | 即時 |
| G-6 独立レビュー | 作成を指示した者以外が挙動を確認 | 独立レビュア | 2営業日 |
| G-7 出荷判定 | 記録の完備 | 出荷判定者(QA) | 3営業日 |
| G-8 リリース決裁 | 事業リスクの受容 | 事業決裁者 | 48時間 |

**G-4 と G-5 は、どの事業ステージでも省略できません。** この2つを外すと、仕様の承認を経ない実装と、機械検証を経ない統合が発生します。それ以外のゲートは、チーム規模と事業ステージに応じて簡略化または省略します(第8節)。

G-5 だけは全部を機械が判定し、人の判断を挟みません。基準は次の8つです。

- 全テストの合格
- 静的解析と脆弱性の重大指摘が0件
- テストカバレッジ
- 曖昧語の検査(「適切に」「必要に応じて」など、受入基準に使えない語が残っていないか)
- 依存関係のライセンス
- 文脈ファイル(AI へ渡す前提を書いたファイル)の形式
- 秘匿情報の混入
- 依存関係の追加・更新の識別

このうち秘匿情報の混入だけは、「記録して後で対応」を認めません。混入した資格情報は履歴に残り、削除するコミットを重ねても消えないためです。是正は、その資格情報の無効化と再発行によります。

## 5. 席と責任 — AI は結果責任を持てない

![主な6つの席(事業決裁者・価値責任者・技術判断者・独立レビュア・出荷判定者・開発者)と、実行だけを担う AI の位置を示した図](/images/pit-in-process/fig-roles.png)

責任分担は RACI(責任分担表。R は実行、A は結果責任、C は相談、I は報告)で表します。生成AI時代に重要なのは、結果責任(A)と実行(R)の分離です。

- 各成果物の結果責任(A)は、記名の自然人1名だけが負う
- AI はどれだけ実行(R)しても、結果責任は必ず人間に紐づく
- AI の列に A は存在しない

判断の確定を人に固定する理由は、確定するのが結果責任(A)を負う者でなければ、責任の所在を失うためです。

ロールを、責任者(席の結果責任を負う記名の人)や担い手(席の作業を実際に行う人または AI)と対で述べるときは「席」と呼びます。席は責務と、判定者となるゲートの組であり、体制が変わっても変わりません。主な席は次の6つです。

| 席 | 責務 | 判定するゲート |
| --- | --- | --- |
| 事業決裁者 | 投資とリリースのリスクを受容する | G-1、G-8 |
| 価値責任者 | 何を作るかと受入基準に責任を持つ | G-2、G-4 |
| 技術判断者 | 設計の選択と代替案に責任を持つ | G-3 |
| 開発者 | 仕様を書き、AI の生成した差分を検証する | — |
| 独立レビュア | 作成を指示した者以外の目で挙動を確認する | G-6 |
| 出荷判定者 | 記録の完備を確認して出荷を判定する | G-7 |

## 6. 3つの原則

![3原則を並べた図。判定者は1人。作成者は承認しない。AI は結果責任を持てない](/images/pit-in-process/fig-principles.png)

標準の4つの設計原則と、第5節の責任の原則のうち、判定と責任に関わる3つです。残る設計原則は「技術と事業の分離」と「文脈は基盤に一度書く」です。

### 判定者は1人

工程ゲートでは、合議体を判定の場にしません。事前の非同期コメント期間を置き、意見はそこで集約します。判定は1人が単独で行います。責任を一意にし、判定を速くするためです。ステージ移行ゲートと、AI 自律レベルの引き上げは、会議体が判定します。

### 作成者は承認しない

同一成果物で、作成を指示した本人と独立レビュアを兼ねません。同一案件で、開発ラインと出荷判定者を兼ねません。出荷判定者は、開発ラインから独立していることが条件です。

この禁止は2つの層で強制します。1つ目はブランチ保護です。ただし、AI に作成させた変更を、指示した本人が承認する形はブランチ保護を通ります。リポジトリの上では、指示した者は作成者ではないためです。そこで2つ目の層として、出荷の証跡を集約する段階で、この承認を独立した確認に数えず差し戻します。

### AI は結果責任を持てない

第5節のとおりです。AI の担い手は、モデルの版・指示資産(AI へ渡す指示の集合)の版・権限の組で識別します。責任者は記名の自然人のままです。

## 7. AI にどこまで任せるか — 引き上げは判定、引き下げは自動

![AI 自律レベル L1〜L3 を階段として並べ、引き上げには判定が要り、引き下げは検知した時点で1段階ずつ自動に発火する非対称を示した図](/images/pit-in-process/fig-ratchet.png)

AI にどこまで任せるかを、番号だけでなく3つの変数で定義します。

| レベル | 監視者 | フォールバック | 適用範囲 |
| --- | --- | --- | --- |
| L1 主導実装 | 人がすべての変更を確認する | 人 | 1機能単位。開発環境 |
| L2 仕様駆動の並行実行 | 人が統合点を確認する | 人、および自己修正ループ(検査に落ちたとき AI が自分で直す反復) | 複数機能の並行実装。検証環境まで |
| L3 自己修復 | 機械が常時監視し、人が事後に確認する | 自動的な切り戻し | 事前に登録した変更種別に限定 |

引き上げには判定が要ります。連続運用期間、差し戻し率(独立レビューで差し戻された変更の割合)、変更失敗率などの条件をすべて満たしたときに申請し、判定を受けます。

引き下げは判定を待ちません。検知した時点で自動に発火します。

| 検知する状態 | 措置 |
| --- | --- |
| 自動承認の比率が急上昇した | 1段階引き下げる |
| AI が起因の重大事象が発生した | 1段階引き下げる |
| 差し戻し率が0%のまま推移した | 形骸化の疑いとして引き下げる |
| コア機能の理解保持者が1名になった | 該当機能を L1 へ引き下げる |

差し戻し率0%を「うまくいっている」と読まないのが要点です。

## 8. 規模に合わせる — テーラリング

標準は参照モデルであり、そのまま全組織に適用するものではありません。組織の条件に応じて、5つの軸で調整します。

| 軸 | 選択肢 | 何に効くか |
| --- | --- | --- |
| A. チーム規模 | 1〜2名 / 3〜9名 / 10名以上 | 兼務の許容、独立レビューの方式 |
| B. 事業ステージ | 探索 / 価値確立 / スケール | ゲートの厳格さ、負債の扱い |
| C. 期待品質・規制 | 標準 / 高 / 規制業 | 出荷判定の厳格さ、記録の粒度 |
| D. 開発形態 | 内製 / 受託(発注側) / 受託(受注側) | 契約ゲート(検収に対応づけるゲート)の位置、検収の扱い |
| E. 安全重要度 | CL0 〜 CL3(最悪の故障の帰結で決める。CL0 が最も軽い) | 安全に関する成果物の要否、自律レベルの上限 |

たとえば2名・探索段階・標準品質・内製・CL0 の PoC では、次の構成になります。

- G-4 と G-5 を残す
- G-6 は、作成を指示していない側の人が確認する(相互の確認で成立する)。2人とも作成の指示に関与した変更は外部へ依頼し、置けなければ「未達」として表示する(未達の意味は第9節)
- 他のゲートは、省略として宣言する
- CI の基準の厳格化は代償措置として記録する。ただし、独立レビューの代替には数えない

調整は宣言を伴います。標準から外した項目を、理由とともに残します。どの組み合わせでも外せない項目を、標準本文は9つ定めています。そのうち要点は次の6つです。

1. 結果責任を2人以上にしない
2. AI を結果責任にしない
3. 差し戻し基準のないゲートを作らない
4. 安全重要度が最上位の、安全機能を担う部分で、自律レベルを L1 より上げない
5. 安全重要度が高い場合に、リスクアセスメントと検証記録を省略しない
6. 標準から外した項目を、宣言せずに運用しない

## 9. 1人でも回るのか

1人と AI だけでは、独立レビュー(G-6)を埋められません。G-6 の判定基準のうち、「作成を指示した本人でない」の1項目が、1人では成立しないためです。

AI で埋めることもできません。標準は、独立を人の単位で定義します。同じモデルを使う限り、エージェントを分けても事前学習の知識という共通の原因が残ります。モデルの系統を変えても、独立の条件には数えません。

1名体制では、外部の確認者(他チーム・他部門)を置けば G-6 が成立します。置けなければ、省略ではなく「未達」として表示し続けます。

| 状態 | 意味 |
| --- | --- |
| 省略(omitted) | 規則により省略した。調整として成立している |
| 未達(unmet) | 目的を達成する構成を示せていない |

未達を「省略の宣言」で済ませない理由は、宣言が差分を追跡する手段であって、目的の達成の代わりにはならないためです。

## 10. 明日から何をするか

![テンプレートからリポジトリを作り、設問に答えて構成を決め、次の一手に従って回す3ステップの図](/images/pit-in-process/fig-start.png)

準拠テンプレートを用意しています。

https://github.com/Takenori-Kusaka/pit-in-template

1. GitHub の **Use this template** から新しいリポジトリを作る
2. Claude Code で開き、`/pit` を実行する。最初の一手は `/process-init` で、人数・段階・品質要求・開発形態・最悪の場合の帰結などの設問に答える
3. 以後も `/pit` が出す次の一手に従う

回答から、あなたの状況に合ったプロセス構成が生成されます。人の判断を要する段階では、AI は先へ進まず、待つ席を示して止まります。

## 11. よくある質問

**Q. 稟議やレビュー文化のある日本の会社では無理では?**
標準の調査は、独立した第三者レビューを制度化してきた日本の品質保証文化には、むしろ追い風になりうるとみています。稟議・決裁権限規程と、QA 部門が出荷判定を行う体制は変えません。

既存制度への変更は4点です。標準は、この変更を小さく見せないと明記しています。

1. 技術判断を決裁階層から分離し、単独の判定者へ移す
2. ゲートの判定を、合議から「単独判定と事前の非同期コメント」へ移す
3. 出荷判定者の署名の意味を定め、残存リスクの受容を事業決裁者の記名へ移す。出荷判定の規程の改定を要する
4. トップマネジメントが、品質保証の方針と受容の基準に記名する

**Q. ルールを作っても形骸化するのでは?**
標準は、形骸化が起きる箇所に次の手当てを置いています。

- 差分の確認は、数え上げられる範囲(受入基準の数、外部インターフェースの変更数など)を先に確かめる
- 遵守が必須の規則は、AI への指示ファイルではなく、実行環境の設定に置く。指示ファイルの遵守は保証されないため
- 自律レベルの引き下げを自動にする(第7節)

**Q. 名乗れば準拠になる?**
なりません。名称は内容を保証しません。適合の主張は、ゲート判定の記録とテーラリングの宣言によります。

## この標準の限界

- この標準の運用が欠陥の流出を減らしたという測定は、まだありません
- 特定の業界規格への適合を主張するものではありません
- 実証を欠く値と判断には、識別子と見直し期限を付けて公開しています。どこが確からしくて、どこが暫定なのかを読者が判断できる状態を保つためです
