話者分離（発話を話し手ごとに分ける処理）をローカルで動かしたとき、ライブラリの既定閾値のままだと **4人の会話が7人になりました**。閾値を上げていくと 0.9 で正解の4に一致します。それでも既定値には 0.8 を選びました。

この記事は、その判断と、話者区間を文字起こしのセグメントへ割り当てるロジックの実装です。**評価が足りていないことも含めて**書きます。

- 正本（Zenn Books『ローカル完結ボイスジャーナルの設計』）: [話者分離の閾値を測って決める章を読む](https://zenn.dev/takenori_kusaka/books/quickscribe-design/viewer/evaluation-driven-diarization)
- 実装（OSS）: [Takenori-Kusaka/QuickScribe](https://github.com/Takenori-Kusaka/QuickScribe)

## まず切り分ける：モデルが悪いのか、パラメータが悪いのか

使ったのは [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/) です。話者分離は、発話区間を切る segmentation モデルと、声の特徴を数値化する embedding モデル、そしてその特徴をまとめるクラスタリングの3段で動きます。精度が出ないとき、どこが原因かは切り分けないと分かりません。

4話者だと分かっている約57秒のテスト音声で、**話者数を教えて**推論させたところ、正確に4話者を検出しました。モデルとクラスタリングは働いています。つまり問題はパラメータ側です。この確認を飛ばすと、モデルの差し替えという重い作業に向かってしまいます。

## 閾値をスイープする

実運用では話者数は分かりません。話者数を未知にすると、クラスタリングは閾値で分割数を決めます。閾値を振った結果はこうでした。

| 閾値 | 検出話者数（正解は4） |
| --- | --- |
| 0.4 | 8 |
| 0.5（ライブラリ既定） | 7 |
| 0.7 | 5 |
| 0.9 | 4 |

ライブラリの既定 0.5 は、**4話者を7話者へ過分割**していました。既定値はそのライブラリの平均的な用途に合わせてあるので、自分の用途に合う保証はありません。

## 技術選定：数字が最良の 0.9 を選ばなかった理由

閾値の選択は、2種類の誤りのどちらを受け入れるかという問題です。

| 誤り | 何が起きるか | 読み手への害 |
|---|---|---|
| **過分割**（ひとりを複数に割る） | 実在しない話者が増える | 記録を読み返す人が、いない人の発言として読む。害が大きい |
| **過統合**（複数をひとりにまとめる） | 似た声が同じラベルになる | 「この2人が同じに見える」で済む。害は小さい |

正解に一致させたいなら 0.9 です。選んだのは 0.8 でした。理由は2つあります。

1つは上の表のとおり、**過分割の害のほうが大きい**ことです。実在しない話者が増える記録は、読み手を強く混乱させます。

もう1つは、0.9 が**この1本の音声にぴったり合いすぎている**ことです。テストサンプル1本に最良の値を出荷値にするのは、過適合そのものです。少し分割を抑える側に倒した 0.8 を既定にして、日本語での実測で見直す前提にしました。

設定はコードのコメントに判断を残しています。

```rust
// 出典: https://github.com/Takenori-Kusaka/QuickScribe/blob/f51e1104e7a82d56c22739bbab2f270bc10f297d/src-tauri/src/diarize.rs
        // 話者数は未知前提: num_clusters<=0 で閾値ベースの自動推定（単一話者は1へ収束）。
        // 閾値は 0.8（実検証で決定 / 2026-07-10）。sherpa 既定 0.5 は過分割で、4話者テスト音声で
        // 0.5→7・0.7→5・0.9→4話者と検出された。1人を複数話者に割る偽検出は用途上有害なため、
        // 分割を抑える高め(0.8)を既定にする。TODO(Phase2): 日本語実音声での最適閾値を実測で確定する
        // （ADR-0031 が留保。話者数既知なら num_clusters 固定＝4話者で正確一致を確認済み）。
        let config = DiarizeConfig {
            num_clusters: Some(-1),
            threshold: Some(0.8),
            ..Default::default()
        };
```

`num_clusters: Some(-1)` が「話者数は未知」の指定です。**マジックナンバーの隣に、なぜその値なのかとスイープの実測値を置いておく**と、後から見直すときに測り直しの出発点になります。

## 割当ロジック：重なりの合計で決め、同点は決定的に

話者分離の出力（話者ごとの発話区間）と、文字起こしの出力（セグメント）は、別々に出てきます。これを結ぶ必要があります。

採ったのは [WhisperX](https://arxiv.org/pdf/2303.00747) と同じ考え方で、**セグメントと各話者区間の重なりの長さを合計し、最大の話者に割り当てる**方法です。

```rust
// 出典: https://github.com/Takenori-Kusaka/QuickScribe/blob/f51e1104e7a82d56c22739bbab2f270bc10f297d/src-tauri/src/diarize.rs
/// whisper セグメント区間 `[seg_start_cs, seg_end_cs)` に最も重なる話者を返す（whisperX 方式）。
/// 各話者との重複長を合算し argmax。重なりが無ければ中点最近傍（fill-nearest）。
/// 話者区間が空なら None（＝ラベル無し）。同点は小さい話者IDを優先（決定的）。
pub fn assign_speaker(seg_start_cs: i64, seg_end_cs: i64, turns: &[SpeakerSegment]) -> Option<i32> {
    if turns.is_empty() {
        return None;
    }
    let mut overlap: HashMap<i32, i64> = HashMap::new();
    for t in turns {
        let ov = (seg_end_cs.min(t.end_cs) - seg_start_cs.max(t.start_cs)).max(0);
        if ov > 0 {
            *overlap.entry(t.speaker).or_insert(0) += ov;
        }
    }
    if !overlap.is_empty() {
        // 重複合計の最大。同点なら speaker id が小さい方（b.0 の降順比較で小 id を勝たせる）。
        return overlap
            .into_iter()
            .max_by(|a, b| a.1.cmp(&b.1).then(b.0.cmp(&a.0)))
            .map(|(spk, _)| spk);
    }
    // 重なり無し → セグメント中点に最も近い話者区間へ割当。
    let mid = (seg_start_cs + seg_end_cs) / 2;
    turns
```

コピペするなら、3つの細部に注目してください。

1つ目は `.max(0)` です。重なりの計算は「終端の小さい方 − 始点の大きい方」で、重なりが無いと負になります。ここを落とすと、**離れた区間が負の寄与として合計に混ざります**。

2つ目は `.then(b.0.cmp(&a.0))` です。`HashMap` の反復順は実行ごとに変わるので、重なりが同点のときに勝つ話者が揺れます。同点は話者IDの小さい方を勝たせて、**同じ入力なら同じラベルが付く**ようにしています。話者分離の結果が実行ごとに変わると、利用者は原因を追えません。

3つ目は、重なりが1つも無いときのフォールバックです。`None` を返してラベル無しにするのではなく、セグメントの中点に最も近い話者区間へ割り当てます。発話区間の境界と文字起こしのセグメント境界は一致しないので、**わずかにずれた短いセグメントがラベルを失う**のを防ぎます。

なお、この関数と話者ラベルの整形は Cargo のフィーチャーに関係なく常にビルドされ、テストされます。実推論だけがフィーチャーの裏にあります。

```rust
// 出典: https://github.com/Takenori-Kusaka/QuickScribe/blob/f51e1104e7a82d56c22739bbab2f270bc10f297d/src-tauri/src/diarize.rs
// 話者特定（Speaker Diarization / S2.5・ADR-0031）。
// 純ロジック（話者区間→whisperセグメントへの割当・話者ラベル整形）は feature 非依存で常にビルド・
// テストされる。実推論の `SherpaDiarizer` は `diarization` feature 配下（sherpa-onnx / ONNX ランタイム）。
// 配布はオンデマンド: ネイティブDLL・ONNXモデルは有効時のみ初回DL（ADR-0012 単一バイナリを維持）。
```

**割当ロジックを純ロジックとして分離しておくと、ONNX ランタイムを用意できない環境でもテストが回ります。** 重なりの計算や同点処理のような、間違えやすくて壊れても気づきにくい部分ほど、依存の外に出しておく価値があります。

## 測れていないこと

ここは取り繕わずに書きます。

**話者誤り率のような指標を継続測定する仕組みは、ありません。** DER（Diarization Error Rate）を計算するコードも、区間単位の正解データ（RTTM など）も、リポジトリに置いていません。上のスイープは、閾値ごとの検出話者数を手で並べた1回きりの記録です。

正解として使ったのも、ライブラリ公式のデモ音声1本です。**しかも中国語の音声で、想定している用途は日本語です。** 4話者と分かっているのはファイル名とメタ情報からで、誰がいつ話したかの区間ごとの正解はありません。だから「検出話者数が合ったか」しか言えず、「割り当てが正しかったか」は測っていません。

文字起こしのほうは、CER をマイクロ平均とブートストラップ信頼区間で測る仕組みを作りました。話者分離をそこへ接続していないのが現状です。0.8 という既定値は、**1本の非日本語サンプルで決めた暫定値**として、そのまま残っています。
