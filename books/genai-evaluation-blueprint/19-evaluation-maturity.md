### 序論：本章が扱う範囲

本章は、評価を組織で回す仕組みの段階を、V0からV4の5段階として定義します。[期待値への距離の章](16-distance-to-expectation)の10層が「何を測るか」を定めるのに対し、本章の段階は「測る仕組みがどこまで回っているか」を定めます。

5段階は著者による分類です。ただし、段階の考え方には先行する整理があります。実務家のHamel Husainは2024年に、評価をアサーションによる単体テスト、人手とモデルによる評価、A/Bテストの3層に分け、費用はこの順に高くなると書きました [ [ 345 ] ](https://hamel.dev/blog/posts/evals/) 。日本のPharmaXは、評価を機能の出力、ユーザーの反応、KPIの3つのレベルに分け、オフライン評価で測れるのは最初のレベルだけだと述べました [ [ 429 ] ](https://zenn.dev/pharmax/articles/df59290ba875ff) 。本書の5段階は、これらに目視の段階と、評価が仕様を駆動する段階を加えたものです。

各段階には、必要な人材、道具、根拠のある費用の目安、よくある失敗を書きます。費用は一次資料に数値があるものだけを書き、無いものは無いと書きます。導入フェーズS1からS6との対応は[導入フェーズと評価の章](20-adoption-stage-and-evaluation)で扱います。

### 1. 5段階の定義

| 段階 | 名前 | 定義 | 典型の道具 |
| --- | --- | --- | --- |
| V0 | 目視 | 作った人が数件を見て判断する | チャット画面 |
| V1 | 固定セット | ゴールデンセットと人手の採点で判断する | 表計算、promptfoo |
| V2 | 自動評価 | 指標と審判モデルで、変更のたびに回帰を検査する | RAGAS、DeepEval、CI |
| V3 | 本番評価 | 本番の記録を採取し、抽出・人手の確認・監視で評価する | LangSmith、Phoenix、Langfuse、クラウドの標準機能 |
| V4 | 評価駆動 | 評価が仕様と改善を駆動し、監査に耐える | 評価の台帳、適合性評価 |

段階を分ける軸は、判断の根拠が個人の印象から、記録された数値へ移る度合いです。V0とV1は人の判断に頼ります。V2で機械の判断が加わり、V3で本番の利用者が評価の対象になります。V4では、評価の記録そのものが組織の約束になります。

### 2. V0目視：数件を見て判断する

V0は、作った人がチャット画面で数件を試し、良さそうなら次に進む段階です。英語圏の実務家は、これを「vibe checks」と呼びます。Hamel Husainは、製品が機能しているかを知るには目視の確認を超える測り方が要ると書きました [ [ 345 ] ](https://hamel.dev/blog/posts/evals/) 。

V0の限界は、道具の提供事業者も認めています。LangChainは2023年にLangSmithを発表した際、「30%程度動けばTwitterのデモには十分」だが本番には足りないと述べました [ [ 374 ] ](https://www.langchain.com/blog/announcing-langsmith) 。

V0には、もう1つの性質があります。Shankarらは、利用者が出力を採点しながら評価の基準を定めていく「criteria drift」を報告しました [ [ 346 ] ](https://arxiv.org/abs/2404.12272) 。V0の目視は、無駄な作業ではありません。何を測るべきかを見つける段階です。失敗は、目視のまま本番へ出すことです。

### 3. V1固定セット：ゴールデンセットで判断する

V1は、入力と期待する出力の組を固定し、変更のたびに同じセットで採点する段階です。

規模の目安には、公表された推奨があります。Anthropicは、エージェントの評価について、実際の失敗をもとにした20〜50の単純な課題で始めればよいと述べています [ [ 406 ] ](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 。Hamel HusainとShreya Shankarは、多様な100件の記録で始めて最初の30件は自分で注釈すること、注釈は合否の二値で始めることを勧めています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。

V1で要る人材は、ドメイン専門家です。同じ2人は、注釈者として単一のドメイン専門家を立てる方法が最も効果的だと書いています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。a16zが企業のCIO100名に聞いた2025年の調査では、社内の基準、ゴールデンデータセット、開発者の意見が依然として性能評価の中心でした [ [ 409 ] ](https://a16z.com/ai-enterprise-2025/) 。この調査は投資家によるものです。

人手の採点の費用は、次の公開値があります。

| 項目 | 値 | 時点 |
| --- | --- | --- |
| Amazon Bedrockの人手評価 | 完了した人手タスク1件あたり0.21ドル [ [ 395 ] ](https://aws.amazon.com/bedrock/pricing/) | 2026年10月 |
| Prolificの参加者への最低報酬 | 時給8.00ドル、企業の手数料42.8% [ [ 407 ] ](https://www.prolific.com/pricing) | 2026年10月 |
| FActScoreの人手評価の見積もり | 6,500件の生成で2.6万ドル [ [ 39 ] ](https://arxiv.org/abs/2305.14251) | 2023年 |

Amazon Mechanical Turkは2026年9月30日に閉鎖されました [ [ 408 ] ](https://www.mturk.com/pricing) 。クラウドソーシングで人手評価を安く集める選択肢は、狭まっています。

V1のよくある失敗は、セットを作って更新しないことです。本番で見つかった失敗をセットに足さなければ、セットは古い期待を測り続けます。

### 4. V2自動評価：変更のたびに回帰を検査する

V2は、指標と審判モデルで採点を自動化し、プロンプトやモデルを変えるたびに回帰を検査する段階です。

V2の中心は、継続的インテグレーション(CI)への組み込みです。promptfooのGitHub Actionは、プロンプトを変えるプルリクエストのたびに変更前後を比較します [ [ 414 ] ](https://www.promptfoo.dev/docs/integrations/github-action/) 。DeepEvalは、しきい値を下回る指標でビルドを失敗させます [ [ 415 ] ](https://deepeval.com/docs/evaluation-unit-testing-in-ci-cd) 。Braintrustは、プルリクエストでは一部の件数だけを走らせ、全件はマージのときに回す運用を文書にしています [ [ 416 ] ](https://www.braintrust.dev/docs/evaluate/run-in-ci) 。これは費用と速度の釣り合いを取る設計です。

審判モデルは安くて速い一方、それ自体を評価する必要があります。MT-Benchの論文は、GPT-4の審判と人の嗜好の一致が80%超で、人同士と同程度だと報告しました。同時に、位置・冗長さ・自己強化の偏りも示しています [ [ 89 ] ](https://arxiv.org/abs/2306.05685) 。ThoughtworksのTechnology Radarは、審判モデルの手法を2024年10月に「Trial」としましたが、2025年11月に「Assess」へ下げ、かつて信じられていたほど成熟していないと評しました [ [ 358 ] ](https://www.thoughtworks.com/radar/techniques/llm-as-a-judge) 。

自動化の費用は、人手より桁が小さくなります。DeepMindのSAFEは人手の20分の1以下の費用でした [ [ 40 ] ](https://arxiv.org/abs/2403.18802) 。Amazon Bedrockでは、アルゴリズムによる自動の採点は追加料金なしで、審判モデルは使ったトークンの料金がかかります [ [ 395 ] ](https://aws.amazon.com/bedrock/pricing/) 。

V2のよくある失敗は、審判モデルの採点を人の判断と照合しないことです。OpenAIの評価の手引きは、人のフィードバックで自動採点を較正し、一致を保つことを原則に挙げています [ [ 119 ] ](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 。

### 5. V3本番評価：本番の記録で評価する

V3は、本番の記録(トレース)を採取し、その一部を抽出して自動と人手で評価し、品質を監視する段階です。

本番の評価は、費用のため抽出して行います。LangSmithのオンライン評価は、抽出率を設定して対象を絞ります。0.1なら対象の記録の10%を採点します [ [ 402 ] ](https://docs.langchain.com/langsmith/online-evaluations) 。MicrosoftのFoundryは、本番後の評価として、抽出した本番トラフィックの継続評価、定期のレッドチーミング、品質がしきい値を下回ったときの警報を挙げています [ [ 133 ] ](https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/evaluation-approach-gen-ai) 。人手の確認には、注釈の作業列が使われます。LangSmithの注釈キューでは、確認した記録をそのままデータセットに加えられます [ [ 405 ] ](https://docs.langchain.com/langsmith/annotation-queues) 。

V3の普及の程度は、評価の道具の提供事業者による調査で分かります。LangChainが2025年11月から12月に1,340件の回答を集めた調査は、次の割合を報告しました [ [ 423 ] ](https://www.langchain.com/state-of-agent-engineering) 。

| 実践 | 回答の割合 |
| --- | --- |
| テストセットでのオフライン評価 | 52.4% |
| オンライン評価 | 37.3% |
| 審判モデル | 53.3% |
| 人手の確認 | 59.8% |

観測の規格は、まだ固まっていません。OpenTelemetryの生成AIの意味規約は2024年5月に導入されましたが、2026年10月の時点でも状態は「Development」です [ [ 401 ] ](https://github.com/open-telemetry/semantic-conventions-genai) 。

V3のよくある失敗は、A/Bテストの信号だけを信じることです。OpenAIは2025年のGPT-4oの迎合の件で、小規模なA/Bテストでは問題が出なかったと説明しました [ [ 303 ] ](https://openai.com/index/expanding-on-sycophancy/) 。本番の利用者の反応は、迎合のように利用者が喜ぶ失敗を捉えにくい信号です。

### 6. V4評価駆動：評価が仕様を駆動する

V4は、評価の基準が製品の仕様として先に決まり、改善と監査がその記録に基づいて行われる段階です。Eugene Yanは2023年に、評価から作り始める実践を「Eval Driven Development」と呼びました [ [ 343 ] ](https://eugeneyan.com/writing/llm-patterns/) 。

V4の要件は、規制と規格が具体的に書き始めています。EU AI Actの第9条(8)は、高リスクのAIの試験を、事前に定義した指標と確率的なしきい値に対して行うよう求めます [ [ 547 ] ](https://artificialintelligenceact.eu/article/9/) 。第72条は、性能のデータを能動的・体系的に集めて分析する市販後の監視を求めます [ [ 552 ] ](https://artificialintelligenceact.eu/article/72/) 。ISO/IEC 42001は出力の精度の指標そのものは定めず、監視・測定・分析・評価や内部監査という評価の仕組みを要求します [ [ 519 ] ](https://webdesk.jsa.or.jp/preview/pre_jis_q_42001_000_000_2025_j_ed10_ch.pdf) 。

評価の数値を外に示すなら、定義と分母も示す必要があります。テキサス州の司法長官は2024年、医療の要約を提供する企業が「重大な幻覚率が10万件に1件未満」と広告した件で、指標の定義と算出方法の明示などを義務づける和解をしました。同社は違反を否認しています [ [ 490 ] ](https://www.texasattorneygeneral.gov/news/releases/attorney-general-ken-paxton-reaches-settlement-first-its-kind-healthcare-generative-ai-investigation) 。

評価の台帳は、道具から独立させておくのが安全です。OpenAIは2026年6月にEvalsのプラットフォームの廃止を告知し、2026年11月30日に停止する予定です [ [ 127 ] ](https://developers.openai.com/api/docs/guides/evals) 。評価のデータと基準を特定の道具の中だけに置くと、道具の撤退とともに失います。

### 7. 段階を上がる条件

各段階で要るものを1表にまとめます。この表は著者による整理で、費用の欄は前節までの公開値だけを示します。

| 段階 | 人材 | 費用の根拠 | よくある失敗 |
| --- | --- | --- | --- |
| V0 | 作った人 | 追加の費用なし | 目視のまま本番へ出す |
| V1 | ドメイン専門家1人 | 人手タスク1件0.21ドル、最低時給8ドル | セットを更新しない |
| V2 | 評価を設計する技術者 | 審判モデルのトークン、自動の採点は無料の例あり | 審判を人と照合しない |
| V3 | 運用の担当、注釈者 | 抽出率で費用を制御する | A/Bの信号だけを信じる |
| V4 | 評価の責任者、監査役 | 公開の一次資料に総額の目安なし | 道具の中にしか記録がない |

開発の工数の比率は、実務家の自己申告が1つあります。Hamel HusainとShreya Shankarは、開発時間の60%から80%をエラーの分析と評価に使っていると書いています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。これは2人の経験の値で、業界の統計ではありません。

### 🗺️ 図：評価の成熟度は判断の根拠が記録へ移る階段

#### 図の読み方

この図は、左下から右上へ5つの段を積んだ階段です。各段に段階の記号と名前を置いています。V0は目視、V1は固定セット、V2は自動評価、V3は本番評価、V4は評価駆動です。

色は判断の主体を表します。丹のV0とV1は、人が判定する段です。藍のV2とV3は、機械の評価が加わる段です。千歳緑のV4は到達点です。読み順は左下から右上です。図の下の一文「判断の根拠が、印象から記録へ移る」が本章の主張です。

### 本章の位置づけ

本章の5段階は、著者による分類です。先行するHamel HusainやPharmaXの整理を土台にし、目視と評価駆動の2つの段階を加えました。各段階の道具と費用の数値は、出典に示した時点の公開値です。

著者は、5段階を順に登る必要はないと考えます。ただし、V2の自動評価をV1のゴールデンセットなしに始めることは勧めません。審判モデルの採点を照合する相手がいないからです。同じ理由で、V3の本番評価もV2の回帰検査を前提にします。段階を飛ばすときは、飛ばした段階の役割を誰が担うかを決めておく必要があります。
