### 序論：本章が扱う範囲

本章は、検索拡張生成(RAG)の評価が2023年から2025年にかけて、どのように1つの分野として成立したかを記述します。RAGは、利用者の入力だけでは足りない情報を検索で集め、その情報を根拠に回答を生成する仕組みです。評価の対象は、集めた情報の良し悪し(入力側)と、集めた情報から作った回答の良し悪し(生成側)の2つに分かれます。

検索の評価そのものは1960年代のCranfield実験とTRECに遡ります。その系譜は[人が測っていた時代の章](01-human-judgement-era)で扱いました。本章は、検索と生成を一続きの仕組みとして測る試みに限ります。審判モデル(LLM-as-a-judge)の成立とバイアスは[審判としてのLLMの章](05-llm-as-judge)で扱い、本章では採点の道具として使われた範囲だけを記します。

記述の順序は次のとおりです。最初にRAGという語と定義の揺れを確かめます。次に、評価の枠組みが4つの指標の骨格に収斂した経緯を記します。続いて、文脈が「十分か」という新しい問い・失敗の7類型・長文脈との比較・第三者による商用製品の実測を順に扱います。最後に、主要クラウドの評価機能と日本語の評価データを記します。

### 1. RAGという語と、定義の揺れ

「Retrieval-Augmented Generation」という名称は、Facebook AI ResearchのLewisらが2020年5月22日に投稿した論文で与えられました。論文は、事前学習した生成モデルをパラメトリックな記憶とし、Wikipediaの密ベクトル索引を非パラメトリックな記憶として組み合わせると、生成文がより具体的で事実に即すと報告しています [ [ 158 ] ](https://arxiv.org/abs/2005.11401) 。

事業者による定義は一致していません。AWSは、回答の前に学習データ外の信頼できる知識ベースを参照するよう「LLMの出力を最適化する過程」と定義します [ [ 160 ] ](https://aws.amazon.com/what-is/retrieval-augmented-generation/) 。2023年12月18日のGaoらのサーベイは、RAGの発展をNaive・Advanced・Modularの3段階に整理し、評価の枠組みとベンチマークも併せて示しました [ [ 161 ] ](https://arxiv.org/abs/2312.10997) 。定義が過程なのか枠組みなのかで、何を評価の単位にするかも変わります。

### 2. 指標の骨格：4つへの収斂(2023〜2024)

RAG専用の評価枠組みは、2023年の秋に相次いで公開されました。

- **RAGAS(2023年9月26日)**: 参照回答なし(reference-free)でRAGのパイプラインを評価する枠組みとして登場しました [ [ 41 ] ](https://arxiv.org/abs/2309.15217) 。
- **TruLensのRAG Triad(2023年)**: 文脈の関連性、根拠への接地(groundedness)、回答の関連性の3つの評価で構成されます [ [ 168 ] ](https://www.trulens.org/getting_started/core_concepts/rag_triad/) 。
- **ARES(2023年11月16日)**: 合成データで軽量な判定器を要素ごとに微調整し、予測駆動推論で数百件の人手ラベルから信頼区間つきの評価を出します [ [ 42 ] ](https://arxiv.org/abs/2311.09476) 。

指標の定義は公式ドキュメントで確かめられます。RAGASの忠実性(faithfulness)は、回答に含まれる主張のうち、取得した文脈で支持される主張の割合です。値は0から1をとり、すべての主張が文脈で支持される回答を忠実とみなします [ [ 166 ] ](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) 。Context Precisionは適合する断片を上位に並べる検索器の能力を測り、Context Recallは必要な情報をどれだけ取得できたかを測ります [ [ 167 ] ](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/) 。

これらの枠組みは名前こそ違いますが、骨格は共通しています。入力側では「集めた文脈は関係があるか」と「必要な情報を取りこぼしていないか」の2つを問います。生成側では「回答は文脈に忠実か」と「回答は質問に答えているか」の2つを問います。

評価用の質問を作る作業も自動化されました。Ragasは、知識グラフとシナリオに基づき、単一の文書で答えられる質問と、2つ以上の情報源を要する質問を生成します [ [ 182 ] ](https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/) 。一方で、専門領域で検証した2024年7月15日の研究は、RAGASが数値の導出過程を見せないことを問題にし、中間の出力を露出する改変版を作って専門家の判断と照合しました [ [ 183 ] ](https://arxiv.org/abs/2407.12873) 。2024年6月25日のRAGBenchは、産業5領域の10万件のデータを公開し、LLMによる評価が微調整した小型モデルに劣ると報告しています [ [ 171 ] ](https://arxiv.org/abs/2407.11005) 。

### 3. 文脈は「十分」か：入力側と生成側を切り分ける問い

指標が整うと、失敗が検索の側にあるのか、生成の側にあるのかを分ける問いが立てられました。

2023年9月4日のRGBは、RAGに必要な能力を、雑音への頑健さ・答えがないときに断る力・複数の情報の統合・誤った文脈への頑健さの4つに分けて測りました [ [ 169 ] ](https://arxiv.org/abs/2309.01431) 。2024年6月7日のMetaのCRAG(Comprehensive RAG Benchmark)は4,409問で評価し、先端のLLM単体の正答率は34%以下でした。素朴にRAGを足しても44%にとどまり、業界の最先端のRAGでも幻覚(ハルシネーション)なしに答えられたのは63%でした [ [ 175 ] ](https://arxiv.org/abs/2406.04744) 。

Googleの「Sufficient Context」(2024年11月9日)は、文脈が回答に足りるかを判定する自動の分類器を作りました。大型モデルは文脈が十分なら正答する一方、不十分なときに棄権せず誤答しがちでした [ [ 172 ] ](https://arxiv.org/abs/2411.06037) 。同社の2025年5月14日の解説によれば、Gemmaの誤答率は文脈なしで10.2%でしたが、不十分な文脈を与えると66.1%に上がりました [ [ 173 ] ](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/) 。情報を足せば正しくなるとは限らないことを、数値で示した実測です。

検索の質を下流の成否で測る試みも現れました。2024年4月21日のeRAGは、取得した文書を1件ずつLLMに渡し、下流の課題の正解で採点して文書の適合ラベルとします。この方法は、従来の方法より全体の性能との相関が高いと報告されました [ [ 177 ] ](https://arxiv.org/abs/2404.13781) 。2024年8月15日のRAGCheckerは、検索と生成の双方に細粒度の診断指標を与え、8つのRAGシステムを比較しました [ [ 176 ] ](https://arxiv.org/abs/2408.08067) 。

### 4. 失敗の7類型(2024年1月)

Deakin大学のBarnettらは2024年1月11日、研究・教育・生物医学の3つの事例から、RAGを作るときの7つの失敗点を整理しました [ [ 198 ] ](https://arxiv.org/abs/2401.05856) 。論文本文の定義を、本書の2層に対応させると次のとおりです。

| 番号 | 失敗点 | 論文の定義(要約) | 層 |
| --- | --- | --- | --- |
| FP1 | 内容が無い | 手元の文書では答えられない質問をした | 入力側 |
| FP2 | 上位に入らない | 答えは文書にあるが、返すほど上位に並ばなかった | 入力側 |
| FP3 | 文脈に入らない | 取得はできたが、回答を作る文脈に入らなかった | 入力側 |
| FP4 | 抽出できない | 答えは文脈にあるが、モデルが取り出せなかった | 生成側 |
| FP5 | 形式が違う | 表や一覧を求める指示をモデルが無視した | 生成側 |
| FP6 | 具体性が合わない | 答えは含まれるが、具体的すぎるか曖昧すぎる | 生成側 |
| FP7 | 不完全 | 誤りではないが、文脈にあった情報の一部が欠けた | 生成側 |

この論文は結論として2点を挙げました。RAGの検証は運用中にしかできないこと、そして頑健さは最初に設計で作り込むものではなく運用の中で育つものだということです [ [ 198 ] ](https://arxiv.org/abs/2401.05856) 。

### 5. 長文脈との比較：公称の長さと実効の長さ

入力できる文脈が長くなると、検索をせずに文書を丸ごと渡す方法との比較が評価の主題になりました。

- 2023年7月6日の「Lost in the Middle」は、関連情報が入力の中ほどにあると性能が大きく落ち、先頭や末尾にあると高いことを示しました [ [ 185 ] ](https://arxiv.org/abs/2307.03172) 。
- 2024年4月9日のRULERでは、評価した全モデルが32Kトークン以上を公称する一方、32Kで満足な性能を保てたのは半数でした [ [ 188 ] ](https://arxiv.org/abs/2404.06654) 。
- 2025年2月7日のNoLiMaは、針と質問の語の重なりを除くと、128K以上を公称する13モデルのうち11モデルが、32Kで短い文脈のときの半分以下に落ちると報告しました [ [ 189 ] ](https://arxiv.org/abs/2502.05167) 。
- 2024年10月3日のHELMETは、59のモデルを評価し、針探しのような合成課題は下流の性能を予測しないと結論しました [ [ 190 ] ](https://arxiv.org/abs/2410.02694) 。

事業者も自社の条件で実測を公表しました。Databricksは2024年8月12日、取得する文書を増やすと平均の再現率は2Kトークンの0.468から128Kの0.95へ上がる一方、64K超で精度を保てるのは最新の少数のモデルだけだと報告しました [ [ 194 ] ](https://www.databricks.com/blog/long-context-rag-performance-llms) 。Chromaの2025年7月14日の報告は、18のモデルで入力が長くなるほど性能が不安定に劣化することを示しました [ [ 195 ] ](https://www.trychroma.com/research/context-rot) 。Anthropicは2024年9月19日、断片に説明の文脈を付けて索引する方法で、上位20件の取得の失敗率が5.7%から再ランキング併用で1.9%に下がったと公表しました [ [ 197 ] ](https://www.anthropic.com/news/contextual-retrieval) 。これらは各社が自社の手法や製品に関わる条件で測った値です。

### 6. 引用の正しさと、第三者による商用製品の実測

回答に出典を付ける製品が広がると、「出典があること」と「出典が主張を支えること」を分けて測る評価が整いました。2023年5月24日のALCEは引用の再現率と適合率を自動で評価し、最良のモデルでも半分の場合で引用の裏付けが不完全だと報告しました [ [ 224 ] ](https://arxiv.org/abs/2305.14627) 。

同じ種類の第三者の実測が、2023年から2025年にかけて繰り返されています。

| 時期 | 実施者 | 対象 | 主な結果 |
| --- | --- | --- | --- |
| 2023年4月 | Stanford(Liuら) | 生成型検索4製品 | 生成文の51.5%しか引用で完全に支持されない [ [ 226 ] ](https://arxiv.org/abs/2304.09848) |
| 2024年11月 | Tow Center | ChatGPT search | 200件の出所の特定で153回が部分的か全面的に誤り [ [ 228 ] ](https://www.cjr.org/tow_center/how-chatgpt-misrepresents-publisher-content.php) |
| 2025年3月 | Tow Center | 8製品・1,600クエリ | 全体で60%超が誤答 [ [ 229 ] ](https://www.cjr.org/tow_center/we-compared-eight-ai-search-engines-theyre-all-bad-at-citing-news.php) |
| 2025年10月 | EBUとBBC | 4製品・22の公共放送 | 45%の回答に重大な問題、最大の原因は出所(31%) [ [ 232 ] ](https://www.ebu.ch/files/live/sites/ebu/files/Publications/MIS/open/EBU-MIS-BBC_News_Integrity_in_AI_Assistants_Report_2025.pdf) |

EBUとBBCの報告は、BBC同士の比較で重大な問題の割合が51%から37%に下がったとも記しています [ [ 232 ] ](https://www.ebu.ch/files/live/sites/ebu/files/Publications/MIS/open/EBU-MIS-BBC_News_Integrity_in_AI_Assistants_Report_2025.pdf) 。同じ方法の測定を繰り返したことで、改善の傾きが初めて見えるようになりました。

### 7. 商用の評価機能への収斂と、日本語の評価データ

主要クラウドは2025年に、RAGの評価を標準の機能として提供しました。AWSはAmazon BedrockのRAG評価を2025年3月20日に一般提供とし、検索だけの評価(文脈の関連性・網羅)と、検索から生成までの評価(正しさ・完全さ・忠実性)を選べるようにしました。同時に、引用の適合率と網羅の指標も加えています [ [ 241 ] ](https://aws.amazon.com/about-aws/whats-new/2025/03/amazon-bedrock-rag-evaluation-generally-available) 。Microsoft Foundryの評価器は、根拠への接地を「適合率」の側面、回答の完全さを「再現率」の側面と位置づけます [ [ 242 ] ](https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/evaluation-evaluators/rag-evaluators) 。Google CloudのVertex AIは、回答のすべてが文脈に帰属するかを0か1で採点するテンプレートを提供します [ [ 243 ] ](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/metrics-templates) 。いずれも、第2節で述べた4つの骨格と同じ構造です。

日本語では、2024年、評価データが個人と企業からほぼ同時に出ました。JQaRAは、LLMが正しく答えられる検索結果へ正解ラベルを付けた日本語のRAG検索評価データで、1問あたり100件の候補を持ちます [ [ 234 ] ](https://github.com/hotchpotch/JQaRA) 。SB IntuitionsのJMTEBは日本語の埋め込みの標準ベンチマークで、v2.0は5種類の課題と28のデータセットからなります [ [ 236 ] ](https://github.com/sbintuitions/JMTEB) 。2026年、学習データに含まれない架空の実体と出来事の合成文書を検索の対象とする日本語のRAGベンチマークが、LREC 2026で発表されました [ [ 239 ] ](https://lrec.elra.info/lrec2026-main-589) 。

#### 図の読み方

この図は、Barnettらの7つの失敗点を、左の入力側と右の生成側の2列に分けて並べたものです。左の列にはFP1・FP2・FP3を、右の列にはFP4〜FP7を、上から順に置いています。各類型の定義は第4節の表にあります。

読み順は左の列の上から下へ進み、右の列へ移ります。左の列の失敗は、回答を作る前の段階で情報が揃わなかったことを表します。右の列の失敗は、必要な情報が文脈に入った後で回答が期待からずれたことを表します。図の下の添え書きにあるとおり、2つの列を分けて測る問いが、第3節の「文脈は十分か」です。

### 本章の要点と解釈

本節は、著者による解釈です。前節までの事実記述とは区別して読んでください。

要点は3つです。第一に、RAGの評価は2023年秋の約2か月で枠組みが出揃い、指標は入力側の2つ(関連性と網羅)と生成側の2つ(忠実性と回答の関連性)に収斂しました。2025年には主要クラウドが同じ骨格を標準機能にしています。第二に、「文脈は十分か」という問いと7つの失敗点は、失敗の原因が検索にあるのか生成にあるのかを切り分けるための道具になりました。不十分な文脈が誤答率を上げるという実測は、入力側を測らずに生成側だけを測ることの危うさを示しています。第三に、商用製品の出典の正しさは、同じ方法の第三者の実測が繰り返されたことで初めて改善の度合いが見えました。

著者は、実務家への含意を「RAGの評価は、指標を選ぶ前に、失敗をどちらの層に帰属させるかを決める作業だ」と考えます。忠実性の数値が高くても、必要な文書が上位に入っていなければ、利用者の期待には届きません。逆に、検索の数値が高くても、回答が形式や具体性で外れれば、期待には届きません。経営層にとっての含意は、RAGの品質は導入時の1回の検査では確定しないということです。運用中にしか検証できないという7類型の論文の結論は、評価の予算を開発費ではなく運用費として組むべき根拠になると、著者は考えます。入力側と生成側の各層の測り方は[入力側の評価の章](17-evaluating-input)で扱います。
