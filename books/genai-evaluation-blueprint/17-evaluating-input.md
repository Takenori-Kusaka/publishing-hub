### 序論：本章が扱う範囲

本章は、[期待値への距離の章](16-distance-to-expectation)で定義した入力の層の5項目(I1必要、I2十分、I3精度、I4鮮度、I5出所)の測り方を、項目ごとに示します。各項目の代表的な手法の定義と数値は一次資料から引きます。どの手法をどの項目に置くかは著者の分類です。

入力側の評価には、2つの系譜があります。1つは1960年代から続く情報検索の評価で、もう1つは検索と生成を一続きの仕組みとして測るRAGの評価です。後者の起点として、2020年のKILTは、出力の正しさに加えて、出所を示せるかを評価の軸に含めました [ [ 164 ] ](https://arxiv.org/abs/2009.02252) 。参照回答の要らないRAG専用の枠組みが出そろったのは2023年です。系譜そのものは[RAG評価の成立の章](06-rag-evaluation)で述べたので、本章では現在の実務で使える測り方に絞ります。

本章が扱わないのは、生成側の忠実性と事実性、引用の裏づけです。それらは[生成側の評価の章](18-evaluating-generation)で扱います。

### 1. 入力側の評価の骨格

情報検索の評価は、文書集合・問い・適合性判定からなるテストコレクションで測る方式が基本です。英国のCranfieldの実験は1966年の報告書で1,400文書と279の質問を使いました [ [ 143 ] ](https://ntrl.ntis.gov/NTRL/dashboard/searchResults/titleDetail/PB169574.xhtml) 。1992年に始まったTRECは、参加システムの結果をプールして判定する方式を確立しました [ [ 3 ] ](https://trec.nist.gov/overview.html) 。

RAGの評価は、この骨格を生成と組み合わせました。RAGASは2023年に、参照回答なしでRAGを評価する枠組みとして登場しました [ [ 41 ] ](https://arxiv.org/abs/2309.15217) 。TruLensは文脈の関連性・根拠性(groundedness)・回答の関連性の3つを「RAG Triad」と呼びます [ [ 168 ] ](https://www.trulens.org/getting_started/core_concepts/rag_triad/) 。Amazon Bedrockの評価も、検索のみの評価(文脈の関連性、網羅性)と検索と生成の評価を分けています [ [ 241 ] ](https://aws.amazon.com/about-aws/whats-new/2025/03/amazon-bedrock-rag-evaluation-generally-available) 。どの道具も、検索の側を独立に測る形を取っています。

### 2. I1必要：入力だけで何が足りないか

I1は、ユーザーの入力から集めるべきものを正しく把握したかを問います。5項目のうち、標準の指標が最も未成熟な項目です。

入力が曖昧なことは、標準データでも珍しくありません。AmbigQAは、質問応答の標準データであるNQ-openの質問の半数超が曖昧だと報告しました [ [ 1301 ] ](https://arxiv.org/abs/2004.10645) 。曖昧さを解く手段の1つは、聞き返すことです。Aliannejadiらは、良い明確化の質問を1つするだけで、上位1件の適合率が170%超改善することを、最良の質問を選べると仮定した実験(オラクル実験)で示しました [ [ 1302 ] ](https://arxiv.org/abs/1907.06554) 。

検索するかどうかの判断も、I1に含まれます。Self-RAGは「いつ検索するか」を学習させ、その判断自体を評価の対象にしました [ [ 162 ] ](https://arxiv.org/abs/2310.11511) 。誤った前提を含む質問も、I1の失敗の源です。FreshQAは、規模を問わずすべてのモデルが、急速に変わる知識と誤った前提を含む質問に弱いと報告しました [ [ 219 ] ](https://arxiv.org/abs/2310.03214) 。MicrosoftのAzure AI Searchの文書は、RAGの課題の第一に「クエリ理解」を挙げています [ [ 210 ] ](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview) 。

著者は、I1の測り方を次の3つの率で設計することを勧めます。曖昧な入力を曖昧と検出した率、聞き返しが必要な場面で聞き返した率、誤前提を指摘した率です。いずれも、曖昧・誤前提の入力を意図して混ぜたゴールデンセットがあれば数えられます。

### 3. I2十分：必要な情報が集まったか

I2は、答えに必要な情報が文脈にそろったかを問います。

RagasのContext Recallは、参照回答に含まれる主張のうち、取得した文脈で支持される数を、参照の主張の総数で割った値です。参照文脈が分かっている場合は、取得できた参照文脈の数を参照文脈の総数で割る版もあります。どちらも、何が必要だったかを示す参照が要ります [ [ 1651 ] ](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/) 。

参照なしで十分性を測る方法もあります。Googleの研究者は、文脈が質問に確定的な答えを出すのに必要な情報をすべて含むかを分類する自動判定器を作り、人手ラベルとの一致が93%以上だったと報告しました [ [ 172 ] ](https://arxiv.org/abs/2411.06037) 。これは研究として公表された判定器です。不十分な文脈を与えると、Gemmaの誤答率は文脈なしの10.2%から66.1%に上がりました [ [ 173 ] ](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/) 。

集める量を増やせば十分性は上がりますが、別の問題が出ます。Databricksの実測では、取得する文書を増やすと平均の再現率が2Kトークンで0.468、128Kトークンで0.95に上がった一方、64Kトークン超で精度を保てたのは最新の少数のモデルだけでした [ [ 194 ] ](https://www.databricks.com/blog/long-context-rag-performance-llms) 。

目標値の例として、OpenAIの評価の手引きは「文脈の再現率0.85以上、文脈の適合率0.7超」を挙げています [ [ 119 ] ](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 。これは1つの例示で、業務ごとに決め直す値です。

### 4. I3精度：雑音は少ないか

I3は、集めた情報が関係のあるものか、関係のない雑音がどれだけ混じったかを問います。

RagasのContext Precisionは、関係のある断片を上位に並べられたかを測ります。返した断片の各順位について、その順位までの適合率に、その順位の断片が関係あるか(1または0)を掛けた値を合計し、返した断片のうち関係ある断片の件数で割ります [ [ 167 ] ](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/) 。段階的な適合度を扱うnDCGは、2002年にJärvelinとKekäläinenが提案した指標です [ [ 147 ] ](https://researchportal.tuni.fi/en/publications/cumulated-gain-based-evaluation-of-ir-techniques) 。

雑音の害は実測されています。Chromaの2025年の報告は、妨害文が1つあるだけで性能が落ちること、焦点を絞った約300トークンの入力が約113Kトークンの全文より一貫して高いことを示しました [ [ 195 ] ](https://www.trychroma.com/research/context-rot) 。

検索の構成は、評価して選ぶものです。次の数値は、いずれも提供事業者が自社の手法について公表したものです。

| 公表者 | 比較 | 結果 |
| --- | --- | --- |
| Microsoft(2023年) | キーワード、ベクトル、ハイブリッド、ハイブリッドと意味的ランカー | 顧客データのnDCG@3で40.6、43.8、48.4、60.1 [ [ 201 ] ](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/azure-ai-search-outperforming-vector-search-with-hybrid-retrieval-and-reranking/3929167) |
| Anthropic(2024年) | 文脈つき埋め込み、BM25の併用、再ランキングの併用 | 上位20件の取得失敗率が5.7%から3.7%、2.9%、1.9%へ [ [ 197 ] ](https://www.anthropic.com/news/contextual-retrieval) |
| Chroma(2024年) | 文書の断片の分け方(チャンク分割) | 戦略により再現率が最大9%違う [ [ 199 ] ](https://www.trychroma.com/research/evaluating-chunking) |

### 5. I4鮮度：情報は古くないか

I4は、集めた情報が質問の時点で正しいかを問います。時間で変わる事実への対応は、2021年から測られています。TimeQAでは、最良のモデルの正答率が46%で、人間の87%に遠く及びませんでした [ [ 216 ] ](https://arxiv.org/abs/2108.06314) 。

鮮度の評価には、評価データ自体を更新し続ける設計が要ります。RealTime QAは毎週新しい質問を出す動的な評価で、GPT-3が取得文書に十分な情報がないと古い答えを返す傾向を示しました [ [ 218 ] ](https://arxiv.org/abs/2207.13332) 。FreshQAのリポジトリは、データセットを週次か要望に応じて更新すると述べています [ [ 219 ] ](https://arxiv.org/abs/2310.03214) 。

企業の文書では、古い版が検索結果に混じることがI4の主な失敗です。MicrosoftはCopilotの導入手引きで、活動のない文書や陳腐化した文書を保持・削除の方針で取り除き、回答の品質を上げるよう求めています [ [ 214 ] ](https://learn.microsoft.com/en-us/microsoft-365/copilot/configure-secure-governed-data-foundation-microsoft-365-copilot) 。企業文書の陳腐化率を示す一次統計は、本書の調査では見つかりませんでした。著者は、取得した文書の更新日の分布と、正本でない版が上位に入った率を記録することを、I4の最小の測り方として勧めます。

### 6. I5出所：信頼でき、使ってよいか

I5は、情報が信頼できる出所から来たか、利用者がそれを読む権限を持つかを問います。

権限は、評価の対象として明記されています。Azure AI Searchの文書は「利用者とエージェントは許可された内容だけを取得しなければならない」と述べます [ [ 210 ] ](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview) 。MicrosoftのCopilotの手引きは、過剰に共有されたサイトや所有者のいないサイトを事前に見つけて直すよう求めます [ [ 214 ] ](https://learn.microsoft.com/en-us/microsoft-365/copilot/configure-secure-governed-data-foundation-microsoft-365-copilot) 。

出所の信頼性の失敗は、検索の要約で表に出ました。Googleは2024年5月、検索の要約機能の誤回答の原因を、情報の乏しい「データの空白」、風刺、フォーラムの皮肉などと説明し、ユーザー生成コンテンツの利用を制限しました [ [ 230 ] ](https://blog.google/products/search/ai-overviews-update-may-2024/) 。どの出所を検索の対象に入れるかが、I5の評価の対象です。

著者は、権限を件数の試験として測ることを勧めます。権限の違う試験用のアカウントを用意し、各アカウントで、読んではならない文書を狙った質問を投げます。回答や引用にその文書が出た件数を数え、目標は0件とし、1件でも出れば公開を止めます。製品として複数の顧客に提供する場合は、顧客ごとの文書が混ざらないかも同じ形で試します。権限の設定や文書の共有範囲を変えたときは、この試験を回し直します。

出典を引用して答える場合、引用が主張を支持しているかは、生成した文と出典の対応の問題です。著者はこれを生成の層のG2に置き、[生成側の評価の章](18-evaluating-generation)で扱います。

### 7. 入力側の評価の組み方

5項目の測り方を、参照データの要否で整理します。この表は著者による整理です。

| 項目 | 主な指標 | 参照データ | 道具の例 |
| --- | --- | --- | --- |
| I1必要 | 曖昧の検出率、聞き返しの率、誤前提の指摘率 | 曖昧・誤前提の入力を混ぜたセット | 自前の採点 |
| I2十分 | 文脈の再現率、十分性 | 参照回答か根拠の文書 | Ragas、Bedrock |
| I3精度 | 文脈の適合率、nDCG | 適合性のラベル(無ければ審判モデル) | Ragas、Foundry |
| I4鮮度 | 古い版の混入率、時点つき正答率 | 更新日つきの文書 | 自前の記録 |
| I5出所 | 権限違反の件数、信頼できない出所の混入率 | 権限の表、試験用のアカウント、出所の一覧 | 権限は自前の試験、出所は自前の記録 |

参照データが要らない指標から始めると、運用を早く回せます。MicrosoftのFoundryは、根拠ラベルがあれば検索品質の複合指標を、なければ審判モデルによる1から5の採点を使い分けます [ [ 242 ] ](https://learn.microsoft.com/en-us/azure/ai-foundry/concepts/evaluation-evaluators/rag-evaluators) 。著者は、次の順序を勧めます。最初に、I5の権限を件数の試験として作ります。次に、I3を審判モデルによる参照なしの採点から始めます。I2は参照が要るので、ゴールデンセットの各件に根拠の文書を付けて測ります。ゴールデンセットが育つにつれて、I3も参照ありの指標に移ります。

### 本章の位置づけ

本章の5項目への分類と、I1とI4の測り方、I5の権限の試験の提案は、著者によるものです。I2とI3には、Ragasや各クラウドの評価機能という確立した指標があります。I1とI4、そしてI5のうち権限の部分には、広く使われる標準の指標がまだありません。

著者は、入力側の評価で最初に投資すべきはI5の権限だと考えます。I2とI3の失敗は回答の質を下げますが、I5の失敗は読んではならない情報を回答に出します。被害の性質が違うため、権限の評価は精度の評価と別に、件数で管理するのが安全です。
