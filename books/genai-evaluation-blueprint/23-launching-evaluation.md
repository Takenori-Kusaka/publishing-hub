### 序論：本章が扱う範囲

本章は、本書の枠組みを、組織が最初の90日で実行する手順に落とします。目標は、評価の成熟度をV1(固定セット)からV2(自動評価)へ上げることです。V0(目視)の組織は、90日の前半でV1に上がります。

手順は6つです。前半の3つで、評価の現在地を診断し、測る項目を絞り、ゴールデンセットを人が採点します。後半の3つで、審判モデルで自動化し、90日の計画に並べ、経営会議に出す1枚の資料に書きます。成熟度の定義は[評価の成熟度の章](19-evaluation-maturity)に、測る項目の定義は[期待値への距離の章](16-distance-to-expectation)にあります。導入フェーズS1〜S6との対応は[導入フェーズと評価の章](20-adoption-stage-and-evaluation)で扱いました。

本章の件数と時間の目安は、公表された実務の文書から引いたものです。記入例は架空の会社のもので、著者の例示です。本編『AIトランスフォーメーションの設計図』の会議資料と90日計画の型を、評価に絞って作り直しています。

### 1. 手順1：評価の現在地を診断する

次の問いに上から答え、最初に「いいえ」となった段階の1つ下が現在地です。

| 段階 | 問い |
| --- | --- |
| V0目視 | 出力の良否を、作った人が数件を見て決めているか |
| V1固定セット | 用途ごとに数十件以上のゴールデンセットがあり、同じ基準で人が採点しているか |
| V2自動評価 | 変更のたびに、指標か審判モデルで回帰の検査を回しているか |
| V3本番評価 | 本番の記録を採取し、抜き取りで人が見て、監視しているか |
| V4評価駆動 | 評価の結果が仕様と改善を決め、記録が監査に耐えるか |

導入フェーズごとに要る段階は、[導入フェーズと評価の章](20-adoption-stage-and-evaluation)の対応表のとおりです。診断は、用途ごとに行います。社内文書検索はV1、議事録の要約はV0という分布が普通です。全社の平均で1つの段階を名乗ると、最も弱い用途が見えなくなります。

### 2. 手順2：測る項目を3〜4つに絞る

本書は、評価の対象を入力側の5項目(I1必要、I2十分、I3精度、I4鮮度、I5出所)と生成側の5項目(G1整形、G2忠実、G3事実、G4安全、G5期待)に分けました。最初の90日で10項目すべては測りません。用途の失敗に効く3〜4項目を選びます。

入力側を外さないことが要点です。Googleの研究では、文脈なしで10.2%だった誤答率は、不十分な文脈を与えると66.1%に上がりました [ [ 173 ] ](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/) 。集めた情報が足りないと、生成側はかえって自信を持って誤ります。実務家のJason Liu(独立のコンサルタント)も、RAGの改善では生成より先に検索を評価するよう勧めています [ [ 642 ] ](https://jxnl.co/writing/2024/05/22/systematically-improving-your-rag/) 。

| 用途の例 | 選ぶ項目の例 | 理由 |
| --- | --- | --- |
| 社内規程の問い合わせ(社内文書検索) | I2十分、I5出所、G2忠実、G5期待 | 規程が集まったか、古い版でないか、条文と回答が一致するかが失敗を分ける |
| 顧客向けの問い合わせ応答 | I3精度、G3事実、G4安全、G5期待 | 誤った約束と不適切な応答が実害になる |
| 社内文書の下書き | G1整形、G5期待 | 形式と、手直しの量が価値を決める |

表の対応は著者の例示です。各社は自社の失敗の記録から選び直します。

### 3. 手順3：ゴールデンセットを作り、人が採点する(V1)

ゴールデンセットは、本番か試行の記録から作ります。Anthropicは2026年1月に、実際の失敗から作った20〜50の単純な課題で始めれば十分だと述べました [ [ 406 ] ](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 。Hamel HusainとShreya Shankarの手引きは、多様な100件の記録から始め、最初の30件は自分で注釈するよう勧めています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。日本の実例でも、Beatrustは日本語の資料から50組を手作りし [ [ 765 ] ](https://note.com/beatrust/n/n6474d36f9290) 、RevCommは21組で審判モデルを検証しました [ [ 732 ] ](https://tech.revcomm.co.jp/llm-as-a-judge) 。

採点の作法は、3つに集約されています。

- **二値で採点する**。同じ手引きは、二値の評価のほうが考えと採点を明確にすると述べています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。LINEヤフーも社内RAGの評価で、各項目を数値ではなく真偽で出し、原因の特定を優先しました [ [ 721 ] ](https://techblog.lycorp.co.jp/ja/20240819a) 。
- **最終判定者を1人決める**。同じ手引きは、ドメイン専門家1人を最終判定者に立てるのが最も効果的だとしています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。社内規程の用途なら、規程を所管する部門の担当者です。
- **基準は採点しながら変わる**。出力を採点するうちに人の基準自体が変わる現象は、2024年に報告されています [ [ 346 ] ](https://arxiv.org/abs/2404.12272) 。最初の30件の後に基準を書き直す時間を、計画に入れます。

### 4. 手順4：審判モデルで自動化する(V2)

V2の要点は、審判モデルを人の採点に合わせてから使うことです。審判には、位置・冗長さ・自己ひいきのバイアスが知られています [ [ 89 ] ](https://arxiv.org/abs/2306.05685) 。Anthropicの手引きは、出力を生成したモデルとは別のモデルで評価するのが一般的な慣行だとしています [ [ 352 ] ](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests) 。

**較正に要る人のラベル**。Husainらは、失敗の類型ごとに100〜200件のラベルを付けるよう勧めます [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。より少ない件数の報告もあります。AI Shiftの2026年7月の比較では、評価基準を較正する方法で、10件のラベルから専門家間の一致の80%に達しました。ただしこれは各条件1回、1つのモデルでの結果です [ [ 729 ] ](https://zenn.dev/aishift/articles/08bbe9ec0a4b3b) 。一致の目安として、コーエンのκが0.6以上を求める実務家の提案があります [ [ 439 ] ](https://note.com/wayne_chang/n/n3dcff96258b1) 。本書は数値の基準を1つに決めず、一致の度合いを記録して会議に出すことを勧めます。

**継続的インテグレーションへの組み込み**。DeepEvalは、しきい値を下回る指標でビルドを失敗させます [ [ 415 ] ](https://deepeval.com/docs/evaluation-unit-testing-in-ci-cd) 。費用と速度の釣り合いのため、変更の提案ごとにはゴールデンセットの一部だけを回し、統合の時に全件を回す運用が文書化されています [ [ 416 ] ](https://www.braintrust.dev/docs/evaluate/run-in-ci) 。日本の実務記事は、変更ごとには代表の30〜50件で主要な指標だけを確かめ、リリース前に全件を回す段階運用を勧めています [ [ 438 ] ](https://zenn.dev/libercraft/articles/20260919-ragas-component-evaluation) 。

**費用の構造**。AWSの例では、自動のアルゴリズム評価は追加料金なし、審判モデルはトークンを通常の料金で課金、人手評価は完了した1件あたり0.21ドルです [ [ 395 ] ](https://aws.amazon.com/bedrock/pricing/) 。最大の費目は、多くの場合、評価者の時間です。Husainらは、開発の時間の60〜80%をエラー分析と評価に費やしていると述べています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。

一致が届かない項目は、人の採点に残します。90日の終わりに全項目を自動化できている必要はありません。

### 5. 手順5：最初の90日

次の計画は、用途を1つに絞った例です。用途を増やすのは、次の90日です。

**第1〜30日：集めて見る**。用途を1つ選び、評価者を1人決めます。本番か試行の記録から100件を集め、評価者が最初の30件に合否と理由を付けます。失敗を類型に分け、手順2の項目を3〜4つに絞ります。V0の組織は、ここで初めて失敗の分布を数で持ちます。

**第31〜60日：固定する(V1)**。失敗の類型から20〜50件のゴールデンセットを作ります。各件に、期待する出力の要点と合否の基準を書きます。プロンプトやモデルを変えるたびに、評価者が全件を採点し、結果を記録します。30件を過ぎたら基準を見直します。

**第61〜90日：自動化する(V2)**。項目ごとに審判モデルを作り、人のラベルとの一致を測ります。一致が記録された項目から、継続的インテグレーションに組み込みます。一致が足りない項目は人の採点に残し、次の90日の課題にします。

90日の終わりの確認は3点です。ゴールデンセットがあること。審判と人の一致の度合いが項目ごとに記録されていること。変更のたびに回帰の検査が回っていること。3つがそろってV2で、1つでも欠ければV2の手前です。

### 6. 手順6：会議資料の1枚の型

経営会議に出す資料は、1枚に収めます。本書が勧める型は、次の10の見出しです。記入例は、従業員600名の架空のメーカーが、社内規程の問い合わせに社内文書検索を使う場合です。

| 見出し | 書くこと | 記入例(著者の例示) | 根拠の章 |
| --- | --- | --- | --- |
| 1. 評価の現在地 | 用途ごとのV段階とS段階 | 社内規程の問い合わせはV0、S3 | [評価の成熟度の章](19-evaluation-maturity) |
| 2. 期待値の定義 | 良い出力の条件を1〜3文で | 該当条文を示し、条文と矛盾しない回答。該当がなければ「該当なし」と答える | [期待値への距離の章](16-distance-to-expectation) |
| 3. 測る項目 | 10項目から3〜4つ | I2十分、I5出所、G2忠実、G5期待 | [入力側の評価の章](17-evaluating-input)、[生成側の評価の章](18-evaluating-generation) |
| 4. ゴールデンセット | 件数、出所、更新の頻度 | 40件。試行の記録から作り、四半期ごとに失敗を足す | 本章第3節 |
| 5. 採点の方法と較正 | コード・審判・人の分担と、一致の度合い | 出所の有無はコード、忠実は審判、期待は人。審判と人の一致を項目ごとに記録 | 本章第4節 |
| 6. 合格と停止の基準 | 出す条件と、止める条件 | 忠実の不合格が0件なら出す。本番の抜き取りで不合格が2週続けば前の版に戻す | [失敗から逆算する評価の章](12-evaluation-from-failures) |
| 7. 担当と費用 | 評価者、取りまとめ、費用の内訳 | 評価者は規程を所管する総務の担当1名で週4時間。費用は評価者の時間、審判のトークン、道具 | 本章第4節 |
| 8. 前提とする道筋と指標 | 道筋と、見る指標の担当 | 道筋は決めない。上位3指標を経営企画が四半期に確認 | [3つの道筋の章](22-three-paths) |
| 9. 決裁事項 | 本日承認してほしいこと | 評価者の時間の確保と、V2への移行 | 本章 |
| 10. 答えていない問い | 決めなかったこと、分からないこと | 顧客向けの用途への拡大の時期。審判モデルの提供事業者の選定 | [総括](conclusion) |

7番目の見出しに評価者の時間を書くことが、この型の要点です。評価の費用の大半は道具ではなく人の時間であり、時間を確保しない計画はV1で止まります。10番目の見出しは、本書の記述規範に由来します。決めなかったことを書かない資料は、決めたことの範囲が分からなくなります。

### 🗺️ 図：90日でV1からV2へ ―― 人の採点が先、自動化は後

![90日を3つの箱で示した図。第1〜30日の集めて見る、第31〜60日の固定する(V1、人が採点)、第61〜90日の自動化する(V2、審判を較正)を左から右へ矢印でつなぎ、下に会議資料の1枚を置く](/images/genai-evaluation-blueprint/23-launching-evaluation.png)

#### 図の読み方

図は、上段の3つの箱を左から右へ読みます。左の箱が第1〜30日の「集めて見る」、中央が第31〜60日の「固定する」、右が第61〜90日の「自動化する」です。中央の箱だけを丹(朱色)で縁取りました。ゴールデンセットを人が採点する段階で、本書の図では丹を人が判定する場所にだけ使います。右の箱は藍で、審判モデルという機械が採点する段階です。

下段の帯は、90日の終わりに更新する会議資料の1枚です。本文の第6節の10の見出しに対応します。図の下の添え書きのとおり、審判モデルは人の採点に合わせてから使います。順序を逆にすると、審判の誤りを測る基準がなくなります。

### 経営層への含意

本章の手順と型は、本書の枠組みを会議に持ち込むためのものであり、各社の判断を代替しません。使うときの注意を3つ述べます。

第一に、最初の投資は道具ではなく評価者の時間です。ドメイン専門家1人の週数時間を90日間確保できるかが、V1に上がれるかを決めます。決裁事項に、この時間を書きます。

第二に、自動化は人の採点の後に来ます。審判モデルは人の判断に合わせて初めて使えます。90日でV2の手前にとどまる項目があっても、それは失敗ではありません。一致を確かめずに自動化した項目のほうが危険です。

第三に、1回の90日で上げる用途は1つです。最初の用途で作ったゴールデンセットと手順は、次の用途に使い回せます。90日の終わりに1枚を更新し、次の用途を選びます。
