### 序論：本章が扱う範囲

本章は、本書の枠組みを、組織が最初の90日で実行する手順に落とします。目標は、1つの業務用途の評価の成熟度をV2(自動評価)まで上げることです。V0(目視)から始める組織は、最初の60日でV1(固定セット)に上がり、残りの30日でV2へ進みます。

90日で届くのはV2までです。[導入フェーズと評価の章](20-adoption-stage-and-evaluation)の対応表では、顧客向けの機能(S5)にはV3からV4が要ります。そのため、顧客向けの用途では「90日でV2へ上げ、顧客へ広げる前に本番の抜き取り(V3の最小形)を足す」という順序を、本章は勧めます。全社員向けの汎用チャット(S1〜S2)は、90日の対象にしません。汎用チャットは、[導入フェーズと評価の章](20-adoption-stage-and-evaluation)の第2節のとおり、確認の手順を書いた利用規程と、よく使う業務の数件の確認例で扱います。

手順は6つです。前半の3つで、評価の現在地を診断し、測る項目を絞り、ゴールデンセットを人が採点します。後半の3つで、審判モデルで自動化し、90日の計画を立て、経営会議へ出す1枚の資料を書きます。審判モデルは、AIの出力を別のAIに採点させる仕組みです。成熟度は[評価の成熟度の章](19-evaluation-maturity)で、測る項目は[期待値への距離の章](16-distance-to-expectation)で定義しました。導入フェーズS1〜S6の1行の定義は[付録A](glossary)の第8節に置きました。

本章の件数と時間の目安は、公表された実務の文書から引いたものです。出典の無い件数の目安は書きません。記入例は架空の会社のもので、著者の例示です。手順のうち出典を付けていないものは、著者の推奨です。本編『AIトランスフォーメーションの設計図』の会議資料と90日計画の型を、評価に絞って作り直しています。

### 1. 手順1：評価の現在地を診断する

次の問いに、V1から順に答えます。「はい」が続く最も上の段階が現在地です。V1の問いが「いいえ」なら、現在地はV0です。V0は問いではなく、測る仕組みが何も無い状態の既定値です。問いを一部しか満たさない場合は「いいえ」とします。

| 段階 | 問い(その用途の担当が答える) |
| --- | --- |
| V0目視 | 問いなし。V1の問いが「いいえ」ならV0 |
| V1固定セット | その用途のゴールデンセットがあり、同じ基準で人が採点しているか |
| V2自動評価 | 変更のたびに、指標か審判モデルで回帰の検査を回しているか |
| V3本番評価 | 本番の記録を採取し、抜き取りで人が見て、監視しているか |
| V4評価駆動 | 評価の結果が仕様と改善を決め、記録が監査に耐えるか |

問いに答えるのは、その用途の担当です。自社で作った仕組みに限らず、購入した製品や社員向けの汎用チャットでも、使う部門の担当が答えます。

**購入した製品の場合の読み替え**。購入した製品では、モデルやプロンプトを変えるのは提供事業者です。V2の問いの「変更」は、提供事業者の更新の告知と読み替えます。告知が無くても出力は変わりうるので、定期の再採点も契機にします。Anthropicは2025年9月に、基盤の不具合で応答の品質が断続的に落ち、検出が遅れたと公表しています [ [ 494 ] ](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues) 。購入品では前の版に戻せないことが多いため、止める手段は、利用の停止か利用の範囲の縮小と、利用部門への周知になります。

導入フェーズごとに要る段階は、[導入フェーズと評価の章](20-adoption-stage-and-evaluation)の対応表のとおりです。診断は、用途ごとに行います。たとえば、社内文書検索はV1、議事録の要約はV0というように、用途ごとに段階は違いえます(著者の例示)。全社の平均で1つの段階を名乗ると、最も弱い用途が見えなくなります。

### 2. 手順2：測る項目を3〜4つに絞る

本書は、評価の対象を入力側の5項目(I1必要、I2十分、I3精度、I4鮮度、I5出所)と生成側の5項目(G1整形、G2忠実、G3事実、G4安全、G5期待)に分けました。最初の90日で10項目すべては測りません。用途の失敗に効く3〜4項目を選びます。

入力側を外さないことが要点です。Googleの研究では、文脈なしで10.2%だった誤答率は、不十分な文脈を与えると66.1%に上がりました [ [ 173 ] ](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/) 。集めた情報が足りないと、生成側はかえって自信を持って誤ります。実務家のJason Liu(独立のコンサルタント)も、RAGの改善では生成より先に検索を評価するよう勧めています [ [ 642 ] ](https://jxnl.co/writing/2024/05/22/systematically-improving-your-rag/) 。

| 用途の例 | 選ぶ項目の例 | 理由 |
| --- | --- | --- |
| 社内規程の問い合わせ(社内文書検索) | I2十分、I4鮮度、I5出所、G2忠実 | 規程が集まったか、古い版が混じらないか、読む権限のある規程だけを使ったか、条文と回答が一致するかが失敗を分ける |
| 顧客向けの問い合わせ応答(製品の文書を検索して答える場合) | I2十分、I3精度、I5出所、G2忠実、G4安全 | 答えに要る文書を集めたか、与えた文書と回答が一致するか、不適切な応答をしないかが実害を分ける。複数の顧客に出す製品では、顧客ごとの文書が混ざらないかをI5の権限の試験で最初に確かめる。顧客への実害の経路が多いので、項目は5つになる。文書を検索せずモデルの知識で答える場合は、G2の代わりにG3事実を測る |
| 社内文書の下書き | G1整形、G5期待 | 形式と、手直しの量が価値を決める |

表の対応は著者の例示です。各社は自社の失敗の記録から選び直します。I5とG4は、ゴールデンセットの合否だけでは測れないため、次の2つの試験を足します。

**I5の権限の試験**。I5を選んだ場合は、権限を試験で測ります。閲覧の権限が違う試験用の利用者を2つ以上用意します。片方だけが読める文書を答えに要する質問を、セットに入れます。読めないはずの利用者への回答に、その文書の内容や出所が出た件を、権限違反として数えます。権限違反は件数で記録します。1件でも出れば公開(または拡大)を止め、原因を調べて直してから再試験します。

**G4の自社試験**。G4を選んだ場合は、ゴールデンセットとは別に安全の試験セットを作り、同じ回帰の検査で一緒に回します。入れる入力は2種類です。1つは攻撃の入力で、指示の乗っ取りや情報の引き出しを狙う文を、利用者の入力と、検索される文書の両方に仕込みます。検索される文書に指示を仕込む攻撃は、2023年2月に実在のシステムで実証されています [ [ 1102 ] ](https://arxiv.org/abs/2302.12173) 。もう1つは過剰拒否を見る入力で、安全なのに危険な語を含む問いです。この型の試験は、2023年8月にXSTestが定式化しました [ [ 316 ] ](https://arxiv.org/abs/2308.01263) 。見逃しと断りすぎの件数を並べて記録し、片方だけを下げる調整を避けます。

### 3. 手順3：ゴールデンセットを作り、人が採点する(V1)

ゴールデンセットは、本番か試行の記録から作ります。本番の前で試行の記録が無い場合は、既存の問い合わせ履歴(サポートの記録など)を素材にできます。Anthropicは2026年1月に、実際の失敗から作った20〜50の単純な課題で始めれば十分だと述べました [ [ 406 ] ](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 。Hamel HusainとShreya Shankarの手引きは、多様な100件の記録から始め、最初の30件は自分で注釈するよう勧めています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。日本の実例でも、Beatrustは日本語の資料から50組を手作りし [ [ 765 ] ](https://note.com/beatrust/n/n6474d36f9290) 、RevCommは21組で審判モデルを検証しました [ [ 732 ] ](https://tech.revcomm.co.jp/llm-as-a-judge) 。

**各件に入れるもの**。各件には、入力、期待する出力の要点、合否の基準を書きます。I2やI3を選んだ場合は、根拠の文書(参照文脈)も各件に付けます。取得の漏れを測る指標は、比べる相手の参照が無いと計算できないためです [ [ 1808 ] ](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/) 。

**正解の更新と版**。根拠の文書が改定されると、セットの正解と根拠が古くなり、正しい回答を不合格にします。対策は3つです。セットに版の番号を付け、どの版で採点したかを結果に残します。規程や製品の文書が改定されたら、その文書を根拠にする件の正解を直します。直す担当を、規程を所管する部門の評価者に決めておきます。

**記録の扱い**。本番や試行の記録には、個人情報や機密が含まれえます。個人情報保護委員会は2023年6月に、個人情報取扱事業者が生成AIサービスに個人情報を含むプロンプトを入力する場合は、利用目的の達成に必要な範囲内であることを十分に確認するよう注意喚起しました [ [ 758 ] ](https://www.ppc.go.jp/files/pdf/230602_kouhou_houdou.pdf) 。著者は、外部の審判モデルや観測の道具に記録を送る評価にも、同じ確認が要ると考えます。社内の個人情報の規程に従い、評価用の写しから個人を特定する情報を除きます。記録を読む評価者の範囲と保管先を決め、利用規程で利用者に知らせます。購入した製品では、記録を取り出す機能があるかと、提供事業者が記録をどう扱うかを、契約で確かめます。

採点の作法は、3つに集約されています。

- **二値で採点する**。同じ手引きは、二値の評価のほうが考えと採点を明確にすると述べています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。LINEヤフーも社内RAGの評価で、各項目を数値ではなく真偽で出し、原因の特定を優先しました [ [ 721 ] ](https://techblog.lycorp.co.jp/ja/20240819a) 。
- **最終判定者を1人決める**。同じ手引きは、ドメイン専門家1人を最終判定者に立てるのが最も効果的だとしています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。社内規程の用途なら、規程を所管する部門の担当者です。
- **基準は採点しながら変わる**。出力を採点するうちに人の基準自体が変わる現象は、2024年に報告されています [ [ 346 ] ](https://arxiv.org/abs/2404.12272) 。最初の30件の後に基準を書き直す時間を、計画に入れます。

### 4. 手順4：審判モデルで自動化する(V2)

V2の要点は、審判モデルを人の採点に合わせてから使うことです。審判には、位置・冗長さ・自己ひいきのバイアスが知られています [ [ 89 ] ](https://arxiv.org/abs/2306.05685) 。Anthropicの手引きは、採点には出力を生成したモデルとは別のモデルを使うことを勧めています [ [ 352 ] ](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests) 。

**較正に要る人のラベル**。較正とは、審判の採点基準を調整し、人の判定に近づけることです。Husainらは、失敗の類型ごとに100〜200件のラベルを付けるよう勧めます [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。より少ない件数の報告もあります。AI Shiftの2026年7月の比較では、要約の一貫性の採点で、評価基準を較正する方法が10件のラベルから専門家間の一致の80%に達しました。一方、幻覚の検知ではラベルの効果は小さく、どちらも各条件1回、1つのモデルでの結果です [ [ 729 ] ](https://zenn.dev/aishift/articles/08bbe9ec0a4b3b) 。

本書は件数の目安を1つに決めません。件数は、用途の失敗の率と、見分けたい差の大きさで決まります。最初は90日の計画で集まるラベル(記録100件の注釈とゴールデンセット)から小さく始め、審判と人の一致を見て増やします。較正に使うラベルと、一致を測るラベルは分けます。審判の基準を調整したラベルで一致を測ると、一致を高く見積もるためです。

**一致の度合いの記録**。一致の度合いは、Cohenのκのような係数で表します。κは、2人の評価者(ここでは人と審判)の一致を、偶然による一致を除いて測る指標です。κが0.6以上なら実質的な一致とみなす、という実務家の説明があります [ [ 439 ] ](https://note.com/wayne_chang/n/n3dcff96258b1) 。本書は数値の基準を1つに決めず、一致の度合いと、測るのに使ったラベルの件数を記録して会議に出すことを勧めます。

**件数が少ないときの不確かさ**。40件のような少ない件数の合否は、本番の不合格の率を広い幅でしか示しません。AnthropicのEvan Millerは2024年11月に、評価を実験として扱い、標準誤差と信頼区間を添えるよう提案しました [ [ 618 ] ](https://arxiv.org/abs/2411.00640) 。合否の件数と一緒に、率の推定の幅も記録します。不合格が0件でも、本番の不合格が0であることは意味しません。

**審判の採点の揺れ**。審判モデルの採点は、同じ入力でも実行のたびに揺れることがあります。審判の版を固定し、同じ件を複数回走らせて、結果が割れた件を人が見ます。日本の実務記事も、審判のバイアスに備えて複数の審判で確かめるよう求めています [ [ 438 ] ](https://zenn.dev/libercraft/articles/20260919-ragas-component-evaluation) 。審判の版を替えたら、人との一致を測り直します。

**継続的インテグレーションへの組み込み**。継続的インテグレーション(CI)は、変更のたびに検査を自動で回す開発の仕組みです。DeepEvalは、しきい値を下回る指標があると、変更を取り込む手続き(ビルド)を自動で失敗させます [ [ 415 ] ](https://deepeval.com/docs/evaluation-unit-testing-in-ci-cd) 。費用と速度の釣り合いのため、変更の提案ごとにはゴールデンセットの一部だけを回し、統合の時に全件を回す運用が文書化されています [ [ 416 ] ](https://www.braintrust.dev/docs/evaluate/run-in-ci) 。日本の実務記事は、変更ごとには代表の30〜50件で主要な指標だけを確かめ、リリース前に全件を回す段階運用を勧めています [ [ 438 ] ](https://zenn.dev/libercraft/articles/20260919-ragas-component-evaluation) 。

**回帰の検査を回す契機**。回帰の検査は、自社の変更のたびに加えて、提供事業者のモデルの更新の告知と、定期の実行でも回します。利用者が何も変えなくても、提供事業者の側の変化で出力は変わるためです。審判モデルについて、著者は次を勧めます。提供事業者がモデルを更新すると審判の採点も変わりうるので、審判のモデルの版を記録し、版が変わったら較正をやり直します。これとは別に、評価の基盤そのものも提供事業者の都合で廃止されえます。OpenAIは2026年6月に、自社の評価の基盤の廃止を告知しました [ [ 128 ] ](https://developers.openai.com/api/docs/deprecations) 。

**費用の構造**。AWSのBedrockでは、自動のアルゴリズム評価は追加料金なし、審判モデルはトークン(モデルが文章を処理する単位)の数を通常の料金で課金します。自前の作業者を持ち込む人手評価では、完了したタスク1件あたり0.21ドルの手数料がかかります [ [ 395 ] ](https://aws.amazon.com/bedrock/pricing/) 。この手数料は、採点する人の人件費を含みません。最大の費目は、多くの場合、評価者の時間です。Husainらは、開発の時間の60〜80%をエラー分析と評価に費やしていると述べています [ [ 351 ] ](https://hamel.dev/blog/posts/evals-faq/) 。費用は次の式で見積もります。

```text
評価者の費用 = 評価者の時間 × 社内の時間単価
技術の担当の費用 = 審判とCIの作業の時間 × 社内の時間単価(外部委託なら見積もり)
審判の費用 = 1件の採点の料金(提供事業者の料金表) × 件数 × 回数
```

一致が届かない項目は、人の採点に残します。90日の終わりに全項目を自動化できている必要はありません。

### 5. 手順5：最初の90日

次の計画は、用途を1つに絞った例です。用途を増やすのは、次の90日です。担当は3つの役割に分けます。評価者は、業務を知る最終判定者です。技術の担当は、V2の自動化(審判モデルとCIへの組み込み)を担います。責任者は、評価の結果を受けて出すか止めるかを決め、経営会議に報告します。社内に技術の担当がいない場合は、外部に委託するか、V1で止めて次の90日に技術の担当を確保します。V1で止めても、ゴールデンセットと人の採点は、[3つの道筋の章](22-three-paths)の後悔しない手としてどの道筋でも残ります。

**第1〜30日：集めて見る**。用途を1つ選び、評価者・技術の担当・責任者を決めます。記録を集める前に、利用目的、保管先、個人を特定する情報の除き方を決め、社内の承認を得ます(第3節)。本番か試行の記録から100件を集め、評価者が最初の30件に合否と理由を付けます。失敗を類型に分け、手順2の項目を3〜4つに絞ります。V0の組織は、ここで初めて失敗の分布を数で持ちます。

**第31〜60日：固定する(V1)**。失敗の類型から20〜50件のゴールデンセットを作ります。各件に、期待する出力の要点と合否の基準を書き、I2やI3を選んだ場合は根拠の文書を付けます。セットには版の番号を付けます。I5を選んだら権限の試験の件を、G4を選んだら安全の試験セットを作ります(第2節)。プロンプトやモデルを変えるたびと、提供事業者の更新の告知のたびに、評価者が全件を採点し、結果を記録します。30件を過ぎたら基準を見直します。技術の担当は、この間に道具を選びます。選ぶ観点は、評価のデータと記録を道具の外へ取り出せることです。道具の例は、[評価の成熟度の章](19-evaluation-maturity)の第3節と第4節にあります。

**第61〜90日：自動化する(V2)**。項目ごとに審判モデルを作り、較正に使ったものとは別の人のラベルで、一致を測ります。一致が記録された項目から、CIに組み込みます。回帰の検査の契機に、提供事業者の更新の告知と定期の実行を加えます。一致が足りない項目は人の採点に残し、次の90日の課題にします。

90日の終わりの確認は3点です。ゴールデンセットがあること。審判と人の一致の度合いが項目ごとに記録されていること。変更のたびに回帰の検査が回っていること。3つがそろってV2で、1つでも欠ければV2の手前です。

**顧客へ広げる前に足すこと**。顧客向けの用途では、V2の確認がそろっても、そのまま全顧客へは広げません。まず、限られた顧客か社内の利用者へ出します。本番の記録を採取し、評価者が週ごとの抜き取りで採点する仕組みを動かしてから、全顧客へ広げます。抜き取りの件数は、評価者の時間から逆算します。最初の2週間で、評価者が1件の採点にかかる時間を測ります。評価者が確保した週の時間をその時間で割り、週の抜き取りの件数の上限にします。この仕組みが、V3の最小形です。本番の抜き取りに依る停止の基準は、この段階から使えます。

### 6. 手順6：会議資料の1枚の型

経営会議に出す資料は、1枚に収めます。本書が勧める型は、次の11の見出しです。記入例は、従業員600名の架空のメーカーが、社内規程の問い合わせに、購入した社内文書検索の製品を使う場合です。

| 見出し | 書くこと | 記入例(著者の例示) | 根拠の章 |
| --- | --- | --- | --- |
| 1. 評価の現在地 | 用途ごとのV段階とS段階 | 社内規程の問い合わせはV0、S3。全社員の汎用チャットはS2で、利用規程と確認例で扱う | [評価の成熟度の章](19-evaluation-maturity)、[付録A](glossary) |
| 2. 期待値の定義 | 良い出力の条件を1〜3文で | 該当条文を示し、条文と矛盾しない回答。該当がなければ「該当なし」と答える | [期待値への距離の章](16-distance-to-expectation) |
| 3. 測る項目 | 10項目から3〜4つ | I2十分、I4鮮度、I5出所、G2忠実 | [入力側の評価の章](17-evaluating-input)、[生成側の評価の章](18-evaluating-generation) |
| 4. ゴールデンセット | 件数、出所、各件の中身、更新の頻度 | 40件。試行の記録から作り、各件に根拠の条文と規程の版を付ける。規程の改定時に該当する件の正解を直し、四半期ごとに失敗を足す | 本章第3節 |
| 5. 採点の方法と較正 | コード・審判・人の分担と、一致の度合い | 権限違反と古い版の混入はコードで件数を数える。十分と忠実は審判、最終の合否は評価者。審判と人の一致を、Cohenのκとラベルの件数で項目ごとに記録 | 本章第2節、第4節 |
| 6. 合格と停止の基準 | 出す条件と止める条件を、V2とV3の段階に分けて | V2：40件で忠実の不合格と権限違反が0件なら全部署へ広げる。件数が少ないと0件でも失敗の率の上限は大きいので、率の推定の幅を併記する(第4節)。権限違反が1件でも出たら拡大を止め、直して再試験する。提供事業者の更新後の再採点で不合格が出たら、利用部門へ周知し範囲を縮める。V3：本番の抜き取りで忠実の不合格が続けば、利用を止める | 本章第1節、第4節、第5節 |
| 7. 担当と費用 | 評価者、技術の担当、費用の式 | 評価者は総務の担当1名で週4時間(13週で52時間)。技術の担当は情報システム部の1名。費用は第4節の3つの式と、道具の見積もり | 本章第4節、第5節 |
| 8. 責任者と報告の経路 | 誰が確かめ、誰に報告するか | 評価者が月ごとに結果を記録し、責任者の総務部長が四半期の経営会議と内部監査に報告する | 本章第5節 |
| 9. 前提とする道筋と指標 | 道筋と、見る指標の担当 | 道筋は決めない。経営企画が四半期の会議で、経営会議で見る3つの指標に更新があったかを確かめる。EUに製品を出さないので、EUの指標は参考にとどめる | [3つの道筋の章](22-three-paths) |
| 10. 決裁事項 | 本日承認してほしいこと | 評価者と技術の担当の時間の確保と、V2への移行。技術の担当を確保できなければV1で止める | 本章 |
| 11. 答えていない問い | 決めなかったこと、分からないこと | 顧客向けの用途への拡大の時期。審判モデルの提供事業者の選定。汎用チャットをV1に上げるか | [総括](conclusion) |

7番目の見出しに評価者の時間を書くことが、この型の要点です。評価の費用の大半は道具ではなく人の時間であり、時間を確保しない計画はV1で止まります。8番目の見出しは、取締役会の「出力が正しいかを、誰がどう確かめているか」という問いに答える欄です。11番目の見出しは、本書の記述規範に由来します。決めなかったことを書かない資料は、決めたことの範囲が分からなくなります。

### 経営層への含意

本章の手順と型は、本書の枠組みを会議に持ち込むためのものであり、各社の判断を代替しません。使うときの注意を3つ述べます。

第一に、最初の投資は道具ではなく人の時間です。ドメイン専門家1人の週数時間を90日間確保できるかが、V1に上がれるかを決めます。V2へ進むには、技術の担当の時間も要ります。決裁事項に、この2つの時間を書きます。

第二に、自動化は人の採点の後に来ます。審判モデルは人の判断に合わせて初めて使えます。90日でV2の手前にとどまる項目があっても、それは失敗ではありません。一致を確かめずに自動化した項目のほうが危険です。顧客向けの用途では、V2の後に本番の抜き取りを足してから広げます。

第三に、1回の90日で上げる用途は1つです。最初の用途で作ったゴールデンセットと手順は、次の用途に使い回せます。90日の終わりに1枚を更新し、次の用途を選びます。
