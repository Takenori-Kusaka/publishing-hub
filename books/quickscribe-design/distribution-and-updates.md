配布の話は、本編では速度の章と話者分離の章に分かれて出てきます。どちらもその章の主題（速度・評価）の途中で必要になったから書いた、という順番でした。結果として「このアプリはどう配られるのか」を知りたい読者が、2つの章を横断しないと全体像にたどり着けません。この付章はその全体像をまとめるためにあります。個々の実測値と経緯は本編に譲り、ここでは配布設計の骨格だけを並べます。

## 課題と方針

方針は最初から1つでした。**単一バイナリで配る**ことです[^adr12]。個人開発で、複数のインストーラを保守し続ける余裕はありません。

ところが、このアプリは環境依存を2つ抱えます。ひとつは GPU です。文字起こしを実用速度で動かすには GPU が要りますが、GPU の有無とドライバの種類は利用者の環境次第です。もうひとつはネイティブ DLL です。話者分離は onnxruntime などのネイティブ DLL を必要とします。どちらも「あるかもしれないし、ないかもしれない」もので、素直に同梱すると単一バイナリ方針が崩れます。

そこで方針を1行に絞りました。**同梱してよいものだけを同梱し、それ以外は「あるか確かめてから触る」**。配布物を分けることで環境差を吸収するのではなく、1つの配布物が実行時に環境を判定する側に寄せます。

## ランタイムとドライバを分けて考える

この切り分けが、配布設計でいちばん効きました。GPU 依存は一枚岩ではなく、2層に分かれます。

- **ランタイム**は再配布できます。CUDA の場合、`cudart` や `cublas` といったランタイムは EULA の Attachment A で再配布可能と明記されており、インストーラに同梱してよいものです[^eula]。
- **ドライバ**は再配布できません。NVIDIA のディスプレイドライバ（`nvcuda.dll`）は同梱・自動導入のいずれもできず、これが実質的な外部依存になります。NVIDIA 自身の推奨は、検出して公式のダウンロードページへ案内することです[^drv]。

つまり「同梱して解決できる依存」と「案内するしかない依存」は別物で、後者にインストーラの分岐を作り始めると配布物が増えていきます。CUDA 版では実際に、インストーラ（NSIS フック）で `nvcuda.dll` を検出し、ドライバ入手ページを開くか・CPU のまま続行するか・中止するかの3択を出す形にしていました。

## 一本化：Vulkan を選ぶと配布が単純になる

その後、GPU バックエンドを Vulkan に寄せる判断をしました。Vulkan は whisper.cpp 側でベンダー横断（NVIDIA / AMD / Intel）として提供され、専用 DLL の同梱が不要で、必要なのは Vulkan 対応の普通の GPU ドライバだけです[^vulkan]。CUDA が求める「専用ドライバの下限バージョン」より、前提がはるかに低くなります。

速度の章で実測したとおり、Vulkan と CUDA の差はわずかでした。その差のために2つ目の別インストーラ・ドライバ前提・DLL同梱・EULA対応を背負うのは、単一バイナリ方針を自分で崩す行為です。そこで CUDA は廃止しました[^adr29]。配布の観点で言えば、この判断の本体は「速い方を選んだ」ことではなく、**選択肢を1つ減らしたこと**です。

結果、配布はこうなりました ― **単一の Vulkan ビルドが、GPU の無い環境から各社の GPU までを1つでカバーする**。インストーラは1つ、アップデータも1つです。利用者にインストール時点で CPU 版か GPU 版かを選ばせる分岐は消え、CPU/GPU の選択は起動時の自動判定と設定トグルに移りました。

## 落ちないこと：試す前に、確実に知る

単一ビルドが成立するかどうかは、ひとつの条件にかかっていました。**GPU が無い環境で、落ちずに CPU へ行けるか**です。

ここで分かったのは、「試して失敗したらフォールバックする」という手が通じない領域の存在でした。GPU デバイスが無い状態で whisper の GPU 初期化を呼ぶと、C++ 例外で abort します。Rust はこの外来例外を捕捉できないので、`Err` が返ってくる前にプロセスごと落ちます。詳しい再現と出力は速度の章に書きました。

答えは反転します。**触る前に、安全な API で確実に知る**。GPU を初期化する前に Vulkan ローダの C API で物理デバイス数を数え、1台以上ある時だけ GPU 経路に入ります。この列挙は戻り値で結果を返し、例外を投げません。デバイス0・ローダ不在・ドライバ不在は、すべてその場で CPU へ倒れます。abort する経路に一歩も踏み込まない、という組み方です。実装は Rust から20行ほどで、GPU 無しを擬似した状態で「abort せず false を返す」ことを実プロセスの統合テストで固定しました。

同じ考え方を、DLL にも当てています。`vulkan-1.dll` は遅延ロードにしてあり、ローダ自体が無い環境でも実行ファイルは起動します。

## ネイティブ DLL は、必要になってから取りに行く

話者分離の DLL も、同じ方針で扱いました。基本インストーラへ同梱すると単一バイナリ方針を崩します。そこで、機能が有効になった時点でオンデマンドに取得し、遅延ロードで解決する形にしました[^adr31]。

実機での確認は、DLL を実行ファイルの隣に一切置かない状態から始めました。実行ファイルは DLL が未解決でも起動し、起動後にアーカイブから DLL を展開して検索パスを設定したときに初めて、話者分離が呼ばれて成功します。取得や検証に失敗したときは、話者分離を呼ばずにラベル無しの文字起こしへ戻します。**プロセスを落とさない**ことを設計の条件にしました。手順と実測ログは話者分離の章にあります。

配布設計として取り出せる原則は1つです。**オプション機能の依存は、オプションが有効になるまで存在しなくてよい**。そうしておけば、その機能を使わない利用者の配布物は軽いままです。

## 実際に起きた効果

配布物が1つに畳まれたことで、環境差を吸収する場所が「インストーラの分岐」から「起動時の判定」へ移りました。利用者から見ると、インストール時に技術的な選択を求められる場面が無くなります。開発側から見ると、保守するインストーラとアップデート経路が1本で済みます。

もうひとつは、環境を確かめてから触るという型が、GPU と DLL の両方で同じ形になったことです。事前検出と遅延ロードの組み合わせは、どちらの依存にもそのまま当てはまりました。

## 学びと宿題

配布で学んだのは、**依存を「同梱できるか」で分類すると設計が決まる**ことです。同梱できる依存はバイナリの問題で、同梱できない依存は UX の問題になります。混ぜて考えると、インストーラの分岐という一番増えやすいものが増えます。

もう1つは、ネイティブの世界では「試して落ちたら戻る」が成立しない場面もあるという点です。捕捉できない失敗に対しては、フォールバックではなく事前検出を置く。これは GPU に限った話ではないはずです。

最後に、正直な宿題を1つ。**配布物へのコード署名と公証は、まだ対応できていません**。署名の無いインストーラは、OS 側の警告を越えないと実行できません。単一バイナリに畳んで配布経路を単純にしたところまでは進みましたが、その1本を「安心して実行できる1本」にする作業は残っています。配布は技術的に動くことと、利用者が不安なく受け取れることは別で、いまは前者だけが終わっている状態です。
