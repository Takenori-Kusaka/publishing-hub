> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

生成AIとの開発では、品質を守る「装置」が増えます。検査スクリプト・CI のワークフロー・PR のテンプレート・hook・AI への指示書です。がんばりクエストでは、この装置が製品コードの 0.76 倍に達し、直近の PR の 60% が装置自身の修理になりました。その時点で装置を減らす専任のロールを新設し、続いて装置の追加を凍結しました。この章では、その Platform ロールと、装置を減らすときの判断原則、「80 点で止める」に至った経緯を扱います。

## 装置が顧客を止めた

Platform セッションの起動プロンプトは、冒頭で凍結を宣言しています。

> 「増やす・良くする」は凍結中です（2026-08-05〜、オーナー決定）
> 品質ゲート / guard / fitness / lint / テンプレート / hook を 増やさない・良くしない。`pre-ready` にも step を増やしません。進めてよいのは A（削減）と B（リリースプロセスへの移管）だけ[^platform]

理由は数字で書かれています。

> なぜ: 直近 14 日の Issue は装置・プロセスが 56%、顧客に届く変更が 24%。`scripts/check-*` は 61 本あり、「8 本に絞る」E5 は CLOSED なのに 1 本も減っていません。装置が顧客を止めた実例として、本番 NUC が 3.5 時間停止しています（#4275、バックアップの沈黙を防ぐ検査が原因）。[^platform]

バックアップが黙って失敗することを防ぐための検査が、本番のセルフホスト環境を 3.5 時間止めました。装置は顧客を守るためにあるのに、装置が顧客を止めた。この実例が、凍結の決め手になりました。

凍結には例外と再開条件があります。例外は「顧客の金かデータに現に届いている装置不具合」だけで、判定は QM が行い、PO の決裁は要りません。再開のトリガーは、課金の一連の流れ（checkout、webhook、プランの反映、実画面）が staging で 1 周した時点です[^platform]。

## Dev を顧客とするロール

Platform は Team Topologies の platform team にあたり、Dev を顧客として扱います。目的は「装置を増やして人に守らせるのではなく、守らなくてよい形にする」ことです[^platform]。憲章の 3 つの制約は [第Ⅳ部-1](one-human-many-sessions) で見ました。装置の総数は ratchet で増やせない、「直す」より「消す」「生成する」を先に検討する、成功指標は Dev の手戻りである、の 3 つです。

成功指標の具体は 3 つの数です。

| 指標 | 何を数えるか |
| --- | --- |
| QM の差し戻し件数 | `state:qm-blocked` が付いた回数 / PR |
| `pre-ready` の落ち回数 | Ready 化までに何回 fail したか |
| PR の往復回数 | Draft → Ready → 差し戻し → Ready の回数 |

計測は既存のデータ（label の履歴、CI の run、PR のレビュー回数）から取ります。「新しい計測装置を先に作らない」と明記されているのは、装置を減らすロールが装置を増やして始めるのは自己矛盾だからです[^platform]。

ratchet には、あとから明確化された例外があります。

> ratchet が縛るのは「新しい検査の追加」だけ。置換・統合は増加に当たらない（2026-08-02、#4199 で明確化）。散在した同じ記述を SSOT 1 本に寄せる作業（例: `node-version: 22` × 52 箇所 → `node-version-file: .nvmrc`）は行数がほぼ変わらず、減らす原資を必要としない。この区別が無いと、制約が正しい作業を止める — 実際に #4199 本体（置換）が「ratchet の原資が無い」を理由に着手不能と判断されかけた。[^platform]

[第Ⅰ部-5](pre-pmf-scope) の Pre-PMF、[第Ⅳ部-5](sixty-to-hundred) の class-lock と同じく、制約は書いた時点では完成せず、正しい作業を止めた事例から適用範囲が絞られていきます。

## 装置を減らす判断原則

装置を減らすとき、何を守っているかで扱いを決める判断原則が ADR-0007 にあります。

| # | 何を守るか | 扱い |
| --- | --- | --- |
| 1 | 証跡の真正性 / 不可逆な損失（偽装・成果物の消失・自己承認） | hard-fail で残す |
| 2 | 顧客に見える正しさ（XSS / LP の嘘 / 用語） | 残す。安ければ hard-fail、重ければ警告 |
| 3 | 書式・網羅性・手続きの整合 | 警告に降格、または撤去 |
| 4 | 参照ゼロ | 削除 |

> 「稼働中だが keep list に無い」は削除理由にならない。 keep list は hard-fail の一覧であって「守る価値のあるものの全集」ではない。削除の前に類型 1〜4 のどれかを明示する。[^adr07]

この原則は v2 で、v1 の誤りを訂正したものです。v1 は「消すか keep list に入れるかの二択」と書いていたため、稼働中で価値のある gate に対して消す以外の選択肢がなくなりました。実際に、最近 deploy した資産の削除を検知する gate（類型 1）と、LP の innerHTML を検査する gate（類型 2）が削除候補に載りました[^adr07]。

適用の実績で象徴的なのは、PR 本文を検査するスクリプトの分離です。1 本のスクリプトに類型 1 と類型 3 の検査が同居していたため、スクリプト単位で「類型 1」と扱われ、書式の検査 19 本が類型 1 の看板で hard-fail に残っていました。統合 PR が 60 の検査中 57 で成功しながら、書式の gate 2 本で 4 日間止まった実害の構造です。26 の検査を id 単位で分離し、hard-fail するのは明示列挙した 7 件だけ、列挙されていない検査は警告が既定、に変えました[^adr07]。新しい検査を hard-fail にすることを、明示的な意思決定にするためです。

## 実行されない gate

もう 1 つの象徴が、ローカルの検査 CLI `npm run pre-ready` です。ADR-0030 は 2026-05-01 に、git の hook で重い検査を自動実行するのではなく、開発者が明示的に 1 本叩く CLI を採用しました。Husky や lefthook は、commit のたびに重い検査が走ると体験が悪化すること、Pre-PMF で依存を増やしたくないこと、Windows と WSL の環境差が事故源になることを理由に退けています[^adr30]。

その CLI は、2026-07-30 に 20 ステップから 6 ステップに縮小されました。

> 根拠 (実測 2026-07-30): 全 step 通しで 1350s。19 step のうち 14 step は変更内容に関係なく無条件実行されており、Ready 化のたびに 20 分超を要していた。結果として実際には実行されないか、実行しても待ち時間の間に別の作業へ移り結果を確認しない運用になっていた = 「実行されない gate」であり、gate として機能していなかった。[^adr30]

22 分半かかる検査は、実行されません。実行されない gate は、gate として存在しないのと同じです。Ready の判定根拠は「CI の全 job が pass」に移し、ローカルの CLI は着手中に手元で早く落とすための道具として残しました。6 ステップは、安い順に走ります。PR 本文だけを見る検査、静的なテキスト検査、型検査、スクリーンショットの検査の順で、これを cheap-fail-first と呼んでいます[^clihelp]。

CLI のヘルプには、外した 14 の検査の行き先が書かれています。CI で hard-fail のまま走り続けるもの、別のワークフローに移ったもの、そして「検査ではなく案内を表示するだけだった」ため撤去したものです。外したうちの大半は、その後の「品質ゲート 80 点主義」の削減でスクリプトごと削除されました[^clihelp]。

## 4 階層の実行頻度

装置の設計で、ADR-0007 が最初に決めたのは実行頻度でした。静的解析のツールを 7 本並行して導入する Issue が起票されたとき、根本原因をこう診断しています。

> 「ツールを導入すれば品質が上がる」という発想のまま 7 本並べ、実行頻度 × blast radius の組合せを設計していない。CI 時間は無尽蔵ではないので、頻度設計こそが品質戦略である。[^adr07]

| 階層 | 実行頻度 | 判定ルール | 失敗時の扱い |
| --- | --- | --- | --- |
| T1 PR ゲート | 全 push / PR 毎 | 30 秒未満で、merge されたら致命的 | merge を止める |
| T2 PR 並行レーン | 全 PR、別 job | 30 秒〜3 分で、誤検知があっても merge 判断は人間 | merge を止める（override 可） |
| T3 nightly / 週次 | main に schedule | 3 分超、または広域の負債検知 | PR は止めない。finding は PR コメントか Accepted residual に記録 |
| T4 四半期 / 手動 | 四半期または手動 | 重い、外部 API のコスト | 同上 |

T3 と T4 の finding を Issue にする基準も、あとから絞られました。「顧客の金・データ・法務に接続する finding のみ」を Issue 化し、それ以外は記録して閉じます。旧来の「finding を Issue に自動起票」は装置起因の Issue を量産し、backlog の 10% が「同 class N 例目」を名乗る装置修理の Issue で占められました[^adr07]。

## 80 点で止める

この章の記録を通して見ると、装置の運用は 3 つの段階を経ています。第 1 段階は追加で、事故が起きるたびに検査が足されました。第 2 段階は設計で、頻度と類型で扱いを分け、実行されない gate を縮小しました。第 3 段階は凍結で、装置が製品を上回り顧客を止めた時点で、追加そのものを止めました。

憲章 §0 の判定基準を、もう一度引きます。「すべてのブロッカーを機械で入れることは不可能だと判断しました。機械的な打ち手は『その打ち手を守る打ち手』を呼び、無限ループになります。80 点を目標値とし、残り 20 点を詰めるための装置は持ちません。」

生成AIとの開発では、装置を足すことが安すぎます。AI は検査スクリプトを数分で書き、CI に組み込みます。だからこそ、装置の総数に上限を置き、減らす専任を置き、それでも増える圧力に対して「80 点で止める」と決める必要がありました。次の [第Ⅴ部-1](pre-ready) からは、この 80 点を構成する装置の実体を 1 つずつ見ていきます。
