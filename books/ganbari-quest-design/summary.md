一人の人間が、生成AIに実装を任せて、子供向けの商用サービスを 7 か月で作りました。本書はその設計と開発の記録です。この章だけで、本書が何を主張し、どこを読めば何が分かるかが伝わるように書きました。

## この本の筋

製品には「子供をアプリに滞在させない」という、ふつうと逆の方針があります。方針は設計を縛り、設計はインフラを縛ります。第Ⅰ部から第Ⅲ部は、その「何を作ったか」です。

本書の中心は「どう作ったか」です。生成AIは 60 点のものをすぐに出しますが、100 点に寄せる工程で修正が修正を呼びます。それを止めるために、一人の人間が 5 つの部署のセッションを立てました。作った者と認める者を分け、「完了しました」を検証に置き換え、同じ型の不具合を型ごと止めました。第Ⅳ部がその体制と判断で、第Ⅴ部はそれを機械に落とした検査、第Ⅵ部と第Ⅶ部は生成AIに渡す文脈とリポジトリの運用です。検査を増やしすぎて道具が製品より大きくなり、80 点で止めると決めるまでの経緯も含みます。第Ⅷ部は数字と失敗の記録と、導いた原則です。

## 何を作ったのか

がんばりクエストは、3〜18 歳の子供の「がんばり」を親子で記録する家庭向けのウェブアプリケーションです。歯みがきや宿題をタップで記録するとポイントがたまり、親が用意したごほうびと交換できます。SvelteKit と AWS CDK によるフルサーバレス構成で、月額 500 円から有料プランを提供しています。ソースコードは AGPL-3.0 で公開し、自宅の小型 PC でも動かせます。

製品の紹介は[第Ⅰ部-1](product) と [第Ⅰ部-2](anti-engagement) でほぼ終わります。本書の主題は製品ではなく、それを作った方法です。

## 何を学んだのか

本書の各部は、それぞれ 1 つの問いに答えます。

第Ⅰ部「プロダクト」は、製品の方針がなぜ設計を縛るのかを扱います。滞在時間を価値の毀損と数える原則（[第Ⅰ部-2](anti-engagement)）、年齢帯で機能を変えない判断（[第Ⅰ部-3](age-tiers)）、増殖した仕掛けを 3 層に削った経緯（[第Ⅰ部-4](point-economy)）、作らないことを決める基準とそれが悪用されたときの修正（[第Ⅰ部-5](pre-pmf-scope)）、子供のデータを扱う法務を画面と実装に落とす方法（[第Ⅰ部-6](legal-by-design)）です。

第Ⅱ部「アプリケーションアーキテクチャ」は、1 章 1 部品です。技術選定（[第Ⅱ部-1](stack-selection)）から始まり、層の構造、デザインの仕組み、データモデリング、家庭ごとのデータ分離、認証、テンプレート市場、生成AIによる提案、課金、ログ、バックアップ、通知、運営者の画面、画像アセットを扱います。第Ⅲ部「インフラ」は、実測の月額（[第Ⅲ部-1](serverless-cost)）から始まり、AWS CDK の構成、Lambda での動かし方、デプロイの前後の検査、監視、デモ、セルフホスト、紹介ページの配信を扱います。

第Ⅳ部「生成AI駆動開発プロセス」が、本書の中心です。前半は、一人の人間が 5 つの部署のセッションを立てる体制と決定権（[第Ⅳ部-1](one-human-many-sessions)）、部署の間の受け渡し（[第Ⅳ部-2](label-mailbox)）、作った者と認める者の分離（[第Ⅳ部-3](maker-not-approver)）、「完了しました」を信じない検証（[第Ⅳ部-4](definition-of-done)）です。後半は、同じ型の不具合を型ごと止める原則（[第Ⅳ部-5](sixty-to-hundred)）、並列化の使いどころ（[第Ⅳ部-6](parallel-agents)）、統合を第三者として判定する監査部（[第Ⅳ部-7](audit-team)）、検査の道具が製品より大きくなった話（[第Ⅳ部-8](platform-session)）です。第Ⅴ部「品質ゲートの機械化」は、その検査の実体です。

第Ⅵ部「ドキュメントとコンテキスト工学」は、生成AIに渡す文脈を「増やす」のではなく「保つ」運用です。第Ⅶ部「リポジトリと Git 戦略」は、生成物の置き場、ブランチの運用の変遷、機械が発行する統合プルリクエスト、自動処理の全体設計です。第Ⅷ部「数字と学び」は、期間と費用の実測（[第Ⅷ部-1](by-the-numbers)）、6 件の事故の記録（[第Ⅷ部-2](postmortems)）、原則の展開（[第Ⅷ部-3](principles)）、未解決と今後（[第Ⅷ部-4](whats-next)）です。

## 導いた原則

本書全体から導いた原則を先に置きます。各項目の根拠は、対応する章にあります。

1. 原則は書くだけでは守られない。自動検査が落とすか、テストが落とすか、構造上できないかのいずれかにする
2. 作った者と認める者を分ける。一人で開発していても、部署のセッションを分ければ分離できる
3. 「完了」は宣言ではなく検証で決める。確認項目が埋まっているかではなく、顧客に届いたかで判断する
4. 同じ型の不具合が 2 件出たら、個別の不具合ではなく型として扱い、3 件目を機械で止める
5. 判断基準には、基準が言い訳に転用されるパターンまで書く。生成AIは基準を都合よく読み替える
6. 設計書を実装の正本にする。書かれていない仕様は存在しない仕様として扱う
7. 文書は増やすより減らす。役目を終えた記録は削除し、履歴は git に任せる
8. 生成AIに渡す文脈は常時読ませない。必要なときに必要な文書だけを読ませる
9. 値が正しいことと、値が効いていることは別物である。両方をテストする
10. 製品の成功の定義を先に決める。がんばりクエストでは「使わなくなること」が成功である

これらは、うまくいった判断だけから導いたものではありません。[第Ⅷ部-2](postmortems) には、ライセンスキー方式の 23 回の修正、スクリーンショットの偽装を防ぐ検査、生成AIの稼働状況の誤検出、個人情報の平文のログ出力、本番だけで失敗するアップロードなど、本書の原則が生まれる前に起きた事故を並べます。

## 読み方

各章の冒頭にリポジトリへの導線を置き、設計の判断は該当箇所を引用して、脚注で設計判断の記録や設計書やテストコードを示します。脚注の出典は執筆時点のコミットに固定した GitHub の URL です。リポジトリは公開されているため、本書で触れた設計は、すべて実物で確かめられます。

登録なしで触れるデモもあります。製品の紹介は [第Ⅰ部-1](product) から始めてください。
