> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

AI がコードを直すとき、最も起きやすい事故は「片方だけ直す」です。アプリのラベルを直して LP を直さない、本番を直してデモを直さない、5 つの年齢モードのうち 1 つだけ直す。この章では、そうした並行実装を先に列挙した「並行実装マップ」と、どこに何があるかを 1 ファイルで俯瞰する codebase-map、そしてその 2 つが古びた箇所を扱います。

## 同期漏れの 4 件

並行実装マップは 2026-04-09 に作られ、72 回改版されて 707 行になりました。冒頭は「本プロジェクトには同じ概念を扱う並行実装が多数存在する」と宣言し、修正時に必ずこのマップを参照してすべてのペアを直すよう求めています[^parallel]。

契機は 4 つの Issue です。#531 は「ちゃんの」という suffix の修正が 5 つの年齢モードのディレクトリに横展開されなかった。#561 は LP の「ようちえんキッズ」が年齢区分の再設計で漏れた。#562 はデモの seed が再設計に追従せず矛盾した。#563 はデモガイドが Step 2 で止まった。原因はすべて「同じ概念を扱う実装が 2 か所以上にあり、片方だけ直した」です[^parallel]。

## 13 のペア

マップは、ペアを優先度で 3 段に分けます。最高は同期漏れが頻発する 3 つ。アプリと LP、年齢モードの 5 ディレクトリ、本番コードとデモ。高は定期的に漏れる 3 つ。デスクトップナビとモバイルナビ、本番ナビとデモナビ、本番チュートリアルとデモガイド。中はスキーマ変更時に注意する 7 つ。seed と migration、マーケットプレイスのプリセットと取込、設計書と実装、プラン機能リスト、年齢と誕生日、法的文書、メール通知系、そして「一度見せたら次から出さない」機構です[^parallel]。

各ペアには、ファイルのパス、同期の方向、検出の手段が書かれています。たとえば「アプリと LP」は、`labels.ts` を SSOT に `site/shared-labels.js` をスクリプトで生成する、と [第Ⅲ部-8](lp-delivery) で見た機構を指します。「本番とデモ」は、[第Ⅲ部-6](multi-lambda-demo) で見たとおりデモの専用ルートを全削除して並行実装を 0 にした結果、「新規 `src/routes/demo/` の追加は禁止」という不在の規則に変わりました。

末尾の「修正時チェックリスト」は 14 項目です。UI ラベルなら 5 か所、DB スキーマなら 3 か所、認証が絡む画面なら `npm run dev:cognito` で自分の目で通る、route の rename なら撮影スクリプトの 4 配列を同期する。最後の項目には実例が付いています。`/admin/settings` を分割した際に撮影スクリプトの URL を更新せず、19 連続で deploy が失敗した[^parallel]。

## 実在を検査する

マップが挙げるパスは、test が実在を検証します。ディレクトリは末尾に `/` を付けて書く。付け忘れると検査から漏れる。撤去済みで「新設禁止」を伝えるために名前を書く必要があるときは、`ASSERTED_ABSENT` に理由付きで登録し、不在であることを assert する側に回る[^parallel]。

これは [第Ⅴ部-4](fitness-functions) で見た「記録を反証可能にする」の、文書への適用です。並行実装マップは、撤去済みのファイルを同期先として指し続けると、AI がそのファイルを作ってしまいます。実在の検査は、マップが「存在しないものを直せ」と言わないことを保証します。

しかし、検査はパスにしか効きません。マップの「解消計画」の表は、Tier 3-I「年齢モード 5 種類を `[uiMode]` パラメータルートに集約」を「未着手（4,434 行の重複解消）」と書いています。ルートの CLAUDE.md は「routes は `src/routes/(child)/[uiMode=uiMode]/` にパラメータルートで統合済み（#664）」と書いています。同じリポジトリの 2 つの文書が、同じ作業を「未着手」と「済み」と言っています。チェックリストの「年齢モード → 5 ディレクトリ全て」も、統合前の文です。年齢帯 variant の項が参照する ADR-0015 は、#2898 で削除されています[^parallel]。

## codebase-map

codebase-map は 2026-05-18 に #2185 で作られ、22 回改版されて 16,794 バイトです。目的は「どこに何があるかを 1 ファイルで俯瞰する SSOT。Claude Code のセッション初期で参照すれば、目的地への最短経路が分かる」。トップレベルのディレクトリ 11 個、`src/` のサブディレクトリ 13 個、`docs/` の SSOT 文書 25 本、`infra/`、`tests/`、`site/`、npm スクリプト、`.claude/` の順です[^codebasemap]。

最後の節は「クイック動線」で、「やりたいこと」と「最初に見るファイル」の対応表です。新規 UI 画面を作るなら DESIGN.md から src/routes/CLAUDE.md へ、用語を変えるなら DESIGN.md §6 から terms.ts、認可ルールならセキュリティ設計書 §5 から `src/lib/policy/`。AI に「まずどこを読むか」を教える表で、CLAUDE.md の階層より 1 段具体的です[^codebasemap]。

更新の規則もあります。新規トップレベルディレクトリの追加時は 1 行追記、CLAUDE.md の追加時は link を追加、そして「4 半期ごとの retrospective」。「次回 retrospective 予定: 2026-08（本ファイル作成: 2026-05）」と書かれたまま、9 月になっています。`.claude/` の行は「Skills (13)」と書いていますが、[第Ⅵ部-6](skills-as-sop) で見るとおり skill は 26 あります。同じ節の別の行は「全件は `ls .claude/skills/` を SSOT とする、件数の数え上げはここに固定しない」と書いています。固定しないと決めた文の隣に、固定された数字が残っています[^codebasemap]。

## グラフと地図

[第Ⅵ部-4](graphify) で見た Graphify の評価は、codebase-map を比較対象にしていました。人手の SSOT ナビと grep が、`query` の BFS に勝った。採用後も「UI 層の探索は codebase-map と grep を主経路のままとする」です。

地図とグラフは、違うものを持ちます。グラフは import と call の関係を AST から自動で持ちます。地図は「同じ概念を扱う 2 か所」を持ちます。`labels.ts` と `site/index.html` の間に import は無く、グラフには辺がありません。両方を直す必要がある、と知っているのは人だけで、それを書いた場所が並行実装マップです。AI がコードから推測できない関係を、先に書いておく。それが地図の仕事でした。

## 今ならこうする

並行実装マップは、この本で見た文書の中で、AI にとって最も価値の高い 1 本です。コードから推測できない関係を持ち、実在を test が守り、修正時のチェックリストに実例が付いています。生成AIに既存のリポジトリを触らせるなら、最初に作るべき文書です。

腐ったのは「解消計画」と「件数」でした。計画は完了しても表が更新されず、件数は数えた日で止まります。実在を検査する test が守っているペアの一覧は腐らず、test が見ていない計画と件数だけが腐りました。「変わるもの」は文書に書かず、計画は Issue に、件数は `ls` に任せる。この線引きは、実在を検査する test と同じ発想です。

codebase-map の retrospective は、日付を書いた時点で腐り始めました。「次回 2026-08」は、8 月に誰かが読まなければ意味を持ちません。読む契機が無い日付より、[第Ⅵ部-3](adr-deletionism) の月 1 棚卸のように、mailbox に届く Issue の方がまだ動きます。それも 6 月で止まっていましたが。
