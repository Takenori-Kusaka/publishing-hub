---
title: "第Ⅳ部-2　受信箱としてのラベル ― 部署の間の受け渡しを GitHub に載せる"
---

> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

5 つの部署のセッションは、互いの存在を知りません。別の複製リポジトリで動くセッションに「次はあなたの番です」と伝えるには、何かの経路が要ります。生成AIどうしを直接つなげばよいのではないか。なぜ、いちばん地味な GitHub のラベルに落ち着いたのか。

生成AIのセッションは、実行中に割り込まれると仕事を取り落とします。だから「相手に届ける」通信ではなく、「相手が見に来る」掲示にしました。ラベルは掲示です。

## オーナーが 1 日 8 往復していた

仕組みができる前、部署の間の受け渡しはオーナーの手作業でした。企画部のセッションの発言を写して開発部に貼り、開発部の結果を写して品質保証部に貼る。2026 年 7 月には、これが 1 日 8 往復に達していました[^mailbox]。

手間だけなら我慢できます。困ったのは 2 つです。1 つは、決定がセッションの会話の中にしか残らないことでした。あるプルリクエストには「企画部の承認条件 3 件」と書かれていましたが、その出典が GitHub のどこにも無く、品質保証部が検証できませんでした。もう 1 つは、オーナーが席を外すと全部署が止まることでした。各セッションは自分の仕事を自分で拾えず、中継を待つだけでした。

設計の方針は「新しい通信基盤を作らない」でした。GitHub はすでに全員が読み書きする場所です。足りないのは「次に誰が動くか」の 1 情報だけなので、それをラベルにしました。本書では、この仕組みを **受信箱** と呼びます。各部署は、自分宛てのラベルが付いた Issue とプルリクエストの一覧を、自分の受信箱として見に行きます。

## 退けた 4 つの手段

ラベルより高機能な手段はいくつもありました。退けた順に書きます。

1 つ目は、Claude Code のセッションどうしの直接通信です。設計した 2026 年 7 月の時点で、その機能はありませんでした[^mailbox]。あったとしても、次の理由で採らなかったと思います。

2 つ目は、サブエージェントと Agent Teams です。1 つのセッションが子のセッションを起動して結果を受け取る仕組みで、[第Ⅳ部-6](parallel-agents) で扱います。これは 1 つの部署の内側を並列にする手段で、部署の間の受け渡しには使えません。子のセッションは親の作業ディレクトリと GitHub の認証を引き継ぎます。開発部の起動した子が品質保証部を名乗っても、[第Ⅳ部-3](maker-not-approver) の「作った者と認める者は別」は成り立ちません。加えて、子の結果は親にしか返らず、親が待っていなければ受け取れません。

3 つ目は、対話ツールでの呼びかけです。この開発は、チャンネルごとに生成AIのセッションが立つ対話環境の上で動いています。あるチャンネルで品質保証部を呼べば、そのセッションに届きます。問題は届き方でした。呼びかけは、相手が別の仕事をしている最中に割り込みます。生成AIのセッションは、割り込まれると実行中の文脈を上書きされ、元の仕事を取り落とすか、途中で放り出します。割り込みの往復が続くと、人の目や検証を挟まないまま「指摘、修正、再指摘」が回り続け、トークンだけが減ります[^concurrency]。

4 つ目は、Discord への通知です。GitHub のラベルの変更を Discord に流し、各セッションに届ける案です。採らなかったのは、3 つ目と同じ割り込みを別の経路で作るからです。見落としが実際に起きてから作る、と決めました[^mailbox]。

ラベルが残ったのは消去法だけではありません。ラベルには、他の手段に無い性質が 4 つあります。

- 消えない。決定は Issue やプルリクエストのコメントに残り、あとから検証できる。1 日 8 往復の中継で失われていたのは、まさにこれだった
- 割り込まない。受け手は、自分が手すきのときに自分の受信箱を見に行く。実行中の仕事は壊れない
- 人が中継しない。オーナーが不在でも、ラベルが付いていれば次の部署が拾う
- 壊れたことが見える。どの受信箱にも入っていない項目を、命令 1 本で列挙できる。対話ツールの呼びかけが誰にも読まれなかったことは、誰にも見えない

## ラベルは 9 種類

ラベルは 2 種類あり、混ぜると経路が塞がります。

宛先のラベルは 6 種で、「次に誰に用があるか」だけを表します。開発部宛て、品質保証部宛て、企画部宛て、監査部宛て、基盤部宛て、オーナー宛てです。用件は含みません。何の用かは Issue やプルリクエストのコメントに書きます。

工程のラベルは 3 種で、送り手の状態を表し、前提を含みます。「実装完了」は自動検査がすべて通り、レビュー待ちになっていること。「品質保証部が止めた」は差し戻し。「マージしてよい」は承認済みです[^mailbox]。

運用の原則は 5 つです[^mailbox]。

1. GitHub がすでに持っている仕組みにラベルを重ねない。承認の依頼は GitHub のレビュー依頼を使う
2. ラベルは状態であって指示ではない。「マージしてよい」が付いていても、自動検査が通っているかは自分で確かめる
3. 付けた側が意味に責任を持つ
4. 取り返しのつかない 4 つの操作だけはオーナーに上げる
5. 語彙を増やさない

2 番目には実例が添えられています。企画部がラベルだけを見てマージ可と判断し、品質保証部が自動検査の失敗を理由に拒んだ、というものです。ラベルは実測の代わりになりません。

各部署のセッションは、起動直後に「毎時、自分の受信箱を見る」定期実行を 1 本作ります。分はずらします。開発部は 13 分、品質保証部は 23 分、企画部は 37 分、基盤部は 43 分、監査部は 47 分です[^mailbox]。この定期実行はセッションの中にしか無く、Claude Code を閉じると消えます。つまり「オーナー不在の間に動く」ためではなく、「セッションが生きている間、自分の仕事を自分で拾う」ための仕組みです。

## 壊れた 1 回目: 経路が丸ごと無かった

ラベルの運用は 2 度壊れました。

**狙い。** 最初の語彙は工程に沿って作りました。実装が終われば「実装完了」、止まれば「品質保証部が止めた」、承認されれば「マージしてよい」。工程をラベルにすれば、次に誰が動くかは自明だ、という考えです。

**起きたこと。** 品質保証部宛てのラベルが「実装完了」しか無かったため、完成していないものを品質保証部に送れませんでした。相談や問い合わせもできません。同じ日、監査部宛てのラベルは「リリースの切り出しを渡した」に限られていて、問い合わせに使えないと分かりました。2 つの部署が同じ日に困るまで、誰も気づきませんでした[^mailbox]。

**なぜ。** ラベルに「宛先」と「用件」を同時に持たせていたからです。用件が工程と一致している間は動き、工程に無い用件が生まれた瞬間に経路が消えました。

**変えたこと。** 「宛先のラベルは用件を含まない」という原則を足し、用件でラベルを分けるのをやめました。用件はコメントに書きます。用件で分けると語彙が際限なく増えるからです。

**読者のリポジトリでは。** ラベルやタグに 2 つの意味を持たせているなら、片方の意味に無い場面が来たときに経路が消えます。意味は 1 つにし、もう 1 つは本文に書きます。

## 壊れた 2 回目: 帰り道が無かった

**狙い。** 受け取った側が対応したら、次の部署にラベルを付け替える。行きの経路があれば、帰りは自然に決まるはずでした。

**起きたこと。** 開発部が品質保証部の差し戻しに対応しても、ラベルは「品質保証部が止めた」のまま残り、品質保証部へ戻らずに止まりました。送り手は「戻ってこない」だけを見て、品質保証部は「答えたのに」と思う。問い合わせは往復なのに、往路しか定義していませんでした[^mailbox]。

**なぜ。** 工程のラベルは一方向に進むので、帰り道を考えなくても動きました。問い合わせは答えが返らないと終わらないのに、同じ感覚で設計していました。

**変えたこと。** どのラベルを受け取ったら、対応後にどのラベルへ移すかを、全組み合わせの表にしました。ここで 1 つ判断があります。同じ型の不具合が 2 回起きたのだから、[第Ⅳ部-5](sixty-to-hundred) の原則に従えば、ラベルの遷移を機械で検査するところです。しかし作りませんでした。運用の道具の不具合に検査を足すと「道具を守る道具」が生まれ、際限なく増えるからです。表という定義で塞ぎ、機械は足しませんでした[^mailbox]。前章の「80 点で止める」と同じ判断です。

**読者のリポジトリでは。** 受け渡しを設計するときは、往路と同じ数だけ復路を書きます。そして、運用の道具の不具合は道具で直さず、定義で直します。

## 誰の受信箱にも入っていない項目

受信箱の最大の失敗は「誰の受信箱にも入っていない項目」です。全員が「受信箱は空」と報告し、実際には複数件が止まっている状態と、本当に空の状態が区別できません。

2026 年 7 月 31 日、開発部と品質保証部がともに「対応事項なし」と報告した時点で、着手すべき Issue が 5 件滞留していました。全件に宛先のラベルが無かったため、どの受信箱にも現れなかったのです[^mailbox]。本書では、この状態を **宛先なし** と呼びます。

検出は命令 1 本です。宛先のラベルも、保留の印も、大きな計画の印も付いていない Issue とプルリクエストを列挙します。

```bash
# 宛先のラベルが 1 つも付いていない open の Issue / プルリクエスト
gh issue list --state open --limit 100 --json number,title,labels \
  --jq '.[]|select([.labels[].name]|map(select(startswith("state:") or .=="status:on-hold" or .=="epic"))|length==0)|"ORPHAN ISSUE #\(.number) \(.title)"'
gh pr list --state open --limit 50 --json number,title,labels \
  --jq '.[]|select([.labels[].name]|map(select(startswith("state:") or .=="status:on-hold" or .=="epic"))|length==0)|"ORPHAN PR #\(.number) \(.title)"'
```

保留と大きな計画を除くのは、除かないと着手予定の無い項目が毎回まとめて報告され、本当に浮いているものが埋もれるからです。初回の運用では 16 件が出ましたが、実際に配るべきだったのは 2 件でした[^mailbox]。

企画部にはもう 1 つの義務があります。「受信箱は空」が 3 回続いたら、経路が壊れていると疑って生存確認をすることです。受信箱が空であることは、仕事が無いことより、渡す経路が壊れていることの兆候である方が多い、と運用文書は書いています[^mailbox]。

## 経路の欠落をテストで検出する

1 回目の再発はテストで防いでいます。運用文書そのものをテストが読み、経路の表に空欄がないこと、語彙の表と本文が同じ 9 種を指していること、各部署の指示書が新しい語彙を反映していることを検査します。

```ts
// tests/unit/architecture/label-mailbox-routes.test.ts
/** 宛先 label 6 種 (§3.1)。ここを増減させたら本 test も一緒に直す。 */
const ADDRESS_LABELS = [
	'state:needs-dev',
	'state:needs-qm',
	'state:needs-po',
	'state:needs-audit',
	'state:needs-platform',
	'state:needs-owner',
];

/** 工程 label 3 種 (§3.1)。前提条件を含意する特殊形。 */
const STAGE_LABELS = ['state:dev-done', 'state:qm-blocked', 'state:ready-to-merge'];
```

テストの冒頭には、守るものと守らないものが書かれています。守るのは文書どうしのずれで、守らないのは GitHub 上にラベルが実在することです。テストから GitHub を呼ぶと、ネットワーク依存のテストになるからです[^routestest]。

運用文書をテストが読む、という形は奇妙に見えるかもしれません。しかしこのリポジトリでは、運用文書が正本であり、文書の整合性を機械で検査する例が随所にあります。

## 持ち帰るもの

- 生成AIのセッションへの受け渡しは、通信ではなく掲示にする。実行中の相手に割り込む経路は、仕事を取り落とさせる
- ラベルの意味は 1 つにする。宛先と用件を同じラベルに持たせると、用件に無い場面で経路が消える
- 「誰の受信箱にも無い」を検出する命令を用意し、受信箱が空でも安心しない

次の章では、部署を分けた最大の目的である「作った者と認める者を別にする」を、GitHub の上でどう強制したかを扱います。

[^mailbox]: 受信箱の運用文書。設計背景（1 日 8 往復の中継、決定がセッション上にしか無い問題）、設計原則、ラベルの語彙（宛先 6 種と工程 3 種）、遷移表と機械の検査を作らない理由、宛先なしの検出と 2026-07-31 の実例、定期実行の作り方、「受信箱が空」が 3 回続いたときの生存確認。出典: [docs/sessions/label-mailbox.md](https://github.com/Takenori-Kusaka/ganbari-quest/blob/3af6c2ed9fd4fe5766fc80c255656e940f8ec8f0/docs/sessions/label-mailbox.md)
