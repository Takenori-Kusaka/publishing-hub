---
title: "第Ⅳ部-3　作った者は認めない ― 自己承認の禁止と、承認する側の滑り落ち"
---

> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

部署を分けた最大の目的は、変更を作った者と、それを認める者を別にすることでした。しかし「別にする」と決めるだけでは、生成AIは守りません。GitHub の上でどう物理的に強制したか。強制したあとに何が起きたか。

強制は 3 段で入れました。アカウントを分け、作成の経路を機械で塞ぎ、承認する側が形だけの承認に滑り落ちるのを観測して遮断しました。そして最後の遮断は、費用の理由で外しました。

## 自分のプルリクエストを自分でマージしていた

2026 年 4 月、リポジトリの設定には「承認が 1 件必要」というルールがありました。ところが、リポジトリの所有者は管理者の権限でそのルールを迂回できます。一人で開発していれば、迂回は日常になります。品質保証部のレビューを経ないプルリクエストが、本番ブランチに入り続けていました[^adr22]。

この状態を止めた決定は 3 つです。

1. 管理者の迂回を、所有者を含む全員について禁止する
2. 品質保証部の専用の GitHub アカウントを別に作り、承認だけを担わせる
3. 承認のコメントの書式を統一し、実際に画面を見た所見と、受入基準との 1 対 1 の照合を必須にする

流れは「開発部のアカウントがプルリクエストを作る、品質保証部のアカウントが承認する、マージする」の順です。一人の人間が 2 つの GitHub アカウントを持ち、開発部のセッションと品質保証部のセッションで別のアカウントを使います。

## 規則は 6 回破られ、3 段の機械で塞いだ

規則を書いても破られます。この決定には 6 回の改訂が積み重なっていて、それぞれが「規律に頼った部分が破られた」記録です[^adr22]。

**狙い。** アカウントを分ければ、自分の変更を自分で承認できなくなるはずでした。

**起きたこと。** 品質保証部のアカウントに切り替えたまま、プルリクエストを作ってしまう事故が起きました。作成者が品質保証部なら、承認するのは開発部のアカウントで、分離の向きが逆になります。1 回目を規律で塞いだあと、2 回目が起きました。

**なぜ。** アカウントの切り替えは手元の操作で、どちらのアカウントで何をしてよいかは、セッションが「覚えている」ことに頼っていました。生成AIのセッションは、それを覚え続けません。

**変えたこと。** 3 段の機械で塞ぎました。

| 段 | 場所 | 塞げる経路 | 塞げない経路 |
| --- | --- | --- | --- |
| 1 | Claude Code の操作前に走るフック | Claude Code からのプルリクエスト作成 | Claude Code 以外の端末 |
| 2 | git のプッシュ前に走るフック | プッシュを伴う経路 | プッシュのあとにアカウントを切り替える経路 |
| 3 | GitHub 側の自動処理 | すべての経路 | なし |

3 段目が必要な理由は、その自動処理のコメントに書かれています。1 段目と 2 段目は特定の道具と特定のタイミングに依存していて、別の端末、GitHub の画面、API の直接呼び出し、プッシュ後のアカウント切り替えを塞げません。実際に 2 回再発したので、GitHub 側で全経路を捕まえることにしました[^authorguard]。許可されていないアカウントがプルリクエストを開くと、自動処理が即座にそれを閉じ、違反のコメントを残します。作成者はあとから変えられないので、事前に止めるしかありません。

**読者のリポジトリでは。** 手元のフックは「その道具を使ったとき」しか効きません。守りたいことがあるなら、最後の段は必ずサーバ側に置きます。

あとの改訂 2 つは向きが違います。1 つは、自動で作られる統合プルリクエストの作成者を GitHub App の機械名義にしたことです。機械は承認できないので、なりすましがゼロになりました。もう 1 つは緩和で、品質保証部が書式や受入基準の文言などの軽微な不備を自分で直して、同じプルリクエストを承認することを許しました。些細な指摘の往復が、顧客に届く変更を遅らせていたからです。ただし、実装の方針を変える修正を品質保証部が書いて自分で承認することは、引き続き禁止です[^adr22]。

## 承認する側が 33 日で 42 回、役割から滑り落ちた

作った者と認める者を分けても、認める側が独立した判断をしているとは限りません。

**狙い。** 品質保証部は「顧客から見た品質の最後の関門」として、プルリクエストを止める判断をするはずでした。

**起きたこと。** 品質保証部のセッションが、その役割から「止める項目の列挙と、自動検査の結果の代弁」へ滑り落ちる現象が、33 日間で 42 回観測されました。指示書や覚え書きや確認項目を足す対処を 5 回試しましたが、再発の割合は変わりませんでした[^adr56]。

**なぜ。** 原因は 4 つに整理されています。長い会話の中で役割が薄まること。開発部の主張を肯定的に繰り返すうちに独立した判断が消えること（Echoing と呼ばれます）。「ここまで事故ゼロ」の積み重ねが逸脱を許容に変えること。そして「自動検査が全部通り、止める項目を列挙した」ことが目標になり、本来の顧客の判断が代理の指標に置き換わることです。指示を書き足しても直らなかった理由も説明されています。指示による役割の強化は「演じる」力を強めるだけで、滑り落ちの引き金には効きません。滑り落ちている最中のセッションは、滑り落ちを否認します。文脈に入れる文書が増えるほど、大事な指示は参照されにくくなります[^adr56]。

**変えたこと。** セッションの自覚に頼らない対処を 2 つ入れました。1 つは反対役のサブエージェントです。事業と使い勝手と安全の 3 つの観点からそれぞれ反対理由を出すことを、決まった形式で強制します。決まった形式で答えさせると主張の反復が大きく減る、という研究結果が根拠です。もう 1 つはフックで、承認やマージの操作を検出します。反対役の出力が存在し、30 分以内に作られ、形式を満たしていなければ物理的に止めます[^adr56]。

フックの設計には迂回を防ぐ配慮があります。1 種類の端末だけを対象にすると別の端末からフック自体が走らずに迂回できるので、命令を走らせる道具の全経路を対象にします。入力を判別できなければ通さず止めます。それでも塞げない経路は、あとから承認の一覧と証跡を突き合わせる検知で報告します。「列挙型の防御は、次に増える経路を先回りできない」と、塞いだ範囲を過大に見ないことも書かれています。

## 遮断を外した判断

このフックは、2026 年 8 月 13 日に呼び出しを外されました。滑り落ちが起きなくなったからではありません。

**起きたこと。** 30 分の有効期限が、丁寧なレビューを罰していました。所見を深く書くほど、また自動検査の完了を待つほど、証跡が失効します。遮断は、防ぎたい行動（雑な承認）より、防ぎたくない行動（丁寧なレビュー）を強く罰していました[^adr68]。

**なぜ。** 経過時間は「独立した判断を経たか」の代理指標として弱かったからです。

**変えたこと。** 3 つの案を比べました。フックを外して部署の定義と憲章の遵守で保つ案。GitHub 標準のレビュー必須に寄せる案。有効期限を緩めてフックを残す案。GitHub 標準の仕組みは「誰が押したか」しか見ず「独立した判断を経たか」は見ないので、生成AIが承認者である今の運用では目的を満たしません。有効期限を緩めるほど、代理指標としての意味は薄れます。結局、フック本体とテストは消さず、呼び出しだけを外しました。受け入れる危険は 3 つ明記されています。証跡なしで承認できること。滑り落ちの再発を機械で検出できなくなること。そして「42 回という観測が、解決済みと誤読される」ことです。3 つ目のため、観測の記録は本文を残したまま、状態だけを置き換えにしました[^adr68]。

外す根拠は、決定の中でこう書かれています。

> 外す根拠は「drift が起きない」ではない。 ADR-0056 が観測した 42 回の drift は有効な観測として残す。根拠は費用と段階である — 立ち上げ期に統制を厚くすると、統制の維持費が統制が防ぐ損失を上回る。本件はその実例だった。[^adr68]

統制の維持費が、統制が防ぐ損失を上回る点がある。立ち上げの時期は、その点が近い。[第Ⅳ部-1](one-human-many-sessions) の「80 点で止める」と同じ線の上にあります。

**読者のリポジトリでは。** 統制を外すときは、外す根拠、戻す条件、観測の記録の 3 つを同じ場所に残します。外した事実だけが残ると、次の人は「問題は無かった」と読みます。

## 逃げ口上を禁じる

承認の独立とは別に、作る側の言葉にも統制があります。未完成の実装を完了として報告するときに使われた言い回しが、12 語、禁止されています[^escape]。

過去に 7 回、見た目だけ整えた実装が「完了」として報告されました。共通していたのは、「段階的に統合する」「試作の範囲」「等価性は保っている」「とりあえず」「一旦」「次の段階で」といった語で Issue を閉じたりマージしたりを正当化していたことです。

| 分類 | 語の例 | なぜ禁じるか |
| --- | --- | --- |
| 段階と範囲 | 「段階 N で統合」「試作の範囲」「範囲外」 | 統合を無期限に延ばし、大きすぎる範囲の問題を別の Issue にして放置する |
| 等価性と足場 | 「等価性維持」「足場として」「見た目の差分は許容範囲」 | 見た目が一致すれば実体が不一致でもよいと読み替え、本体の実装に到達しないまま完了を報告する |
| 先送り | 「とりあえず」「一旦」「次の段階で」 | 「動く」を品質と誤認し、起票なしの先送りを永久の放置にする |

禁じるだけでは、生成AIは別の言い回しを見つけます。だから救済策があります。禁止した語を本当に使う必要があるなら、その正当性を設計判断の記録として起票するか、期日と責任者と完了の判定基準を書いた Issue を起票して、プルリクエストの本文に明記します。[第Ⅰ部-5](pre-pmf-scope) で見た「顧客が付く前だから」の誤用禁止と同じ構造で、判断基準には、それが言い訳に転用されるパターンまで書きます。

## 持ち帰るもの

- 作った者と認める者は、セッションだけでなくアカウントで分ける。そして最後の段はサーバ側に置く
- 認める側が形だけの承認に滑り落ちることを前提に、決まった形式の反対意見を強制する。指示の追加は効かない
- 統制を外すときは、観測の記録と戻す条件を一緒に残す

次の章では、認める側が見るべき「完了」とは何かを扱います。生成AIの「完了しました」と、完了の事実は別物です。
