---
title: "第Ⅰ部-5　顧客が付く前の段階 ― 作らないことを決める 3 つの箱と課金への慎重さ"
---

> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

生成AIに実装を任せると、実装の費用がほぼゼロに見えます。すると「作れるものは作る」方向に判断が傾き、必要のない機能と過剰な防衛の設計が積み上がります。顧客がまだ付いていない製品で、何を作り、何を作らないと決めればよいのでしょうか。そして、その基準を生成AIが都合よく読み替えたとき、どう止めるのでしょうか。

既定を「作らない」に置き、作る側に顧客獲得への寄与を示す責任を負わせました。基準が言い訳に使われたときは、基準の適用範囲そのものを書き足しました。課金だけは例外で、慎重さを上げます。

本書では、製品が市場に受け入れられる前、つまり顧客がまだ付いていないこの段階を「顧客が付く前の段階」と呼びます。リポジトリでは `Pre-PMF` と書かれている判断基準の名前です。

## 一人と生成AIの体制で起きる 3 つの偏り

設計判断の記録は、企画部 1 人と生成AIの体制で発生する構造的な偏りを 3 つ挙げています[^adr10]。

1. 技術者への偏重。2026-04-11 時点の未完了の Issue を数えると、課金まわりが 61 件、管理画面が 25 件あった一方、成長・販促・利用開始に関するものは 0 件だった
2. 過剰な防衛の設計。ライセンスの記録台帳、運営者の操作の監査ログ、総当たり攻撃の検知、ウェブアプリケーションファイアウォール、ログの長期の分析基盤など、市場に受け入れられたあとなら妥当だが今は投資に見合わない設計が連鎖して提案された
3. 紹介ページの内容の不均衡。親の懸念を「書けば安心」と追加すると、かえって新しい不安を誘発する懸念が分かった

1 つ目の数字は象徴的です。課金まわりの Issue が 61 件ある一方で、顧客を獲得するための Issue は 0 件でした。生成AIは実装の相談には際限なく応じますが、「そもそも顧客が来ていない」という問題は Issue の形で現れません。記録はこの状況を、起票されなかった Issue と書かないことの価値は見えないため、プルリクエストの雛形やレビューや自動検査では検出できない、と分析し、起票の時点と設計の時点での機械的な確認が必要だと結論づけています[^adr10]。

## 3 つの箱

決定の中心は、Issue、紹介ページの内容、機能の実装のすべてに適用する 3 つの箱です。

| 箱 | 内容 | 例 |
| --- | --- | --- |
| 実装して訴求する | 顧客獲得への効果が明確で、紹介ページでの訴求も有効 | 自動スリープ、使用時間の可視化、年齢の移行への対応 |
| 紹介ページで訴求するだけ | 実装せずに紹介ページで安心感を提供できる | 撤退の費用の説明、サービス終了時のデータの扱いの説明 |
| 沈黙する | 紹介ページに載せると新しい不安を誘発する危険が便益を上回る、または今は要らない | 虚偽申告の検知アルゴリズム、汎用の監査ログ基盤、機械学習による検出 |

判断の軸は 3 つで、被害額、実装と保守の費用、紹介ページに載せることで新しい不安を誘発する危険です。既定は「沈黙する」で、上の 2 つの箱に上げるには明確な顧客獲得への効果の根拠が要ります[^adr10]。

「既定は沈黙」が要です。何かを作る、あるいは紹介ページに書くことを提案する側が、顧客獲得への寄与を示す責任を負います。2 つ目の箱の存在も特徴的で、「実装せずに紹介ページで安心感を提供できる」ものは実装しません。サービス終了時のデータの扱いは、機能ではなく約束として紹介ページに書けば足ります。

安全対策については、今の段階で採用するものと採用しないものを表にしています。署名の強度は HMAC-SHA256、要求の頻度の制限は AWS の API Gateway の標準の絞り、費用の監視は無料の AWS Budgets、実行時のログは CloudWatch Logs の 3 日保持。採用しないのは AWS WAF、Cost Explorer の定期的な取得、汎用の監査ログ基盤、接続元ごとのカウンターによる総当たり攻撃の検知です。それぞれには「市場に受け入れられたあとで再評価する契機」が書かれています。たとえば AWS WAF は、絞りの既定値を恒常的に超過したときが再評価の契機です[^adr10]。破棄すると決めた過剰な設計を新規に採用したい場合は、この記録を置き換える新しい記録を先に起票します。

Issue を起票するときの確認項目も定められています。どのペルソナのどの課題を解決するか。事業目標の文書（V2MOM）の施策に紐づくか。そして「この機能がなくても、顧客が付く前の段階の目標である申し込み 20 名/月に到達できるか」を自問し、到達できるなら優先度を中以下にします。根拠のない高優先度は、レビュー担当が降格します[^adr10]。

## 基準が言い訳に使われた

判断基準は、それ自体が言い訳の道具になります。

**狙い。** 「顧客が付く前の段階だから最小限で」という基準は、新規の過剰な機能追加と過剰な防衛の設計を退けるためのものでした。

**起きたこと。** 生成AIが「顧客が付く前の段階だから最小限」を、見せかけの実装や一時しのぎの対処、品質の作業の先送りの言い訳に繰り返し使いました。2026-07-17 に企画部が指摘しました[^adr10]。

**なぜ。** 基準は「何を退けるか」を書いていましたが、「何には適用しないか」を書いていませんでした。生成AIは「最小限で」という指示を、未完成のままでよいという意味に読み替えました。

**変えたこと。** 記録に「適用範囲と誤用の禁止」の節を足しました。この基準が適用されるのは新規の過剰な機能追加と過剰な防衛の設計を退けるときだけです。見せかけの実装や一時しのぎの対処を「顧客が付く前だから」で正当化することは、この基準ではなく単なる未完成であり技術的な負債です。「最小の実装」を選ぶ場合も「正しく完成した最小」が条件で、動くだけを許容する意味ではありません。既存の実装の整理や完成度の向上、品質の向上、移管の完遂を「顧客が付く前だから」で後回しにすることも禁じました。それらは常に正当な作業です[^adr10]。以後のレビューでは、この基準を根拠にした未完成を即座に却下できます。

**読者のリポジトリでは。** 生成AIに判断基準を渡すときは、基準の適用範囲と、基準が言い訳に転用されるパターンまで書いてください。「まだ作らない」と「雑に作る」は別物ですが、生成AIはその 2 つを同じ語で受け取ります。本書の後半で扱う「禁止された逃げ口上」の一覧は、この延長にあります。

## 課金への慎重さ

この段階の判断で例外的に扱われる領域が課金です。「作らない」方向の偏りが最も効かない領域でもあります。顧客がお金を払ったのに期待した結果を受け取れない、という事故は、顧客が付く前であっても許されません。

この製品の課金は一度、大きな設計の失敗を経験しています。当初はライセンスキー方式で有料機能を管理していましたが、この方式は 23 回の修正を重ねても安定せず、最終的に全廃されました。詳細は [第Ⅱ部-12](billing) と [第Ⅷ部-2](postmortems) で扱います。ここで確認したいのは、その失敗から生まれた決まりです。課金の領域では 1 領域 = 1 週間 = 1 つの調査 = 1 つのプルリクエストという歩幅を守り、複数の課金の変更を 1 つの作業にまとめません。「顧客が付く前だから」を理由に範囲を落とす提案は、そもそも選択肢として提示しません。

制限の設計にも、この慎重さが現れています。無料プランの制限は、機能の一覧として 1 つのファイルに集約されています[^planfeatures]。

```ts
// src/lib/domain/plan-features.ts
	free: [
		'お子さまの登録：2人まで',
		'プリセット活動の利用',
		'オリジナル活動の作成：3個まで',
		'レベル・ポイント・おみくじ・スタンプカード',
		'毎日のごほうび・続けるごほうび',
		'持ち物チェックリスト 3個/子まで（取込を含む）',
		`${PLAN_RETENTION_TERMS.free}間の履歴保持`,
		'メールサポート（標準）',
		`${REWARD_TERMS.productRegistration}は${PLAN_TERMS.standard}以上`,
	],
```

このファイルのコメントには、表記のずれが顧客にどう見えたかが残っています。紹介ページの料金表だけが「（取込を含む）」に直り、アプリ内の料金画面が旧文言のまま残った、という指摘が監査で出て、同じ機能が顧客には別物に見えていました。無料プランで「できないこと」のうち、貯めたポイントの使い道に直結する制限（ごほうびの商品登録は有料）は、検討の時点で見えている必要がある、というコメントもあります[^planfeatures]。

## プランで縛る画面の統一

有料機能に無料プランの利用者が触れたとき、画面はどう振る舞うべきか。この問いは 20 回以上、個別の画面ごとに違う答えで実装され、そのたびに指摘されました。画面の設計書は最終的に 5 つの方針で固定しています[^ui06]。

1. 制約の詳細（上限、各プランでできること）はプラン画面に集約する。機能の画面は「存在を示し、操作できない」に留め、画面内に残数のカウンターや個別の勧誘を置かない
2. 操作できない要素はタップで小さな説明を出し、利用不可の明示、対象のプラン名、プラン画面へのリンクを示す
3. 上位プランへの案内の導線はヘッダーに一本化する
4. 専用のプランのバッジは採用せず、汎用の錠前の印で代替する
5. 文言は 1 か所の定数を参照し、独自の文言を持たない

1 つ目の理由は、同じ制約を 1 つの画面で何度も認識させると認知の負荷が上がり、案内は無視されるようになるからです。4 つ目は、生成した専用のバッジに根拠がなく、[第Ⅰ部-2](anti-engagement) の原則と生成の費用に見合わないという判断です[^ui06]。実装の決まりとして、有料機能は必ず共通の `FeatureGate` 部品を経由し、`{#if planTier !== 'free'}` のような生の分岐を部品の中に書かないと定めています。画面側の制御は二重の防御であり、サーバ側でも別途 403 を返します[^ui06]。

## 「値が正しい」と「値が効いている」は別

課金の制限には、テストで守るべき性質が 2 つあります。どちらも、実際に起きた事故から生まれました。

**狙い。** プランごとの制限を 1 つの関数が返し、その値でアプリの各所が機能を制限する構成でした。

**起きたこと。** 有料の根拠として売っている機能の切り替え旗が、誰にも参照されていませんでした。旗は値としては正しく、既存のテストも関数が正しい真偽値を返すことを確かめていましたが、その値によって何かが制限されることは 1 本も検証していませんでした。同じ事故が 2 件出ました[^planlimits]。

**なぜ。** 値の正しさと、値が効いていることは別物だからです。テストは前者だけを見ていました。

**変えたこと。** 2 件目が出た時点で個別の不具合ではなく同じ型の不具合と見なし、3 件目を機械で止めました。対策のテストは、プランの制限を表す型の全項目が本番のコードから実際に読まれていることを検査します。定義だけあって参照されない旗があれば落ちます[^planlimits]。

2 つ目の事故は、プランの可否判定が 2 か所にあったことです。認可の方針の層に、招待の可否を「`family` プラン以外は拒否」と定義した箇所があり、これは制限を管理するサービス（スタンダードは 4 人まで招待可）と正反対でした。配線されていなかったため誰も困っていませんでしたが、1 行足した瞬間にスタンダードの契約者の招待が 403 になる状態でした[^capabilities]。対策のテストは、プラン別の可否判定を 1 つのサービスだけが持ち、方針の層にプランの条件を書き足せないことを保ちます。

**読者のリポジトリでは。** 有料機能の旗があるなら、旗を読んでいる場所を数えてください。0 か所なら、その旗は顧客に何も売っていません。

どちらも「2 件目が出たら個別の不具合ではなく型として扱い、3 件目を機械で止める」という考え方で作られています。本書の後半で繰り返し出てくる決まりで、[第Ⅳ部-5](sixty-to-hundred) で体系的に扱います。

## 判断基準を書くということ

この記録は、機能を作るかどうかの基準です。しかし読み返すと、本当の役割は「生成AIとの開発で、誰が何の責任を負うか」を決めることだと分かります。作る提案をする側が顧客獲得への寄与を示す。基準を言い訳に使うことを禁じる。課金の領域では慎重さを例外的に上げる。制限が効いていることを機械で確認する。判断基準は、書いた時点では完成しません。誤用されるたびに、適用範囲を明示する節が足されていきます。

## 持ち帰るもの

- 既定を「作らない」に置き、作る側に顧客への寄与を示す責任を負わせる。「書けば安心」も同じ審査にかける
- 判断基準には、適用範囲と、言い訳に転用されるパターンまで書く。生成AIは基準を都合よく読み替える
- 有料機能の制限は、値が正しいことではなく、値が効いていることをテストする
