---

> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

生成AIに実装を任せると、実装のコストがほぼゼロに見えます。すると「作れるものは作る」方向に判断が傾き、必要のない機能と過剰な防衛設計が積み上がります。がんばりクエストでは、この傾きを止めるための判断基準を ADR-0010 として明文化しました[^adr10]。この章では、その基準と、基準そのものが悪用されたときの修正、そして課金まわりの慎重さを扱います。

## 一人 + AI の体制で起きる 3 つのバイアス

ADR-0010 のコンテキスト節は、PO 1 人と AI エージェントの体制で発生する構造的なバイアスを 3 つ挙げています。

> 1. エンジニア偏重 — 2026-04-11 時点 open issue 集計で `area:billing=61`, `area:admin=25`、growth / marketing / activation = 0
> 2. 過剰防衛設計 — `license_event` / `ops_audit_log` / ブルート検知 / WAF / S3+Athena 等、PMF 後なら妥当だが Pre-PMF では ROI が見合わない設計が連鎖提案
> 3. LP コンテンツの不均衡 — 親の懸念項目を「書けば安心」と追加すると、かえって新規不安を誘発する懸念が判明[^adr10]

1 つ目の数字は象徴的です。課金まわりの Issue が 61 件ある一方で、顧客を獲得するための Issue は 0 件でした。AI は実装の相談には際限なく応じますが、「そもそも顧客が来ていない」という問題は Issue の形で現れません。ADR はこの状況を「『起票されなかった issue』『書かないことの価値』が可視化されないため、PR テンプレ・レビュー・CI では検出不可能」と分析し、起票時点と設計時点での機械的なチェックが必要だと結論づけています[^adr10]。

## 3 バケット判断基準

決定の中心は、Issue、LP の内容、機能の実装のすべてに適用する 3 つのバケットです。

| バケット | 内容 | 例 |
| --- | --- | --- |
| A: 実装 + 訴求 | 顧客獲得インパクトが明確で、LP 訴求も有効 | 自動スリープ、使用時間の可視化、年齢移行対応 |
| B: LP 訴求のみ | 実装せずに LP で安心感を提供できる | 撤退コスト説明、サービス終了時データ扱い説明 |
| C: 沈黙 | LP 掲載で新規不安誘発リスクが便益を上回る / YAGNI 該当 | 虚偽申告検知アルゴリズム、汎用監査ログ基盤、ML 検出 |

> 判断軸は 3 軸: 被害額 × 実装保守コスト × LP 掲載による新規不安誘発リスク。デフォルトは 沈黙（C）。A / B に上げるには明確な顧客獲得インパクトの根拠を要する。[^adr10]

「デフォルトは沈黙」が要です。何かを作る、あるいは LP に書くことを提案する側が、顧客獲得への寄与を示す責任を負います。バケット B の存在も特徴的で、「実装せずに LP で安心感を提供できる」ものは実装しません。サービス終了時のデータの扱いは、機能ではなく約束として LP に書けば足ります。

セキュリティについては、Pre-PMF で採用するものと採用しないものを表にしています。鍵の強度は HMAC-SHA256、レート制限は API Gateway の標準スロットリング、コスト監視は無料の AWS Budgets、ランタイムログは CloudWatch Logs の 3 日保持。採用しないのは AWS WAF、Cost Explorer API の定期ポーリング、汎用監査ログ基盤、IP カウンターによるブルートフォース検知です。それぞれに「PMF 後に再評価するトリガ」が書かれており、たとえば WAF はスロットリングの既定値を恒常的に超過したときに再評価します[^adr10]。破棄すると決めた過剰設計を新規に採用したい場合は、この ADR を supersede する新しい ADR を先に起票します。

Issue を起票するときのチェックリストも定められています。どのペルソナのどの課題を解決するか、V2MOM の Method に紐づくか、そして「この機能がなくても Pre-PMF のサインアップ 20 名/月に到達できるか」を自問し、到達できるなら優先度を中以下にします。根拠のない高優先度は、レビュアーが降格します[^adr10]。

## 基準が悪用されたとき

判断基準は、それ自体が言い訳の道具になります。ADR-0010 には 2026-07-17 に追記された「適用範囲と誤用禁止」の節があり、その背景はこう書かれています。

> AI エージェントが「Pre-PMF 最小」を、はりぼて実装・一時対処・品質作業の deferral の言い訳に繰り返し誤用した（2026-07-17 PO 指摘）。本 §0 はその誤用を構造的に止めるための scope guard。[^adr10]

追記された節は、Pre-PMF の判断が「新規の過剰な機能追加・過剰防衛設計を退ける」ためだけに適用されることを明示し、禁止する誤用を列挙しています。

> - はりぼて実装 / 一時的な対処 (band-aid) を「Pre-PMF だから」で正当化する — これは Pre-PMF ではなく単なる未完成・技術的負債であり、ADR-0061（band-aid サイクル打破）違反。「最小実装」を選ぶ場合も "正しく完成した最小" が条件であり、はりぼて / 未完成 / 動くだけを許容する意味ではない。
> - 既存実装の refactoring / 完成度向上 / 品質向上 / 移管の完遂 を「Pre-PMF だから」で妨げる・後回しにする — これらは Pre-PMF の対象外であり、常に正当な作業。[^adr10]

「まだ作らない」と「雑に作る」は別物です。AI は「Pre-PMF なので最小限で」という指示を、未完成のままでよいという意味に読み替えました。この読み替えを禁じる一節を ADR に足した結果、以後のレビューでは「Pre-PMF」という語を根拠にした未完成を即座に却下できます。生成AIとの開発で判断基準を書くときは、基準の適用範囲と、基準が言い訳に転用されるパターンまで書く必要があります。本書の後半で扱う「禁止された逃げ口上」の一覧は、この延長にあります。

## 課金への慎重さ

Pre-PMF の判断で例外的に扱われる領域が課金です。「作らない」方向のバイアスが最も効かない領域でもあります。顧客がお金を払ったのに期待した結果を受け取れない、という事故は、Pre-PMF であっても許されません。

この製品の課金は一度、大きな設計の失敗を経験しています。当初はライセンスキー方式で有料機能を管理していましたが、この方式は 23 回の修正を重ねても安定せず、最終的に全廃されました。詳細はアーキテクチャ編の課金の章と、数字と学び編の postmortem で扱います。ここで確認したいのは、その失敗から生まれた規律です。課金の領域では 1 領域 = 1 週間 = 1 つの調査 = 1 つのプルリクエストという歩幅を守り、複数の課金変更を 1 つの作業にまとめません。「Pre-PMF だから」を理由にスコープを落とす提案は、そもそも選択肢として提示しません。

制限の設計にも、この慎重さが現れています。無料プランの制限は、機能の一覧として 1 つのファイルに集約されています[^planfeatures]。

```ts
// src/lib/domain/plan-features.ts
	free: [
		'お子さまの登録：2人まで',
		'プリセット活動の利用',
		'オリジナル活動の作成：3個まで',
		'レベル・ポイント・おみくじ・スタンプカード',
		'毎日のごほうび・続けるごほうび',
		'持ち物チェックリスト 3個/子まで（取込を含む）',
		`${PLAN_RETENTION_TERMS.free}間の履歴保持`,
		'メールサポート（標準）',
		`${REWARD_TERMS.productRegistration}は${PLAN_TERMS.standard}以上`,
	],
```

このファイルのコメントには、表記のずれが顧客にどう見えたかが残っています。LP の料金表だけが「（取込を含む）」に直り、アプリ内の料金画面が旧文言のまま残った、という指摘が監査で出て、同じ機能が顧客には別物に見えていました。無料プランで「できないこと」のうち、貯めたポイントの使い道に直結する制限（ごほうびの商品登録は有料）は、検討の時点で見えている必要がある、というコメントもあります[^planfeatures]。

## プランで縛る UI の統一

有料機能に無料プランの利用者が触れたとき、画面はどう振る舞うべきか。この問いは 20 回以上、個別の画面ごとに違う答えで実装され、そのたびに指摘されました。UI 設計書は最終的に 5 つの方針で固定しています[^ui06]。

- P1: 制約の詳細（上限、各プランでできること）はプラン画面に集約する。機能画面は「存在を示し、操作できない」に留め、画面内に残数のカウンターや個別のアップセルを置かない
- P2: 操作できない要素はタップで小さな説明を出し、利用不可の明示、対象プラン名、プラン画面へのリンクを示す
- P3: アップグレードの導線はヘッダーに一本化する
- P4: 専用のプランバッジは採用せず、汎用のロックマークで代替する
- P5: 文言は 1 か所の定数を参照し、独自の文言を持たない

P1 の理由は、同じ制約を 1 つの画面で何度も認識させると認知負荷が上がり、バナーは無視されるようになるからです。P4 は、生成した専用バッジに根拠がなく、前々章の anti-engagement 原則と生成コストに見合わないという判断です[^ui06]。実装のルールとして、有料機能は必ず共通の `FeatureGate` コンポーネントを経由し、`{#if planTier !== 'free'}` のような生の分岐をコンポーネント内に書かないと定めています。フロントの制御は二重防御であり、サーバ側でも別途 403 を返します[^ui06]。

## 「値が正しい」と「値が効いている」は別

課金の制限には、テストで守るべき性質が 2 つあります。どちらも、実際に起きた事故から生まれました。

1 つ目は、有料の根拠として売っている機能フラグが、誰にも参照されていなかった事故です。

> フラグは値としては正しく、既存 test も `getPlanLimits()` が正しい真偽値を返すことを assert していた。しかしその値によって何かが制限されることは 1 本も検証していなかった。 値の正しさと、値が効いていることは別物である。
> 2 件目が出た時点でこれは個別バグではなく class なので、3 件目を機械で止める。[^planlimits]

対策のテストは、プランの制限を表す型の全フィールドが本番コードから実際に読まれていることを検査します。定義だけあって参照されないフラグがあれば落ちます。

2 つ目は、プランの可否判定が 2 か所にあった事故です。認可ポリシーの層に、招待の可否を「family プラン以外は拒否」と定義した箇所があり、これは制限を管理するサービス（スタンダードは 4 人まで招待可）と正反対でした。未配線だったため誰も困っていませんでしたが、1 行足した瞬間にスタンダード契約者の招待が 403 になる状態でした[^capabilities]。対策のテストは、プラン別の可否判定を 1 つのサービスだけが持ち、ポリシー層にプラン条件を書き足せないことを保ちます。

どちらも「2 件目が出たら個別のバグではなく class として扱い、3 件目を機械で止める」という考え方で作られています。これは本書の後半で繰り返し出てくる規律で、品質ゲート編で体系的に扱います。

## 判断基準を書くということ

ADR-0010 は、機能を作るかどうかの基準です。しかし読み返すと、この ADR の本当の役割は「AI との開発で、誰が何の責任を負うか」を決めることだと分かります。作る提案をする側が顧客獲得への寄与を示す。基準を言い訳に使うことを禁じる。課金の領域では慎重さを例外的に上げる。制限が効いていることを機械で確認する。判断基準は、書いた時点では完成しません。悪用されるたびに、適用範囲を明示する節が足されていきます。
