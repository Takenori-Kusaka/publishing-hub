> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

通知は、滞在時間を伸ばす最も安い道具です。生成AIに通知の機能を書かせると、送る理由は無限に出てきます。達成した、続いている、途切れそうだ、しばらく来ていない。どこで止めればよいのでしょうか。そして、通知を送る先の URL を利用者のブラウザから受け取る以上、その URL が攻撃の入口となることを防ぐには、何を確かめればよいのでしょうか。

上限を先に数字で決めます。1 家族 1 日 3 通、夜 9 時から朝 7 時は送らない、子供の端末には永久に送らない、親宛の案内のメールは年 6 回まで。送り先の URL は、受け取るときと送るときの 2 か所において、同じ関数で検証します。

## どう届くか

サーバレスの構成には、常駐する処理がありません。それでも通知は送れます。

Web Push は、ブラウザごとの配信サービス（Chrome なら Google の FCM、Firefox なら Mozilla のサービス）へ HTTP で送る仕組みです。アプリは `web-push` という部品で、環境変数に配った VAPID（配信サービス向けの署名鍵の規格）の鍵で署名した要求を、購読時に保存した URL へ送ります。Amazon SNS や Pinpoint のような AWS の通知サービスは、送信には使いません。受け取る側はブラウザの中の Service Worker で、ブラウザが閉じていても OS の通知として出ます[^notifservice]。

送る契機は 2 つあります。達成の通知（レベルアップ、実績）は、活動を記録したリクエストを処理している Lambda の中で、記録と同じ処理の流れから送ります。その時点で Lambda は起動済みなので、コールドスタートは関係ありません。リマインダーと連続記録の警告は時刻で決まるので、[第Ⅲ部-3](lambda-sveltekit) で見た定期実行の経路を通ります。EventBridge が 15 分ごとに振り分け役の Lambda を起こし、振り分け役が配信の受け口を呼び、SvelteKit の Lambda が送る対象を選んで送ります。この Lambda が眠っていれば起動して送るので、遅れは数秒で、送られないことはありません。

弱点はコールドスタートではなく別のところにあります。リマインダーの粒度が 15 分であること、1 回の定期実行の処理の予算が 30 秒であること、そして定期実行が届いていなければ何も送られないことです。最後のものは実際に起きました。[第Ⅴ部-4](fitness-functions) で見たとおり、定期実行は 4 か月間 401 で失敗し続け、その間リマインダーは 1 通も送られていません。

## 上限を先に決める

通知の設定は、リマインダー、連続記録の警告、達成の通知の 3 種類と、送らない時間帯です。定数はドメイン層に置かれ、1 日の上限は 3 通、送らない時間帯の既定は 21:00 から 07:00 で、開始が終了より遅い日付またぎを許します[^notifconst]。ローカルモードではログを出すだけで送りません[^notifservice]。

配信は 15 分ごとの定期実行が担います。週次のメールの報告、リマインダー、連続記録の警告の 3 つの配信をまとめて送り、送信済みの印で重複を防ぎます。15 分間隔なのは、リマインダーの時刻が任意の時と分だからで、毎時だと最大 59 分遅れます。判定用の設定は鍵ごとに 1 つの問い合わせにまとめ、実行の頻度を上げても問い合わせの数は家族の数に比例しません[^awsdesign]。

親宛の案内のメール（期限切れ前の知らせ、休眠からの復帰）は、年 6 回の上限と配信停止のヘッダーを構造的に保証します。知らせは 30 日、7 日、1 日前の 3 回、休眠は最後のログインから 90 日です。体験期間の通知は「システム通知」として上限の枠外です[^lifecycle]。

## 子供に送らない

子供の端末への直接の案内は、永久に禁止です。米国の子供のプライバシー保護法（COPPA）の改正と、[第Ⅰ部-2](anti-engagement) の原則の二重の規制です。設計は 2 層で、購読の API は役割が子供なら 403 を返し、送信時にも購読者の役割が親かオーナーでない購読を飛ばして警告を出します。型の定義に子供は含まれず、既定は親です[^security]。

## 送り先の URL が攻撃の入口になる

通知の送信は、保存された購読の URL へ要求を送ります。購読の API が受け取った URL を、方式や接続先の検証なしで保存すると、内部の接続先（クラウドの内部アドレス、自分自身、私設のアドレス）を指定した攻撃者経由で、サーバに内部への要求を出させる攻撃（SSRF）が成立しえます[^security]。

保存前の検証は 4 つです。`https:` のみ。既知の配信サービスの接続先の許可一覧（FCM は完全一致、Mozilla、Apple、Windows は末尾一致）。URL は 2,048 文字まで。鍵は base64 の文字種と長さの上限。末尾一致は区切りのドットを含めるので、`fcm.googleapis.com.attacker.com` のように正規の接続先の名前を頭に付けた偽装は弾かれます。保存は受け取ったままではなく、ブラウザの標準の URL の解釈で正規化した形です。「検証は標準の解釈、送信は `web-push` の古い解釈」という解釈の差を、保存の時点で無くします[^security]。

送る側でも再検証します。過去の記録、保存層への直接の追加、将来の一括取り込みで許可一覧の外の URL が入った場合、実際に要求を出す送る側が攻撃の実際の出口になるからです。購読と送信で同じ検証の関数を共有し、二重に実装しません。飛ばした URL のうち、確定的に不正なもの（`https:` でない、私設や自分自身のアドレス）だけを削除し、許可一覧の漏れ（`https:` で未知だが公開の事業者らしいもの）は削除せず、飛ばして警告するに留めます。許可一覧は「動く標的」で、事業者が配信の接続先を新設した正規の購読を一律に削除すると、永久に失われるからです[^security]。

有効な購読が 0 件で送信全体を飛ばす場合も、通知のログに失敗と理由を記録します。早期の戻りがログを通らないと、通知が黙って全部消えたことを運用が追えません[^security]。

## Service Worker とオフライン

Service Worker は、ビルドの生成物と静的ファイルと事前に描画したページを、事前にキャッシュします。除外は `/uploads/` と `/sounds/` で、`/tenants/` のログイン済みの利用者のデータもキャッシュに載せません。オフライン時の画面遷移の着地先は `/offline` で、事前に描画されているのでキャッシュに載ります。経路は定数にし、キャッシュの対象、代替の着地先、テストが同じ 1 か所を参照します。経路がずれると「キャッシュしていないページへ代替する」形で無効になるからです[^sw]。

通知の受け取りにも Service Worker が要ります。再通知の指定は Notification API の正式な選択肢ですが、TypeScript のブラウザ向けの型には無く、Service Worker 向けの型だけが持つため、型を明示しています。細かい話ですが、生成AIが書くと型の誤りを黙らせる方向に倒れやすい箇所です[^sw]。

## ホーム画面に追加

がんばりクエストは、App Store と Google Play のどちらにも出していません。ホーム画面に追加できるウェブアプリ（PWA）として配ります。計画書と価格の設計書には、理由が費用で書かれています。Apple の開発者登録は年 99 ドル、Google Play は 25 ドルで、どちらも予算の外に置き、ストアへの展開は収益化のあとに回す。ウェブ版を PWA として提供すればストアを経由しなくてよく、ストアへの展開はリーチを広げる目的であって収益を最大化する手段ではない、という判断です[^roadmap][^pricingdoc]。私の判断はもう 1 つあります。登録の費用より、審査と更新を維持し続ける手間の方が重く、それに見合うだけの宣伝の効果がストアにあるとは考えませんでした。

「ホーム画面に追加」の案内は、判定を画面の部品から切り出した純粋な関数です。理由は、判定（どの環境で何を出すか、一度閉じたら二度と出さない）が実害に直結するからです。[第Ⅰ部-2](anti-engagement) の要求「閉じたら二度と出さない」を部品の中の暗黙の分岐に埋めると、回帰を検出できません[^pwainstall]。

閉じた記録はブラウザの端末内の保存です。端末ごとの判断なので、サーバ側の家族の設定にしてはいけません。同じ家庭でも「親のスマホには追加したが、リビングのタブレットにはまだ」が普通に起きます。iOS の Safari は追加を促す合図（`beforeinstallprompt`）を実装しておらず、プログラムから追加のダイアログを出す手段が無いため、iOS だけは手順書を見せます。ブラウザの名乗りで判定することは本来避けたいのですが、機能の検出で代替できないため、ここでの分岐だけは名乗りで行います[^pwainstall]。

## メールの受信

SES は送信だけでなく受信も持ちます。サポート宛のメールは受信の規則で S3 に置かれ、Lambda が Discord に転送します。不達と苦情の知らせは、通知の送信には使わなかった Amazon SNS（AWS の通知配信の仕組み）のトピックで受けます[^sesstack]。

## 効いたか

通知の上限を先に決めたことは、この製品で最も一貫した判断でした。1 日 3 通、夜間は送らない、子供には送らない、年 6 回。数字は変えられますが、上限の無い状態には戻せません。上限は、送らない理由を数字で固定します。

送り先の URL の防御は、購読の側だけでは足りませんでした。送る側の再検証、確定した不正だけを削除する保守的な掃除、0 件で飛ばしたときの証跡まで積み上がりました。許可一覧を「動く標的」と認めて削除を控える判断は、正しさより顧客の購読を守る判断です。

オフラインの着地先を定数にした規律は、小さな例です。「同じ値を 2 か所に書かない」は、[第Ⅱ部-3](design-system) から繰り返し見てきた形です。

## 持ち帰るもの

- 通知の上限を、機能を書く前に数字で決める。送る理由は後からいくらでも増える
- 利用者から受け取った URL へ要求を出すなら、受け取るときと出すときの 2 か所において、同じ関数で検証する
- 「二度と出さない」のような約束は、画面の部品から純粋な関数に切り出し、テストで固定する
