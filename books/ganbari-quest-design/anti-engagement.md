title: "第Ⅰ部-2　滞在時間を価値毀損と数える ― 子供を留めない原則と「卒業」"
---

> リポジトリ: [Takenori-Kusaka/ganbari-quest](https://github.com/Takenori-Kusaka/ganbari-quest)

子供向けのアプリの多くは、毎日開いて長く使われることを成功と数えます。ところが、がんばりクエストにお金を払うのは親で、親が望むのは子供が歯みがきや宿題を自分からすることです。アプリを長く使わせる設計と、親が払う理由は両立するのでしょうか。両立しないなら、滞在時間を延ばさないアプリをどう設計し、どう守らせるのでしょうか。

両立しません。がんばりクエストは滞在時間を価値の毀損と数え、「記録して数秒で閉じる」を最短の動線に置きました。原則は文書に書くだけでなく、自動検査と単体テストと画面の構造で守らせています。

## 通常のアプリと逆の指標

子供向けアプリ、ソーシャルゲーム、動画サービスの多くは、日ごとの利用者数と滞在時間の積を指標にした設計を共有しています。無作為の報酬を引き続けられる画面、無限に続くスクロール、通知による呼び戻し、動画の自動再生などがその道具です。設計判断の記録は、この設計哲学は子供が「アプリと現実の活動のどちらに時間を使うか」の取り合いで現実の活動を減らす方向に働き、親が購入を判断する製品では親の購入動機と反する、と整理しています[^adr12]。

がんばりクエストの購入者は親で、利用者は子供です。親がこの製品に払う理由は「子供が歯みがきや宿題や手伝いを自分からするようになること」であって、「子供がアプリを長く使うこと」ではありません。むしろアプリの中で過ごす時間は、親が増やしたい現実の活動時間を削ります。ここから、決定の第 1 項が置かれました。子供側の画面は「記録する → 数秒で閉じる」を最短経路として設計し、セッションの長さを延ばす動機の設計は採用しない[^adr12]。

指標の設計方針も明文化されています。家族内の日ごとの起動率は追い、セッションの長さは追わず、むしろ短くなる方向を善とします。現実の活動の記録数とチェックリストの達成率はアプリの外の時間の産物なので追います[^adr12]。親の管理画面は情報の把握が目的なので、この制約の対象外です。

## 文言が実装を裏切った

**狙い。** この原則は、最初から明文化されていたわけではありません。作った人間の頭の中にはあり、実装はそれに沿っていました。

**起きたこと。** 紹介ページに「シールガチャ」という文言が混入したまま、実装は 1 日 1 回に制限されたおみくじだった、という食い違いが見つかりました[^adr12]。「毎日引ける」を暗示する販促の文言が、「1 日 1 回、数秒で終わる」実装を裏切っていました。

**なぜ。** 原則が文書に無かったため、販促の文言を書く時点で審査する基準がありませんでした。実装が正しくても、文言が別の製品を売っていました。

**変えたこと。** この事故は 2 つの設計判断の記録を生みました。1 つは本章の原則を定めた記録で、哲学の水準の判断を永続化し、将来の機能追加や販促文言の提案を即座に審査できる状態を作りました。もう 1 つは「紹介ページの文言は実装の事実から作る」という記録で、[第Ⅲ部-8](lp-delivery) で扱います。

**読者のリポジトリでは。** 製品の哲学を、機能の一覧ではなく「何を採用しないか」の形で 1 枚に書いてください。採用しないものの一覧は、提案を審査するときに最も速く効きます。

## 禁止と許容の境界

原則だけでは、個々の機能の境界が曖昧になります。そこで設計判断の記録は、主要な機能ごとに許容する体験と禁止する体験を表にしています。判定の物差しは 1 つで、記録の原文はこうです。

> 判定原則: 「1 日 1 タップ記録 → 数秒で完結 → 即離脱」動線に沿うか。[^adr12]

表から代表的な行を引きます。

| 機能 | 許容する体験 | 禁止する体験 |
| --- | --- | --- |
| スタンプカード | 1 日 1 回のサプライズ獲得 → 結果提示 → 即閉じ | 集めたものを眺める画面で滞在させる。未取得の枠を強調して取得欲を煽る |
| おみくじ | 1 タップ → 即結果 → 数秒で閉じる | 演出の長時間化。2 回目以降を引く動線 |
| バトル | 現実の活動の記録完了への 1 回きりの報酬 | ステージの周回、毎日入れる反復戦闘、スタミナ回復を待つ画面 |
| ごほうびショップ | 交換の動線のみ。必要なときだけ入る | 買わずに眺めて滞在する。おすすめ表示による回遊 |
| 通知 | 親の端末のみ。1 日 3 通まで。21 時から翌 7 時は送らない | 子供の端末への送信。呼び戻す目的の連打 |

最後の行に注目してください。子供の端末への通知は「送らない運用」ではなく「送れない構造」になっています。購読の窓口が子供の役割からの購読を 403 で拒否し、送信側でも二重に防いでいます[^adr12]。運用の決まりは破られますが、コードに埋め込んだ制約を破るには意図的な変更が要ります。この「原則を構造に落とす」姿勢は、本書の後半で繰り返し出てきます。

減点や罰に関する決まりも同じ扱いです。テンプレートの共有機能（みんなのテンプレート）の取り込み対象として「罰」型の決まりが設計上は存在しますが、取り込んでも何もしない警告になるだけで、子供の画面に到達する経路がありません。将来採用する場合の条件として、親の明示的な有効化、子供の画面への文言の非露出、累積の禁止、兄弟比較の無条件の却下、警告の表示の必須化、24 時間の待機期間が列挙されています[^adr12]。子供の失敗体験を強める機能は、作れるかどうかではなく、作ってよいかどうかの審査を先に通します。

## 原則が退けた案

この原則は、何度も「もっと遊べる機能」を退けてきました。中心の輪の設計理由を記録した文書は、3 層のモデルを採用するにあたって「ガチャ中心」の案を退けています。理由は、本章の原則に直接抵触し、連続で引く仕掛けや射幸心への訴えは子供側の滞在時間を増やす設計であって親の購入動機と反すること、そして紹介ページと実装の乖離を生んだ直接の原因でもあったことです[^rationale02]。

シーズンイベントの機構（イベントのバナー、シーズンパス、月替わりのプレゼント）は、自動配信による煽りと不確実な体験が本章の原則と「紹介ページの文言は実装の事実から作る」原則の二重の違反であると判定されました。結果として完全に撤去されました。代替の価値は、後述するチャレンジ機能が能動的に提供します[^ui06]。応援の完了画面は「もう 1 回応援」という誘導を意図的に持ちません[^ui06]。0〜2 歳向けのゲーム風の画面は、現実の利用がない以上「中心の哲学に反する」として廃止されました。代わりに親の準備モードが置かれています[^adr11]。

削るだけではありません。ごほうびショップの特権の交換では、以前は 1 回の申請で 1 個しか交換できず、「ゲーム時間 30 分」を 4 個使って 2 時間遊ぶには、子供の 4 回の交換と親の 4 回の承認が必要でした。個数の指定を入れて 1 回のタップと 1 回の承認に減らしたのは、滞在時間を削るための機能追加です[^ui06]。

## 発達心理学の裏づけ

この原則は好みではなく、子供の動機づけに関する研究の読み込みに支えられています。参考文献の一覧には 3 種類の研究が並びます[^psych]。有形の報酬が内発的な動機を有意に低下させ、言葉の報酬は肯定的な効果を持つとする 128 研究の統合分析（Deci, Koestner & Ryan, 1999）。報酬の予告で幼稚園児が自発的に活動する時間が減った実験（Lepper, Greene & Nisbett, 1973）。5 歳未満は社会的な比較をほとんど行わず、幼児に比較の情報を与えることは発達の面で不適切とする研究（Butler, 1998）です。

これらは製品の具体的な判断に落ちています。兄弟の競争モードは削除され、協力型だけが残りました。ランキングは親が明示的に有効にしない限り表示されません。褒めるときは結果ではなく努力を、という Dweck らの知見は、親向けの応援メッセージの文言設計に入っています。

## 原則を機械で守る

「原則を書いた」だけでは、原則は守られません。がんばりクエストはこの原則を 3 つの層で機械的に検査しています。

1 つ目は紹介ページの語彙です。紹介ページの寸法を測る検査のスクリプトが禁止語の一覧を持ち、「ガチャ」「抽選」「コンプリート」のような射幸性を暗示する語や「ゲーミフィケーション全開」のような逆のメッセージの語を検出すると自動検査を落とします[^measure]。本書の原稿もこの語を本文に書けないよう、同じ規則を本書の検査に足しました。

2 つ目は画面の構造です。ここには失敗の記録があります。

**狙い。** 子供のホーム画面には注意を奪う横長のバナーを置かない、という原則がありました。

**起きたこと。** バナーが 2 度撤去されたあとで 3 つ目が残り、ホーム画面を開くたび全員が常時目にする状態まで悪化しました[^banner]。

**なぜ。** 守る手段が人の注意だけだったからです。原則は文書にあり、レビューでも指摘されましたが、次の変更で別のバナーが足されることを止める仕組みがありませんでした。

**変えたこと。** ホーム画面のソースを静的に解析し、禁止一覧の部品が読み込みと配置のどちらにも現れないことを、単体テストで守るようにしました[^banner]。

```ts
// tests/unit/architecture/child-home-no-fullwidth-banner.test.ts
const CHILD_HOME_MARKUP = [
	'src/routes/(child)/[uiMode=uiMode]/home/+page.svelte',
	'src/lib/features/child-home/components/ProdDashboardSections.svelte',
];

const DENYLISTED_BANNER_COMPONENTS = ['ChallengeBanner', 'MustProgressBar', 'MilestoneBanner'];

describe('child home fitness function — 独立横長 banner 残置禁止 (#3333 / ADR-0061)', () => {
	for (const rel of CHILD_HOME_MARKUP) {
		it(`${rel} は denylist の横長 banner を import / mount しない`, () => {
			const source = stripComments(readFileSync(resolve(REPO_ROOT, rel), 'utf-8'));
			for (const comp of DENYLISTED_BANNER_COMPONENTS) {
				// import 文 (`import X from ...`) と element mount (`<X`) の双方を禁止。
				const importRe = new RegExp(`import\\s+${comp}\\s+from`);
				const mountRe = new RegExp(`<${comp}[\\s/>]`);
				// ...
			}
		});
	}
});
```

このテストは、通常の単体テストとは性格が違います。振る舞いではなく「構造がこうなっている」ことを検査し、原則からの逸脱をプルリクエストの時点で落とします。本書ではこの種のテストを契約テストと呼びます。Neal Ford らが『Building Evolutionary Architecture』で示した手法です。体系的には [第Ⅴ部-4](fitness-functions) で扱います。

**読者のリポジトリでは。** 同じ原則が 2 度破られたら、3 度目を人の注意で防ごうとしないでください。ソースを読むテストを 1 本書けば、次の違反はプルリクエストで落ちます。

3 つ目は端末側の時間です。画面の設計書には、子供の画面を 15 分連続で使うと自動でスリープに入る仕組みが記されています[^ui06]。記録して閉じる用途なら 15 分は使いません。開いたまま放置された端末が、遊び場に変わることを防ぐ最後の壁です。

## 「卒業」を成功と呼ぶ

この原則を最後まで突き詰めると、製品の成功の定義が変わります。紹介ページには「卒業」というページがあり、こう書かれています。

> アプリを開かなくなった日 — それは家族の卒業式
> 「使わなくなる」ことががんばりクエストの成功。記録はいつでも書き出してご家族の手元に残せます[^graduation]

解約の理由に「卒業」を選ぶと、専用のページに遷移します。そこでは残ったポイントを現金や物品や体験に換算して親に還元する提案をし、ブランドのキャラクターが祝福します。同意があれば、実名を禁じたニックネームと卒業のメッセージを事例として公開できます[^ui06]。解約の画面は通常、引き止めの場です。がんばりクエストではそれを、製品が役目を終えたことを祝う場にしました。

継続率を最大化する設計と、卒業を祝う設計は両立しません。この製品は後者を選び、その選択を設計判断の記録、自動検査の禁止語、単体テストの構造検査、自動スリープという 4 つの層で固定しています。

## 持ち帰るもの

- 買う人と使う人が違う製品では、使う人の滞在時間が買う人の利益と逆向きになりうる。指標を決める前に、誰が何のために払うかを書く
- 原則は「採用しない体験」の表にする。表があれば、新機能の提案を数分で審査できる
- 原則が 2 度破られたら、文書とレビューを増やすのではなく、構造を読むテストで固定する
